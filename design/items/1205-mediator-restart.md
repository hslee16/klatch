A restarted mediator matches its own dm proposal by a fixed lead, not the exact text (#1205; no schema or wire change; 2026-11-24).
What the ticket asks. #1205 (a follow-up to #1191) says the dm proposal line carries the exchange count N, which grows, and that a restarted mediator finds its earlier posts by exact text, so it may repeat the line once for an exchange that is still going. It also leaves open which member is told to open the dm (today the line names both and gives the command for the second name) and offers two options: key the case on the room and the pair only and match the earlier post by a fixed prefix, or name the member who posted the 4th message. The triage of 2026-11-24 found it not built and named the smallest step: key the case on room plus pair and match by a fixed prefix.

    How a restart repeats the line. The stuck case is already keyed on room and pair (`long_exchange:<room>:<a>,<b>`, `StuckEvent::key`), so inside one run the `done` set holds it and a growing count changes nothing. The set is lost on a restart. The first pass of a new run seeds it from the mediator's own earlier posts (#906), by comparing each planned proposal's text with the text of those posts exactly. For a long exchange the text holds the count, so a post written at N=4 does not equal the line a new run plans at N=6 for the same pair, the seed finds nothing, and the line is posted again. Any other proposal is a fixed template of names and numbers that do not change while the case stands, so the exact match works for them.

    The same proposal means the same room and the same pair. The fix: a proposal may carry a fixed `lead`, the start of its text up to the number (`mediator proposal: @a and @b have exchanged `), and the seed counts an earlier post as the proposal when its body equals the text or starts with the lead. Only the long exchange sets a lead; every other proposal keeps whole-text matching. The lead holds only names from the stuck event, never member text. The room is not in the lead (the count sits before it) but the history read is of the one watched room and the event's room is that room, so room and pair are both fixed by the read plus the lead. Which member opens the dm is not decided here (the line is unchanged); that stays an owner question on the ticket.

    Authorship. The lines already have the marker this needs: the seed reads only posts whose sender is the mediator's own member name (`m.sender == self.me`), so a member who writes a line that looks like a proposal, with or without the right count, suppresses nothing. No text of an existing line changes, no marker was added, and no stored form changes. Cost: the seed is still the one bounded history read (`HISTORY_MAX_MESSAGES`), made once per run; the match is a prefix test per planned proposal per post.

    Known limit. A post of the same pair from an earlier, ended exchange that is still inside the bounded window suppresses a new proposal for the same pair on the first pass after a restart (before, only an identical count did). A run in progress already forgets a case that ends, so this affects the first pass of a run only; a pair that moves on and returns is proposed on again after that pass. The stale ask proposal has the same shape (its text holds the age in seconds, which grows) and is left as it is, ticketed separately.

    Tests. A restarted mediator over a store that holds the proposal does not repeat it after the exchange has grown (red first by assertion); another pair and another room after a restart each get their own proposal, and a forged member line with the lead does not suppress a real one (both passed before the change, they pin the surrounding behaviour); the domain test pins the lead, that a count change matches and a pair change does not, and that other proposals keep whole-text matching. Mutation checks: matching only the whole text fails the restart test and the domain test; widening the lead to `mediator proposal: ` fails the pair test and the domain test; dropping the sender filter fails the forged-line tests.
