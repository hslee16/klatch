The gateway is shared across threads by one owner thread and a channel (#140; no schema change; 2026-11-20).
**Question.** The daemon of #102 and every listener after it serve several connections at once, but `Gateway` and `Direct` are single-threaded. The two ways out were (A) make the gateway shareable (`Arc` and a lock, or a connection per thread) and (B) leave it alone and give it one owner thread that serves requests from connection threads over a channel.

**What holds the single thread (read from the code).**
- `Direct` holds an `Rc<Gateway<S>>` (`gateway/transport.rs`); so do the `member` module and the `admin` command. An `Rc` cannot cross threads at all.
- `Gateway<S>` holds `Box<dyn Clock>`, `Box<dyn Guard>`, `Box<dyn Notifier>` and `Option<Box<dyn LeaseSource>>`, none with a `Send` bound. `Arc<Mutex<Gateway>>` needs `Gateway: Send`, so each of those traits (and each implementation, including the tests' `Rc<Cell<i64>>` clocks and the `SpyStore`'s `Cell` and `RefCell`) would need `Send`, and `SharedGateway` over a non-`Send` guard would stop compiling for callers.
- `SqliteStore` holds one `rusqlite::Connection` (`Send`, not `Sync`) and a `RefCell<LabelKeys>` (`store/sqlite.rs`). The label keys are per principal and live in the store, so a store shared by callers with different keys is a different design, not a lock.
- `Direct` also holds an optional `Box<dyn Harness>`, which has no `Send` bound.
- The `Subscription` is plain data (no store handle); `poll` takes the gateway as an argument. `Transport` has no blocking call: a wait is the loop in `commands/wait.rs` of `wait_poll`, `change_token` and a sleep on the caller's thread.

**Option A, an `Arc` and a lock.** Smallest at the call site, widest in the code: a `Send` bound on four traits and all their implementations, `Sync` for the store (so a `Mutex` around the connection, which is one writer anyway), and a decision on whether the guard, the clock read and the store write of a request run under one lock (they must, for the sequence and claim checks to mean what they do now). A connection per thread to the same SQLCipher file keeps SQLite's own write lock as the one writer but multiplies the label keys, the open cost (key read and schema check on each open) and the busy-retry behaviour (`Error::Busy`, not fair under load, `proto/CONCURRENCY.md`), and gives no common place to put the clock and the guard. Every request would also hold the lock for its whole length, so the same lock would serialize what the owner thread serializes in B.

**Option B, an owner thread.** No change to `Gateway`, `Direct`, the store, the clock, the guard or the notifier: the gateway is built on the owner thread (the caller passes a closure that opens the store), so none of it has to be `Send`. One connection and one writer, as today. A request is one whole `Transport` call, so the order the guard, the clock and the store see is the order of the channel. The cost is one channel round trip and a copy of the arguments per call, against microseconds of store work (a read of 20 messages is 0.007 ms, `proto/CONCURRENCY.md`), and one thread that a slow request holds up for the others; the same is true of a lock in A.

**Blocking calls.** Settled by the code, so nothing needed a decision: `wait` never reaches the gateway as a blocking call. The owner serves `wait_poll` and `change_token` (each a short request) and the caller sleeps between them on its own thread, so a bounded wait holds neither a lock nor the owner. The streaming subscription is a value the caller keeps and sends to the owner for the length of one `poll`.

**Choice: B.** It is the smaller change (one new file, nothing edited in the engine), it keeps the one-writer rule by construction, and it does not touch the cross-process design of `proto/CONCURRENCY.md` (other processes still meet the same SQLite file through its lock). Shuttle cannot see SQLite, so a Shuttle test of this module would test the channel and not the store; it was not added (the real-thread tests below are the evidence).

**What was built** (`gateway/shared.rs`).
- `SharedGateway::spawn(build)` starts the owner thread, builds the gateway there with `build` (returning the error `build` failed with, or `Backend` if it panicked) and returns a handle that is `Clone`, `Send` and `Sync`. When the last handle is dropped the owner stops and joins, so the store connection is closed.
- `SharedGateway::transport(principal)` gives a `SharedTransport` bound to one principal, like `Direct`. It implements all of `Transport` (the arguments are copied to the owner), with `with_harness` for the harness the edge learned (made on the owner thread for each request).
- A request that panics fails that call with `Backend` and the owner keeps serving.
- `change_token`: the store's token moves only when another connection commits, so a post made through the owner would not move it. The handle adds a count of posts made through handles, so an in-process wait wakes at once, and a commit by another process still moves the store's part.
- The `klatch` binary is unchanged: it still builds its own `Direct`, and nothing in it uses this module.

**Tests** (`gateway/shared_tests.rs`, a temp SQLCipher file, real threads): eight threads post 200 messages and the sequence is exactly 1 to 200, each message once and attributed to its own handle; four writers and a reader lose and duplicate nothing; eight threads claiming one path give one holder and seven `Conflict`s; a bounded wait returns within 1.5 s of another thread's post while a second caller is served at once during the wait; the owner stops when the last handle goes; a gateway that cannot be built is an error; a panicking request leaves the owner serving. The tests were written before the module (a compile failure was the red); the wait test's time bound was tightened after the first green run.

**Not done.** The daemon itself (#102) and any listener; per-connection principals from peer evidence (the edge's job). A slow request holds up the others, as it would under a lock; a pool of readers on separate connections would be a later, measured change.
