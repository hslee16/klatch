coordbench B1 gets working messaging, proves it in every run, and a board that does not manufacture conflicts (#1520, #1523; no schema change to the store; 2026-11-24).
The #1519 isolation gave every agent its own Claude config directory, and three real two-session probes on 2026-11-23 (Haiku, claude 2.1.331, macOS, the flags the driver gives a B1 agent) showed what that did: with one shared HOME and one shared `CLAUDE_CONFIG_DIR` `ListAgents` names the partner, `SendMessage` is delivered and the partner replies; with a separate HOME and a separate config directory per agent `ListAgents` shows no reachable agents and `SendMessage` fails with `No agent named b is reachable`; with a separate HOME and one shared config directory it works again. The peer registry follows `CLAUDE_CONFIG_DIR`, not HOME, and the user's other interactive sessions were never visible, so nothing has to be closed. Until this item B1 was a straw man (B0 plus a board) and nothing noticed.

  Decision: the agents of one B1 or B1-roles run share ONE config directory, `<scratch>/agents/cfg-<token>`, mode 0700, made under the run's scratch (never `~/.claude`), beside the agents' directories and not inside one. HOME, TMPDIR and clones stay per agent in every arm, and every other arm keeps one config directory per agent. The sandbox settings of a B1 agent allow read and write of that directory in place of its own per-agent one (nothing else is new); the scan's policy allows it for B1 agents; a K or B0 run never has it, and the same path in their scratch is under the guarded scratch root, so their policy denies it and their sandbox settings do not list it (tests/test_b1_config_dir.py). A B1 agent is still denied other agents' clones, homes and tmp directories. The honest tradeoff, written in README, SPEC and PILOT: B1 agents share config-directory state, which is the price of native messaging, and K arms are unaffected. With `--no-session-persistence` and the settings passed by file the agents should write little there, but this was not verified by looking at a real run (none was made; no API key in the builder's session): the record carries `messaging_verified.config_dir_entries`, the files a run left in the shared directory, so the first real B1 run answers it.

  Verification (`messaging.py`, recorded in `messaging_verified`, null for every other arm): `tools_present` (every init event that carries a tools list names `SendMessage` and `ListAgents`; null when no stream carries a list, as with fake agents), `listagents_named_peer` (some `ListAgents` result lists a teammate as `NAME [id]`, in the shape `Peer sessions (1): b [eab75d] ... busy`; `No reachable agents` names none), `messages_sent` and `messages_delivered` (a result that begins `Not sent`, `Not delivered` or `No agent named`, or carries is_error, is not delivered), plus `listagents_calls`, `status`, `reason` and `config_dir_entries`. Status `failed` makes the run INVALID with the reason in `notes`: an init event lacks a tool, or a `ListAgents` result came back while another agent had been alive for at least 15 s (the grace period, since a session binds its inbox a few seconds after it starts; the probe started the partner 15 s earlier) and no `ListAgents` result of the run ever named a teammate. Status `unknown` keeps the run valid and says so: one agent, no `ListAgents` while a colleague was alive (every agent finished before another started), or streams without times. Status `verified`: some result named a teammate. Times come from the harness clock on the result events and the start and exit times of each session. Known limit: a run whose agents never call `ListAgents` stays `unknown`, so the trivial B1 pilot run is the real proof only if an agent lists agents.

  Board and arm text (#1523): B1 repositories are seeded with `.gitattributes` containing `TASKS.md merge=union` (the harness writes the board, so it writes this, both for fixtures it builds and in the history fixture), so two appends merge without a conflict and the stream parser counts none; the tallykit and onefile checkers skip `TASKS.md` in their conflict-marker scan (every other behaviour unchanged). The waiting paragraph of every arm now ends with the same sentence, a limit of 5 minutes in total for any one result, true for `sleep` and for `klatch wait` alike; B1 tells agents to add `answer: FACT (from NAME)` to the board, which S4's late and repeat asks and S6's orphaned ask depend on. The text version label default moves to `draft-2`; the harness has no hash of the built prompts, so the version stays a typed label (the review's I8). The other checkers (chain, history, injection, scale, recovery, specialists) still scan `TASKS.md` for markers; with the union merge none should appear, and a ticket tracks making them skip it too.
