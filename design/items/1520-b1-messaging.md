coordbench B1 gets working messaging, proves it in every run, and a board that does not manufacture conflicts (#1520, #1523; no schema change to the store; 2026-11-24).
The #1519 isolation gave every agent its own Claude config directory, and three real two-session probes on 2026-11-23 (Haiku, claude 2.1.331, macOS, the flags the driver gives a B1 agent) showed what that did: with one shared HOME and one shared `CLAUDE_CONFIG_DIR` `ListAgents` names the partner, `SendMessage` is delivered and the partner replies; with a separate HOME and a separate config directory per agent `ListAgents` shows no reachable agents and `SendMessage` fails with `No agent named b is reachable`; with a separate HOME and one shared config directory it works again. The peer registry follows `CLAUDE_CONFIG_DIR`, not HOME, and the user's other interactive sessions were never visible, so nothing has to be closed. Until this item B1 was a straw man (B0 plus a board) and nothing noticed.

  Decision: the agents of one B1 or B1-roles run share ONE config directory, `<scratch>/agents/cfg-<token>`, mode 0700, made under the run's scratch (never `~/.claude`), beside the agents' directories and not inside one. HOME, TMPDIR and clones stay per agent in every arm, and every other arm keeps one config directory per agent. The sandbox settings of a B1 agent allow read and write of that directory in place of its own per-agent one (nothing else is new); the scan's policy allows it for B1 agents; a K or B0 run never has it, and the same path in their scratch is under the guarded scratch root, so their policy denies it and their sandbox settings do not list it (tests/test_b1_config_dir.py). A B1 agent is still denied other agents' clones, homes and tmp directories. The honest tradeoff, written in README, SPEC and PILOT: B1 agents share config-directory state, which is the price of native messaging, and K arms are unaffected. With `--no-session-persistence` and the settings passed by file the agents should write little there, but this was not verified by looking at a real run (none was made; no API key in the builder's session): the record carries `messaging_verified.config_dir_entries`, the files a run left in the shared directory with sizes and hashes, so the first real B1 run answers it (the first real run, a B1 pilot on the trivial fixture, left 8 files, 147 KB of them `.claude.json`; what that holds is ticket #1545).

  Verification (`messaging.py`, recorded in `messaging_verified`, null for every other arm). Fields: `tools_present` (every init event that carries a tools list names `SendMessage` and `ListAgents`; null when no stream carries a list, as with fake agents), `listagents_named_peer` (a `ListAgents` result lists a teammate under its `Peer sessions (N):` header, one `  b [eab75d]  ·  interactive  ·  busy  ·  started 16s ago` line per peer; the asker's own `This session is a [id]` precedes the header and is not a peer; `No reachable agents` names none), `messages_sent` and `messages_delivered`, `listagents_calls`, `status`, `reason`, the clock facts (`clock`: the settle time, the latest agent start, each session's alive window; `first_listagents_after_all_started`: who, when, how long after the last start, whether it named a peer; `listagents_results`) and `config_dir_entries` (path, bytes and sha256 of every file the run left in the shared directory, a snapshot at the end of the run). The real `SendMessage` result is JSON, `{"success":true,"message":"..."}` or `{"success":false,"message":"No agent named 'b' is reachable..."}` (or `Failed to send to uds:...`), and is_error is NOT set on a failed send, so `messages_delivered` reads the `success` field (a non-JSON text falls back to a prefix check). Replaying the real probe streams gives 2 of 2 delivered (shared directory), 0 of 1 (separate config directories), 1 of 3 (separate HOMEs, one shared config directory: a to b worked, b to a failed twice).

  Status. `failed` makes the run INVALID with the reason in `notes`: an init event lacks a tool, or, at least 8 s (SETTLE_S) after EVERY agent of the run had started, a `ListAgents` result named no teammate (or a `SendMessage` failed with `No agent named` or `Failed to send to`) while another agent's stream shows it still running, and no `ListAgents` result of the run ever named a teammate. The first version used 15 s after the peer started, which fired only because the probe script started the partner 15 s earlier; a real agent's first `ListAgents` result comes 3.6 to 4 s after it starts and the harness starts the agents together, so the regression this item fixes would have come out unknown. The reason now says what `ListAgents` showed (`No reachable agents`). `unknown` keeps the run valid: one agent, no probe at least 8 s after the last start with a peer still running (the real B1 pilot on the trivial fixture: no `ListAgents` at all), or streams without times. `verified`: some result named a teammate, meaning the teammate was found and a message could be accepted for it; it does not mean a message was read. Because an unknown run proves nothing, report.py labels any B1 or B1-roles group that holds a run whose status is not `verified` (or whose record has no such field) 'messaging unverified' in the arm tables, the tests, the comparison and a note at the top, and SPEC says a B1 comparison is made only on verified runs. The B1 prompt does not ask agents to call `ListAgents` (prompt parity): the proof comes from a fixture whose agents depend on each other (S3 chain, run by the coordinator), where an agent has a reason to list agents.

  Board and arm text (#1523): B1 repositories are seeded with `.gitattributes` containing `TASKS.md merge=union` (the harness writes the board, so it writes this, both for fixtures it builds and in the history fixture), so two appends merge without a conflict and the stream parser counts none; the tallykit and onefile checkers skip `TASKS.md` in their conflict-marker scan (every other behaviour unchanged). The waiting paragraph of every arm now ends with the same sentence, a limit of 5 minutes in total for any one result, true for `sleep` and for `klatch wait` alike; B1 tells agents to change status by adding a line instead of editing an old one and to add `answer: FACT (from NAME)` to the board, which S4's late and repeat asks and S6's orphaned ask depend on. The text version label default moves to `draft-2`; the harness has no hash of the built prompts, so the version stays a typed label (the review's I8). The other checkers (chain, history, injection, scale, recovery, specialists) still scan `TASKS.md` for markers; with the union merge none should appear, and a ticket tracks making them skip it too.

  Review follow-up on the board metrics. merge=union keeps stale lines (a changes its last line working to done while b appends: the merged board has `- a | working | x.py | T1` and `- a | done | x.py | T1`), so board.py reads the LAST line per (agent, title) in file order as the current state; the one overlap a clone's own pre-pull commit shows (b appended before seeing a's done) is still counted as the blind claim it always was. A board edit is a message (SPEC 5) only when it adds a line that starts with a shared prefix (`seeking:`, `answer:`, `handoff:`, `need-info:`, `info:`), not a claim or status line, and not again when the same agent sent that text with `SendMessage` within 30 s (`boardmsgs.py`); a K answer and the equivalent B1 sequence both count 1. `.gitattributes` is appended to when it exists, created otherwise.
