A mutual TLS listener in klatch-server (#108, epic #13, gate #157; no schema change; 2026-11-23).
`klatch-server https --listen IP:PORT --tls-cert PEM --tls-key PEM --tls-client-ca PEM [--allow-off-loopback]` serves the wire of `klatch-server http` (the same routes `GET /v1/stream`, `POST /v1/frames` and `POST /mcp`, the same events, resume by `seq`) behind rustls. It is hosted by the `klatch-server` crate; the `klatch` binary stays network-free and credential-free. The owner's decisions of #157 (2026-11-23) are what is built: rustls (already in the tree for the optional `jev-http` feature, with ring; `cargo deny check` passes with `proto/deny.toml` unchanged), operator-supplied server certificate and key and a CA file for client certificates, no CA, no enrollment and no certificate generation inside klatch, and a certificate that only gates the port.

    The gate is the handshake. Client authentication is mandatory: rustls's `WebPkiClientVerifier` is built on the CA file and nothing makes it optional. A client with no certificate, a certificate from another CA, an expired one or one that is not for client use fails the handshake and gets no byte of HTTP; a plaintext client gets nothing either. There is no plaintext mode, no `--insecure` and no option that skips a certificate or name check; `tests/no_network.rs` scans the source for every rustls name that would skip one. TLS 1.3 and 1.2 are what rustls offers (it has no 1.1 or 1.0, so a downgrade has nothing to fall back to; a TLS 1.1 client is refused and a TLS 1.2 only client is served). Session resumption and tickets are off, so every connection passes the whole check again and an expired certificate or a replaced CA file is never trusted from a cache. After the handshake `policy::check_peer(MutualTls, ..)` runs once more as a backstop.

    A certificate is a key to the port, not a name. The caller is still the worker credential (`Authorization: Bearer` with `X-Klatch-Member`), checked live by the same guard as over loopback; with a valid certificate and no credential the answer is the one `401`. The certificate's subject is never read, mapped or logged, and there is no new `PeerEvidence` variant (the ticket text of 2026-11-12 asked for one; the owner's decision of 2026-11-23 replaces that). Revocation is the operator's: short-lived certificates, or a new CA file (the file is read at start and on SIGHUP, #1492). No CRL and no OCSP is checked, stated in the module, SECURITY.md and the tunnel guide: revocation means short-lived certificates or a new CA (ticket #1491 for a CRL option).

    Where it listens. `klatch::session::policy::check_mutual_tls_bind` is the one way a klatch listener may leave loopback: a client CA must be configured, and an address that is not loopback needs `--allow-off-loopback` (off by default, named in the refusal, shown in the readiness line). The address is parsed, never resolved. Plaintext off loopback still has no way to start: `bind_loopback` and `check_bind(Plaintext)` are unchanged. `loopback::bind_mutual_tls` asks the policy before the crate's one `TcpListener::bind`, and `tests/no_network.rs` pins the order and that only `wire_https.rs` calls it.

    The key file. It must be a regular file (opened with `O_NOFOLLOW`, so not a symbolic link), owned by the user running the server, with no bit for group or other (mode 0600), checked on the open file before a byte is read; otherwise the server refuses to start before it opens the store. Key bytes go to rustls and are dropped; no message or log line holds any (tests assert the refusals carry no PEM text). The server certificate and key must belong together (rustls checks); a CA file with no certificate is refused.

    How the handlers are reused. `wire_http.rs` handlers take a connected stream and nothing else, so the TLS module makes an in-process pair of local sockets after the handshake, gives one end to `wire_http::serve_connection` and carries the other end's bytes through TLS with a small non-blocking pump (bounded windows both ways, so a slow client cannot grow memory without limit). The pair has no address: no local process can reach the plaintext side, and no second listener exists. `Shared` and `serve_connection` became `pub(crate)`; no handler changed. `tests/tls_wire.rs` runs one scenario with one client against `http` and `https` and compares the frames (responses in order, stream frames as a set), and resumes a stream by `seq` over TLS.

    The scan test and the documents. `tests/no_network.rs` is narrowed, not loosened: rustls and ring may now be in the dependency tree (the jev-http test keeps `ureq` and `webpki-roots` out), but rustls may be named only in `src/tls.rs` and `src/tls_bridge.rs`, no name that skips a check may appear in `src/`, no other TLS or crypto stack and no certificate generator (`rcgen`, a dev-dependency used by the tests for throwaway certificates) may be linked into the server, and the one `TcpListener::bind` is reached by two checked ways. The documents state the claim again: klatch-server opens loopback listeners only, plus one mutual TLS listener that exists only when you name your own certificates, starts no program and makes no outbound connection. The listener is experimental and unreviewed; it does not change the release scope (remote transports remain out of the first release), and an outside review stays a hard gate for an unmarked release (section 23).

    Half-close and the pump. A client that sends its request and then half-closes (a TCP FIN, or a TLS `close_notify`) is done sending, not gone: the pump hands the handler every byte, then shuts the handler's end for writing (as a loopback client's FIN shows it) and carries the answer until the handler is done, then closes TLS with `close_notify`. The first version stopped at the client's end and dropped the answer (found in review, reproduced, fixed with tests: FIN, `close_notify`, pipelined requests, and a POST whose body is still unread when the client closes). The pump has a stall deadline (`--stall-secs`, default 60, longer than the event stream's 15 second heartbeat): no byte moved in either direction for that long closes the connection, so a client that never reads cannot hold a connection or a buffer forever. The poll leaves out a descriptor nobody asked about (a hung-up descriptor is reported even with no events requested and made the loop able to spin).

    The handshake is bounded. `--handshake-secs` (default 3, at most 60), `--max-handshakes` (default a quarter of `--max-connections`, at least one, at most `--max-connections`) and `--stall-secs` (default 60, from twice the event stream heartbeat, 30 seconds, to 86400) are checked at start; a value outside its bound, or not a number, refuses to start naming the flag and the bound (a huge value made `Instant::now() + deadline` panic, or silently disabled the limit; the deadline is now also built with `checked_add`). The floor for the stall time exists so that a stream that is only waiting for its next heartbeat is not cut; a debug build, and only with the environment variable `KLATCH_TEST_SHORT_LIMITS`, lowers that one floor so tests need not wait a minute (a release binary does not have the knob: it is compiled out). The place a connection takes among the handshakes in progress is a guard whose drop gives it back, so a panic in a handshake cannot leak the slot or the descriptor.

    Who loses when the cap is full (`tls_limits.rs`). Every handshake in progress younger than half the deadline: the newcomer is refused (closed at once), honest or not, so an honest client that is mid-handshake is never evicted by a flood (tested with a client that sends its hello in pieces while twelve silent sockets arrive); a valid client that arrives while the cap is full of fresh silent sockets is turned away until they are old enough. The oldest handshake at least half the deadline old: it is closed and the newcomer takes its place, so a flood of silent sockets clears one newcomer at a time and a valid client gets in (tested). What remains: a peer that keeps the cap full of fresh connections keeps newcomers out, and an honest client that is slow past half the deadline can be evicted. The cap bounds a flood; it does not remove denial of service by volume. The residual cost is low: a peer with NO certificate that keeps the handshake cap full of fresh connections needs only a few connections per second (a reviewer starved 10 of 10 honest clients at a cap of 4 with about 3.3 connections per second; with the defaults, a cap of 8, a 3 s deadline and a 1.5 s minimum age, roughly 5 to 6 per second). It was equally cheap before the age rule; what the rule changed is that a client already mid-handshake is no longer evicted. The real remedies are a firewall, a tunnel or loopback, and the per-source limit (done in #1493, below).

    Pre-handshake limits (#1493, `tls_limits.rs`, `tls_admit.rs`). Verified before the change: the pool of #1498 already bounded how many connections were in the handshake, but a connection took a place under `--max-connections` at accept, before the handshake, so silent sockets used up to `--max-handshakes` of the session places (a test with 3 silent sockets and a cap of 4 served 1 of 4 valid clients). Two changes, the smallest that work. (1) The session cap is counted after the handshake (`SessionSlots`); the accept loop's own bound (descriptors and threads) is `--max-connections` plus `--max-handshakes`, and a connection over the session cap is closed after its handshake, as an excess connection always was. (2) A per-source share of the pool: `--handshakes-per-source N` (default 2, 1 to `--max-handshakes`, checked at start with the flag named). The source is an IPv4 /32 or an IPv6 /64 (a host or a site is given a whole /64, so counting /128 would let one machine hold as many places as it has addresses); an IPv4-mapped IPv6 address counts as its IPv4 address. A newcomer over its source's share is closed at accept with no byte (TLS has no HTTP before the handshake, so there is no 503), unless that source's own oldest handshake is at least the minimum age, which then gives way (the same rule as the pool). The share keeps one source from filling the pool by itself; it does not stop the pool's own eviction (below). Bookkeeping is bounded by construction: the table has one entry per handshake in progress (an entry is removed at zero), so it never exceeds `--max-handshakes` entries whatever number of distinct sources arrive, and nothing needs an expiry; eviction counts the evicted source out once and its ticket does not count it again. A refusal is counted and summarised as one log line with a count and no address at most every ten seconds. Found by the slow-loris test: the handshake called rustls `complete_io`, which loops on reads inside one call with a timeout set before it, so a peer sending one byte at a time inside that timeout was never cut; the handshake now takes one read per step and shrinks the timeout to the time left each time. Tests: `tests/tls_flood.rs` (silent sockets do not take session places; the session cap holds; the per-source share closes the excess and the places come back after a client reset; every ending of a handshake gives its place back, with one place in all so a leak fails; a byte at a time is cut at the deadline) and unit tests in `tls_limits.rs` and `tls_admit.rs` (two sources with injected addresses, the table bounded under 1024 distinct sources, eviction counting, the /64 and mapped-address rules, the log summary). Not covered: two real source addresses (macOS has no 127.0.0.2 alias by default and the tests add no unsafe code to bind a source), so the cross-source case is a unit test with injected addresses.

    What #1493 does not do, measured on the real binary (review of #1630). A client that shares an address with the attacker (NAT, shared host, shared IPv6 /64) can still be locked out cheaply: with 50 silent sockets held from that address a client retrying every 100 ms got in after 1.56 s; against an attacker opening 2 silent connections per second 8 of 58 attempts succeeded, at 4 per second 3 of 75, against reconnect-on-close 0 of 60, and a client that does not retry failed every time (about 2 connections per second hold one address's share). So the change protects OTHER sources and open sessions, not a client that shares the attacker's address. And once the pool is full a newcomer of any source closes the OLDEST handshake that is old enough, of any source (the rule of #1498 is unchanged), so with a handful of IPv4 addresses or one IPv6 /48 the churn attack of #1498 still works against everyone. Tickets for the stderr write under the refusal log's mutex, NAT64 and link-local source keys, and refusal threads counting against the accept limit are the reviewer's.

    The minimum age and slow links. The minimum age is half the handshake deadline, 1.5 seconds at the defaults. An honest client is exposed to it only when the cap (8 by default) is full of handshakes AND a newcomer arrives AND that client's handshake has already lasted more than 1.5 seconds: a client with a round trip near half a second (or a lost packet and a retransmit) can be in that state, a LAN or ordinary WAN client is not. Under ordinary load the cap is never full, so the rule never applies. Raising the minimum age protects slower clients and costs the same amount of time the other way: a flood of fresh silent sockets keeps newcomers out for as long as the minimum age (they are refused until the flood is old enough to clear). An operator whose clients are slow sets `--handshake-secs` higher (up to 60; the minimum age follows at half), which trades a longer lockout after a flood for protection of slow handshakes. A different rule would evict by idleness (no byte received for a while) instead of age since the start: an honest client makes progress at every flight, a silent socket makes none. That needs a counting wrapper around the socket the handshake reads, which is a code change not made here; it is the better rule if slow honest clients turn out to matter. The red CI run of `an_honest_client_mid_handshake_is_not_evicted_by_a_flood_and_the_flood_is_refused` (#1509) was not this rule: the test used a 5 second minimum age and failed about 2 times in 50 under CPU load because it did not wait for the server to have the honest handshake in progress before the flood came, so under load a flood socket could take the last place first and the honest client, arriving at a full cap of young handshakes, was refused (as designed). The test now waits for the server's answer to the hello (an event) before the flood, waits for the server to close the flood sockets (an event), and uses the longest deadline so that no machine is slow enough for the age rule to apply.

    The stall clock counts only bytes that move on the client socket, written to it or read from it, not bytes the handler hands to the pump; so a client that accepts nothing is cut once the pump's window and the kernel buffers are full, and the handler's output does not keep it alive. What this cannot do: cut a client that has stopped reading a QUIET stream. Its kernel still acknowledges the 15 second heartbeat for as long as the receive window and our send buffers take to fill (days: tens of bytes every 15 seconds), and the bytes did move. Cutting it sooner needs an application-level acknowledgement that the wire protocol does not have, or a change to the handler; no test of it exists for that reason. A busy stream (more than the buffers hold) is cut, and tested. After a finished answer the pump flushes `close_notify` for at most two seconds, then drains what the client still sends for at most two seconds in all (the first version bounded only the bytes and could hold the socket about 13 seconds against a client trickling one byte at a time; tested), so the close comes at most about four seconds after the handler is done.

    The poll spin. A hung-up descriptor is reported by `poll` even when no events were asked for on Linux; the pump now gives `poll` -1 for a descriptor nobody asked about. No behaviour test shows the spin: macOS does not report the hang-up without a requested event (the mutation that lists the descriptor again passes every behaviour test there), and showing it on Linux needs a one-shot response bigger than the pump's window and the socket buffers, which no route produces and which no Linux machine here could confirm. The unit test of the helper (`poll_fd`) catches the mutation and is the only test of it.

    The policy sees the real client CA: the CA file is read first and `client_ca_configured` is whether it holds a certificate, so the policy's refusal is reachable and tested.

    Not covered. No run against a second machine or a real network path; the tests connect over loopback with throwaway certificates (rcgen). No OCSP; a CRL is optional (`--tls-client-crl`, item 1491). No client certificate subject check by design. Rotation is by SIGHUP (#1492, below). Denial of service by volume is bounded, not removed: a flood fast enough to evict a valid handshake while it is in flight, or any peer that can reach the port, still costs the server work; hence `--allow-off-loopback` is off by default and a firewall or tunnel is advised. The TLS 1.1 refusal test uses the system `openssl` when there is one and skips otherwise. The pump is exercised by the conformance scenario, the resume test, the half-close tests and the stall test, not by bodies near the 1 MiB limit (#1494).

    Reload on SIGHUP (#1492, 2026-11-25; no schema change, no new dependency, no new unsafe site). The certificate chain and key, the client CA file and the client CRL file are read again, through the same functions as at start (`tls::client_roots`, `tls::build_config`, `tls_crl::read_crls`), so no check is copied: key mode 0600 and owner, certificate and key fit, the CA file has a certificate, and every CRL check of #1617 and #1625 (DER reader, caps, owner, one CRL per issuer, `nextUpdate` rules, warnings printed again). The signal reuses the crate's one mechanism (`daemon::install_signal_handlers`, the `sigaction` call already reviewed there): the handler only sets an atomic flag (`daemon::RELOAD`). A watcher thread in `src/tls_reload.rs` takes the flag about every 100 ms, so a flood is one reload running and one pending, and starts a build at most every 500 ms. The build runs on its own thread with a 5 second bound (a FIFO as the CA file costs one abandoned thread and a log line; no other reload starts while it is stuck; a late result is never swapped in). Only a finished `ServerConfig` replaces the `Arc` in `Current` (a `Mutex<Arc<ServerConfig>>`, pointer assignment under the lock); each connection clones the `Arc` when accepted and keeps it, so open streams are not cut and no connection sees a half-built configuration. Any failure keeps the old configuration and logs `reload failed: KIND` with KIND one of a fixed list (client CA file, client CRL file, server key file, server certificate, key and certificate do not fit, other, timeout, an earlier reload has not finished); success logs one `reload ok` line. Flags are not re-read. The plain `http` server now catches SIGHUP and ignores it: before this item SIGHUP ended it with the default action (a test showed it), so "ignores SIGHUP as today" held only under `nohup`. The daemon keeps the default.

    Tests (`tests/tls_reload.rs`, written first and seen to fail): a new server certificate is served to new connections after SIGHUP and not before (files are not watched); an open event stream survives and still works; a CA file with no certificate, a garbage, group-writable, doubled-issuer or missing CRL, a key that does not fit, a key mode of 0644 and a certificate file with no certificate each keep the old configuration, log the kind and leave no key, subject or serial in the log, and a later good reload works; a client accepted before is refused after a reload with a CRL that lists it; the CRL warnings print again; a flood of 100 SIGHUPs gives 1 to 5 reloads and the server works; a blocking CA file times out, the next signal is told one is unfinished, and SIGTERM still stops the server; SIGHUP does nothing to `http`. Not covered: a revocation does not cut a stream that is already open (by design; stop the server for that), and no test of a reload racing a flood of handshakes beyond the stream and flood tests.

    Review fixes of #1492 (2026-11-25). (1) `read_pem` now opens the CA file and the server certificate file with `O_NOFOLLOW | O_NONBLOCK`, checks a regular file of at most 4 MiB on the open descriptor, and for the CA file (a trust anchor) the owner (this user or root) and no group or other write bit, at start and at reload; before, a FIFO at the CA path hung start and made one reload thread block forever, which disabled every later reload ("an earlier reload has not finished"), and a symlinked or world-writable CA file was accepted. Symlinked CA files and certificates are now refused (a documented change; operators name real files). (2) The flood tests now fail on the two mutants that survived (`flag.load` instead of `swap(false)`, and a spacing of 0): one SIGHUP is exactly one reload, a flood stops rising, and a sustained flood is spaced. (3) A reload refuses a CRL file that has expired while the CRL in force is in date (`tls_crl::Stage::Reload`), with an ALERT line; start is unchanged. (4) The watcher stops when the accept loop returns for any reason, and a wait for a build looks at the stop flag every 100 ms. Not covered: the STOP-after-return path of `serve_concurrent` (the non-blocking failure) has no test; a build blocked on a stalled mount still disables reload until restart.
