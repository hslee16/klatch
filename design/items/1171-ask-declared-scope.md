An ask may declare a scope and could_answer checks it (#1171; store schema 37; 2026-11-22).
The decision on #627 listed "scope covers what the ask names" as part of the could-answer check, but a member scope is a free-form word and an ask is free text, so nothing defined what an ask names. The human decided on 2026-11-22 to let the asker say so: an ask may carry a declared scope, in the grammar of a member scope (`valid_scope`: 1 to 80 characters of letters, digits and `. _ : - /`), and `could_answer` compares it with the member's own scope. Prose is never parsed for paths or repository words.

The rule is one condition: the check adds a blocker with the rule word `scope` only when BOTH the ask and the member declare a scope and the two differ. An ask with no declared scope changes nothing, a member with no scope changes nothing, equal scopes change nothing. So every existing ask, every store from before, and every old client behave exactly as they did, and a false "no" can only come from two declarations that disagree. The reason names the ask number, the two scope words and the member, never the ask's text. Scope stays advisory in klatch (a scope only partitions claims and now this one check); clearance still gates access.

The scope is stored in a side table `ask_scopes(room, seq, scope)` (schema 37, migration `migrate_v36`, one row per ask that declares one), not in the message and not in its text, so the message rows, the archive and the sealing of bodies are untouched and a second declaration replaces the first. An ask with no row has no scope. `AskStore` gets `set_ask_scope` and `ask_scopes` (a default that remembers nothing for stores without the table), and `open_asks` fills `OpenAsk.scope` from them.

Wire: `post` takes an optional `scope`, accepted only when the body starts `seeking:` and not together with `kind` or `payload` (`invalid` otherwise, nothing posted, the scope validated before the post). It goes through a new gateway method `post_scoped`, which runs the same checks as `post_labeled` for the same `Post` operation, so it adds no capability (AUTHZ-AUDIT rows `post`, `ask`, `asks`, `could_answer` updated). The scope comes back as `scope` on the ask in `asks`, and on the ask message in `read`, `history`, `wait`, the hook digest and the stream (an optional `scope` on the `message` frame, added within protocol version 1 like `advisory`); the gateway overlays it where it already overlays the advisory mark, from the stored record and never from the text. The CLI shows it as `[scope S]` after the ask in `asks`, the board and `read`. A client that omits the field posts exactly as before. A new client that sends `scope` to a server older than this change is not supported: the old server ignores the unknown param and posts a plain ask, which only loses the declaration (noted in PROTOCOL.md).

CLI: `klatch ask ROOM TEXT --scope S`. `--scope` with `--to` is refused (a dm ask carries no scope; a limitation, not a decision). The Rust client (`PostRequest::scope`), the TypeScript client (`post(..., { scope })`) and the Python client (`post(..., scope=...)`) carry it.
