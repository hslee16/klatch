A supervisor restarts a lapsed local gh-watch receiver, bounded and keyless (#1342; no schema change; 2026-11-24).
gh-watch-supervise is a new small script, not a mode of ask-supervisor or team: those carry issued identities, the human-run admin check on the live store and spend caps, and a restart of a local receiver needs none of them. Each pass reads the receiver pid file and the watch:gh claim (klatch claims ROOM in the isolated status store; KLATCH_HOME unset or inside .klatch is refused). Pid dead with the claim still held is the kill -9 window (#1601): it waits for the lapse and runs nothing. Pid dead with the claim lapsed runs gh-watch ensure, but only with evidence of a crash (the dead pid was seen with the claim held, or a recent lapsed_claim in klatch stuck before the first restart), so a clean stop is left stopped. A live pid with a lapsed claim is an ALERT, never a kill. **Bounds:** at most 3 ensure runs per rolling hour, the wait before the next doubling from 60 s (60, 120, 240; capped at 600); an attempt counts whether or not it worked; at the limit it logs one ALERT, says to run ensure by hand, and exits 3. It never starts the forwarder (that needs the human admin:repo_hook token), installs a launchd unit, runs gh, or reads a credential; if klatch claims fails it reports and restarts nothing. Log lines are fixed templates in gh-watch.log with only self-counted numbers, so no claim, room or webhook text is used in a command or a line.

Alternatives considered: extending ask-supervisor (carries the live-store and credential surface into a keyless job); a mode inside gh-watch (grows the launcher that agents run at session start and needs a long-running loop there); relying only on launchd KeepAlive (not available on every host and not installed by an agent). A launchd KeepAlive receiver and this supervisor do not fight: ensure is a no-op while the receiver is up.
