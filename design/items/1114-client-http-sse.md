The Python and TypeScript client libraries connect to `klatch-server http` over HTTP and server-sent events (#1114, follow-up of #1059; no schema change; 2026-11-21).
**Question.** What is the smallest change that lets a client library use the HTTP and SSE wire of #1059, as `connect_socket` (#1095) lets it use the daemon, with the same session code above the transport?

**What was built.** `Client.connect_http(url, member=, token=)` in Python and `Client.connectHttp(url, { member, token })` in TypeScript, standard library only (`http.client`, `node:http`). The url is plain `http://127.0.0.1:PORT` (also `::1` and `localhost`); anything else is a `ValueError` or `TypeError` before a byte is sent, so the library never sends a token to a remote host or over TLS it does not do. A member without a token, or the reverse, is refused the same way; there is no typed-name tier over HTTP, because the server has none.

The transport is a reader and a writer handed to the code the stdio and socket connects already use, so requests, `collect`, `next_message`, the hello and every refusal path are unchanged. The reader opens `GET /v1/stream` with `Authorization: Bearer` and `X-Klatch-Member`, takes `X-Klatch-Session` from the answer, and yields the `data:` of each event, which is one frame line exactly; `event:`, `id:` and comment lines are skipped. The writer sends each frame line as `POST /v1/frames` with the session header, in order, and the response arrives on the stream. A `401` on the stream is an error with code `identity.refused` that never repeats the token. A `429` (the session's inbox is full) is retried at 50 ms for at most 40 tries; any other answer than `202` to a post is a protocol error (`404` is an ended session). `close` drops the stream, which ends the session on the server, and returns 0.

**Resume.** The transport remembers each room a `subscribe` request named and the last `seq` seen in it. When the stream ends without a `close` (a clean end, or any error on the read, which includes a reset), it reopens a stream with the same credential, drops the new `hello` (the caller has one), and posts `subscribe` with `from_seq` set to the last seq seen for every room still subscribed (an `unsubscribe` removes it). The server's sequence numbers are the store's, so the replay is the same messages with the same numbers and the caller sees no gap and no repeat. The response to a resubscribe carries a library-chosen id and is ignored like any response nobody waits for. Defaults: five reopen attempts with a growing delay; when they fail the session ends and the next request is a protocol error. A post that was in flight when the stream dropped is not repeated (the library cannot know whether the server ran it).

**Tests.** `clients/python/test_http.py` and `clients/typescript/http.test.ts`, written before the code (the Python file was run red, 14 errors; the TypeScript file was written first but not run red before the code). The success path runs against a small in-process server that speaks the wire of #1059 (SSE events, comment lines, the session header, `202`, `429`, `404`), because a verified connection needs a worker credential and only the human issues one: hello first and the credential headers; a request as a POST with the session header; history, then live messages with the server's numbers; a dropped stream reconnects and resubscribes from the last seq without a repeat; an unsubscribed room is not resubscribed; an error injected into the reader (not provoked from the platform, so Linux and macOS agree, the lesson of #1105) is a dropped stream and not a crash; a server that stays gone ends the session; busy and ended sessions; refused credentials; local argument checks; loopback-only urls; a port nobody listens on; close. The refusal path (`identity.refused`) also runs against the real `klatch-server http` when it is built. Every wait has a deadline and no test reads a stream to its end. Beyond the suites, the success path was run by hand against a real server with a credential issued in a throwaway store, from both libraries: replay, live, resume after a dropped stream, two members, `dm`.

**Not done.** The Rust client (it needs a TCP type in the `klatch` crate behind an off-by-default feature, #1122). The full conformance scenario over HTTP in the Python and TypeScript suites (no credential can be issued from them, #1123). Keep-alive and `Last-Event-ID` (the server does not interpret it, the library resubscribes). TLS and remote exposure (#157, #161).
