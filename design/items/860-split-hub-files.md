The hub files are split by family so parallel pull requests stop colliding (#860; decided in #533; no schema change; 2026-11-20). Three files that nearly every pull request edited were the main source of merge conflicts: `kani_proofs.rs`, `commands.rs` and `main.rs`. Each is now a directory or a set of files by family, and nothing about behaviour changed: the command line help text (checked by diffing `--help` for every command before and after), the output, the exit codes and the module paths other code imports are the same.

`commands.rs` became `commands/`: `mod.rs` keeps `Ctx` and `run`, and `messaging.rs`, `work.rs`, `agents.rs` and `wait.rs` hold the handlers of one family each. The command line moved too: `Cmd` in `main.rs` flattens one clap enum per family from `args/` (`MessagingCmd`, `WaitCmd`, `WorkCmd`, `AgentsCmd`) and keeps the commands that belong to no family (init, consent, doctor, the servers, the sub-command groups). `display_order` on every variant keeps the help in its old order. `kani_proofs.rs` became `kani_proofs/` with one file per area (paths, names, larger bounds, labels, session and key proofs) and a shared `common.rs`; the `mod` declarations keep their `cfg(kani)` and `cfg(feature = "cli")` gating and `proto/scripts/kani` reads the directory.

A test (`hub_files_stay_split`) fails when any file under those directories grows past 600 lines, so a new command goes in the file of its family. The tests that read the command list from `main.rs` (`authz_audit`, `facilitator_brief`) read the family files too. The Kani move could not be run here (Kani is not installed); it was checked by compiling the module under `--cfg kani` against a stub `kani` crate, by comparing the sorted harness names (35, unchanged) and by comparing the sorted lines of the old and new files (only module structure and imports differ).
