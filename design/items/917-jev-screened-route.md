Jev screened routing advice: one request, route question plus noul screen, guard first (#917, part of #898; no schema change, no new wire method or command; 2026-11-21).
`klatch::jev::facilitate::advise_route` is the pure core the facilitator loop will call. It builds the route question over label gated facts (`route_question`), adds the noul screen "does this ask need to be routed to a recipient at all?" to the same request (one call per ask, per fan-out), and applies `pick_screened`: a clear no narrows to nothing, an unsure screen leaves the rules decision, a clear yes lets the pick run among the candidates the rules and the guard already allow. Jev can only narrow or route among those candidates, never widen, and a name outside them is ignored. Every failure (a gated sender or topic, no key, a refused request, a transport error, a malformed reply, a missing screen or route answer) leaves the rules decision. It is tested only with the fake transport; no live call.

    Still open on #917, and why. The facilitator loop does not yet call it: members, rooms and claims carry no label, so there is no per-fact label source to build the `Labelled` facts from, and there is no operator setting for the screen's yes and no thresholds (documented starting points 0.7 and 0.3 are `NoulThresholds::default`, not validated on klatch data). Both need a design and probably a schema change, so they are left to their own ticket rather than guessed here.
