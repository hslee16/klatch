The ignored forwarded-header count is shown live and kept in the audit, with no write per request (#1490, epic #13; no schema change; 2026-11-26).
The count of `forwarded.rs` (#110) was in memory and showed once, at shutdown. Both servers (`http` and `https`) now run a timer thread beside the accept loop (`forwarded_report.rs`). Live read: one counts-only line on stderr (`forwarded identity headers seen so far: requests=N name=K ...`), at most once per interval (60 s) and only when the counts changed since the last line. Durable: one `forwarded-ignored` row in the existing `admin_audit` table (target empty, detail `requests=N name=K ...`) at most once per interval (10 minutes), only when the counts changed, holding what was counted since the previous row, plus one at shutdown after the last connection has ended; the rows add up to the total across restarts and `klatch admin audit` shows them. A short interval (1 s and 2 s) exists only in a debug build with `KLATCH_TEST_SHORT_LIMITS`.
How it avoids write amplification: a request only bumps an in-memory counter (`Ignored::note`, handed names, never a value, and holding no handle to the store). The timer is the only code that writes a line or a row, and `Pacer` hands out at most one of each per interval however fast the counts move; a store that refuses a row is not asked again before the next interval and the counts stay unkept until a row succeeds. So an unauthenticated flood of requests carrying these headers costs one line a minute and one row per ten minutes at most (about 144 small rows a day), plus one row at stop. The listener already holds the store through the gateway it embeds (`Backend::note_forwarded_ignored`, which runs on the gateway thread like every other backend call), so no credential or key is added to the server. The gateway keeps a row only when the text is lower case letters, digits, `=`, `-`, `*` and spaces (at most 512 bytes), so a header value cannot be stored even by a bug in the caller; the action name is fixed.
Options not taken. A schema table of counters (a new migration, a table per name, an update per interval): the audit row already carries a time, a name and a counts text, and survives the same retention; rejected as heavier for no new capability. A write on each counted request: rejected, it would let a pre-auth client cause one store write per request. A counts file outside the store: rejected, a second place for state with its own permissions. A new admin call that reads the live in-memory count: the admin path talks to the store, not to the running listener process, so it could only read the rows; the rows are therefore the read path for admin and the stderr line is the live one.
Limits: the rows lag the live count by up to ten minutes (the shutdown row closes the gap on a clean stop; a kill loses what was counted since the last row); `https` now also writes the shutdown summary line it did not have before. Not run: any real proxy.
