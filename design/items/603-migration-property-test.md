Every older schema version migrates with its data intact, tested by a generated fixture (#603; no schema change; 2026-11-19).
The generator in store/sqlite/tests/migration_property.rs builds a database at version N by creating the prototype schema (version 0) and running the first N migrations (MIGRATIONS is now visible to the crate tests), reads each table back with PRAGMA table_info, and fills it with rows whose values are distinct per row, through raw SQL. It then runs the real migrate and checks that every row keeps the value of every column it had, and that the migrated tables and columns equal a fresh store (members.last_id, which the prototype had and nothing drops, is the one named legacy column).

    Decision on the ticket: no binary fixtures. Freezing one database per version would need a dump from each release, most of which no longer build; the generator needs none, and the real frozen databases in fixtures/store plus the hand-built cases in migrations.rs stay as the check on what old databases looked like. The honest limit is that the version-N schema comes from the migrations themselves, so a migration that is wrong about its own predecessor is not caught here. Cost: an in-memory database per case, about two seconds for the exhaustive tests and the default 100 generated cases, so it runs in the existing workspace tests and adds no job or gate step. Planted bug: a migration that rewrote a column (claim_waits.ts + 1 in version 28 to 29) failed both the exhaustive test and the property.
