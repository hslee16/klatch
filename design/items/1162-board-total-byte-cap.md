The board text has a total byte cap (#1162; no schema change; 2026-11-21).
The board text that the `board` wire method and `klatch board` return was bounded only per section (`BOARD_LIST_LIMIT`, 20 entries), so six sections of long lines could grow past any size a client expects. Decision: `render_board` now cuts the whole text to `BOARD_MAX_BYTES` (16000 bytes, `domain/budget.rs`). The cut drops entry lines (the indented ones) from the end of the text and keeps every header line, so each section is still named and the `[board ROOM]` line is intact; the per-section 20 entry bound and its "and N more" lines are unchanged. One fixed last line says `[N more board entries not shown; the board text is capped at B bytes]`, with counts only and none of the dropped text. A board within the cap is byte for byte what it was. Headers and the trailer are kept even when a cap is smaller than they are, so the count is never lost.

Why 16000. The other bounded outputs are sized by who reads them: the hook digest is 8000 bytes and a whole hook 9400, because Claude Code keeps only a 2 KB preview of hook output of about 9.8 KB or more (#549); `history` is 16000 (`HISTORY_MAX_BYTES`). `klatch board` and the wire method are explicit reads, like `history`, not pushed into a session, so they take the `history` size. Worst case before the cap is about 6 sections of 21 lines of 260 characters (above 30 KB); 16000 loses nothing a normal board holds and cuts only a board of many long lines. The session start hook keeps its own tighter cut (`board_within`, #557) on top of this one.

Not decided: a structured board (typed sections instead of text) for clients; the options are on #1162. Tests: `domain/board/tests/render.rs` (a board within the cap is unchanged, over the cap keeps every header and counts the rest exactly, a tiny cap keeps headers, the default cap holds for a board of maximal lines); they were red first (the function did not exist). Not a new operation, so `proto/AUTHZ-AUDIT.md` has no change.
