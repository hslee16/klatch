The klatch wire over HTTP and server-sent events, loopback only: `klatch-server http --listen ADDR` (#1059, phase 3 of epic #1056, the transport of #109; no schema change; 2026-11-21).
**Question.** What is the smallest HTTP mapping of the wire protocol that is not a second protocol, takes who a caller is from a credential, and opens no socket beyond loopback?

**What was built.** `proto/klatch-server/src/wire_http.rs`, with a concurrent accept loop in `loopback.rs` (`serve_concurrent`, a thread per connection, a cap, every open connection shut down on stop). `GET /v1/stream` registers a session and answers `text/event-stream`; it runs the same `Session` over the same `SharedGateway` as the daemon, so a frame means what it means on stdio. Each frame is one event: `event: <type>`, `data: <the frame line exactly>`, and for a `message` frame `id: <room>:<seq>`. The header `X-Klatch-Session` names the session. `POST /v1/frames` with that header writes the JSON lines of the body into the session and answers `202` with no body; the `response` to a request arrives on the stream, as it does on the daemon's connection. Closing the connection ends the session; a post to an ended session is `404`. A session is fed through a bounded inbox (`429` when full) and its output goes through the session's bounded queue and stall limit (#147).

**Resume** needs nothing new: sequence numbers are the store's, so a new stream sends `subscribe` with `from_seq` set to the last `seq` it saw (the `id:` of the last message event) and receives the same messages with the same numbers. `Last-Event-ID` is not interpreted (a room is not implied by it); the client library does the resubscribe.

**Who a caller is.** Both routes need `Authorization: Bearer TOKEN` and `X-Klatch-Member: MEMBER`: a worker credential the human issued, checked live by `verify_credential` exactly as the daemon's `identify` checks it, giving the existing `PeerEvidence::Credential` and a verified principal. The ticket asked for "a new PeerEvidence variant"; none was needed (`Credential` is the one kind that yields a verified principal, and `Bearer` with the evidence table exists for a registered-token mapping later). There is no typed-name or unattributed tier over HTTP. Every failure is the same `401 unauthorized`; the credential is checked before the session lookup and before the body is read, and another member's session is `404`, as absent as a missing one. The token lives only in a header, never in a URL, a log or a reply.

**Loopback only.** `loopback::bind_loopback` refuses every address but `127.0.0.1` and `::1`, naming #157 and #161, before the store is opened. Nothing connects outward. The scan test is unchanged: the new module names no socket type (it uses `loopback::Stream`), and there is still exactly one bind.

**Limits.** 16 KiB headers, 1 MiB bodies (`413` before the body is read), a 5 second request deadline, `Transfer-Encoding` refused, `--max-connections` (default 32, the excess `503`), one exchange per connection (`Connection: close`). After a refusal the server lets the client finish sending (bounded) so the answer is not lost to a reset.

**Tests** (`klatch-server/tests/http_wire.rs`, the server as a child process, a temp store, loopback sockets with read timeouts; `wire_http.rs` unit tests). Written first: the 12 integration tests were red (the subcommand did not exist). The unit tests were written with the code. Covered: non-loopback binds refused; the credential matrix (eight ways of not having one, all 401, token absent from replies and log); hello, event ids and data; 404 for foreign and unknown sessions; two members with dense sequence numbers; resume from the last seen number; garbage in a posted frame; routes, methods, sizes and chunked bodies; the connection cap; SIGTERM; a store that cannot be opened; and the conformance run, the scenario of the daemon test through the in-process session loop and through HTTP and SSE (responses equal and in order; stream frames equal as a set; sequence numbers 1 to 4 then 5 to 8).

**Not done.** Client library HTTP transport (the Rust, Python and TypeScript clients each hold a child process or a socket; not the same small change; ticketed). A bench scenario (the bench cannot drive a `klatch-server` child, #1078). Keep-alive, `Last-Event-ID`, TLS and remote exposure (#157, #161, phase 5).
