Schema numbers are derived and looked up, so two PRs do not claim the same one (#1070, part of #1064; no schema change; 2026-11-21). A migration PR used to edit four hand-kept places that all had to agree: the `SCHEMA_VERSION` literal, the length of the `MIGRATIONS` array type, `VERSIONING.md` and about a dozen literal `35`s in the migration tests, so two PRs claiming the same number each cost a hand renumbering.

    What changed. `SCHEMA_VERSION` is now `MIGRATIONS.len()` (the list is a slice), and the tests compare with the constant, not a literal; a new step is a `migrate_vN` function, one list line and the `VERSIONING.md` line, which `tests/release_docs.rs` already checks. A test (`the_list_names_each_step_once_in_order`) reads the list and requires `migrate_v0`, `migrate_v1` and so on, each once and in order, because with a derived constant a union merge that keeps both PRs' identical `migrate_vN,` lines would otherwise pass quietly. `proto/scripts/next-schema` prints the next free number: one past the highest migration on origin/main and in the patches of the open PRs (REST only), so a PR looks before it claims. A claim named `schema:N` was considered and left out: it needs a live room and a running klatch, while the script needs only git and gh.
