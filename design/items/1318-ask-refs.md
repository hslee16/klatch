An ask can carry references to artifacts outside klatch (#1318; store schema 38; 2026-11-22).
The human asked on 2026-11-22 for context inclusion "as wide as possible": an asker can point an ask at a GitHub ticket or pull request, a commit, a file or line range, a log, a test, a tool, or another klatch message, ask, room or run, so a helper does not parse prose to learn what the ask is about. An ask may carry an optional list of refs. Each ref has a `kind`, a `value`, an optional short `label` (up to 120 bytes) and an optional inline `snippet` (up to 8192 bytes of text, for example the failing output) that gives the helper context without fetching anything.

The kind is open: any token of `[a-z0-9_.-]{1,32}`. The kinds klatch knows get their value checked and nicer rendering: ticket (any tracker), pr, commit, branch, tag, release, path, diff, test, log, ci-run, doc, url, tool, mcp-tool, command, dataset, message, ask, room, run, member, other. An unknown kind is accepted as opaque text, so a new artifact type needs no wire change. The checks of the known kinds are only about shape: `pr` is `#N`, `owner/repo#N` or an http(s) URL; `commit` is 7 to 64 hex digits (optionally after `repo@`) or an http(s) URL; `path` is relative and cleaned (no leading `/`, no `.` or `..` segment, no empty segment) with an optional `:N` or `:N-M`; `url` is http or https; `message` and `run` are opaque ids; `ask` is `N` or `ROOM#N`; `room` and `member` are names; every other known kind is one token with no spaces (a ticket may be `ENG-123`).

Caps are generous and refuse, never cut: up to 32 refs per ask, a value up to 1024 bytes on one line, a label up to 120 bytes on one line, a snippet up to 8192 bytes, and 65536 bytes over every kind, value, label and snippet of one ask. Anything over a cap is `invalid` and nothing is posted.

What klatch does not do is the point. It never fetches, opens, runs or resolves a ref: the binary stays network-free and credential-free. A `tool`, `mcp-tool` or `command` ref is a name or a line of text for a person or an agent to act on, never executed by klatch. A ref is data, not an instruction, and is rendered inert: every control character and bidirectional override is escaped, a value and a label are folded to one line, and a snippet's lines are shown behind a `| ` margin so a snippet cannot pass for a line of the log or of klatch's own output. A ref never implies a scope; only the declared scope of #1171 does, and a ref and a scope may go on the same ask.

Wide does not mean unsafe. A ref carries no credential: a URL (any scheme) with userinfo, or with a query or fragment value that is named like a secret (`token`, `key`, `secret`, `password`, `auth`, `sig`, `session` and the like) or shaped like a token (24 or more token characters with a letter and a digit, other than a plain git id), is refused with the rule `credentials` and the reason never repeats it; every value, label and snippet also goes through the same secret detector, canary check and private-term rules as message text. The label checks are those of the ask: a ref has no label of its own and cannot raise or lower the ask's. An ask under a sealed label carries no refs at all (its text is kept under the label's key and a ref row is stored beside it in the clear), and a `room` ref or an `ask` ref as `ROOM#N` must name a room that the ask's label covers, or the post is `refused` with the rule `label` (the reason names no label). A `message` ref is judged by the room that holds the message (#1328): the store answers a message id with its room name and nothing else (`MessageStore::message_room`, a read only, never a body, sender or label), and the same rule applies, so the post is `refused` with the rule `label` and the same words as for a room ref. The id is folded to upper case (the Crockford base32 alphabet ids use) before the exact lookup, so a lower cased id cannot read as unknown. A store that cannot look a message up answers with an error, never `None` (#485), and a store error in the lookup fails the post closed. An id that no message has is treated as a room that does not exist, which holds the lowest label, so it is accepted exactly as a `room` ref to a missing room is. What an asker can learn from this, precisely: a refusal says that a message with that id exists in a room above the ask's label (the same kind of fact a refused `room` ref tells about a room), and an acceptance says that the id is unknown or sits at or below the label. It does not say which room, and it never returns a body, sender, label or count. The ids are guessable in principle (48 bits of time, fixed bits, and a 32-bit counter, `store/ids.rs`), and the label check runs after authorization (the breaker, admin stops, clearance) and the budget and rate checks, so a stopped, throttled or uncleared asker gets that refusal for a hit and a miss alike and the probe is throttled like any post (#1599); the canary, credential and private-term checks on a ref still run first, as the body's do, because they read nothing about what exists. A `run` has no room in klatch (it is an opaque id of an outside run), so a `run` ref and a `member` ref (a name) stay shape only. The refusal of a room above the ask's label does tell the asker that such a room exists above that label; that is the same fact a refused `join` tells. Whether it should instead answer with the same words as a room that does not exist is a product decision, not made here (ticket #1582). Options: (1) keep the refusal as is, which says a room exists above the label; (2) make a room above the label read as a missing room, which means accepting the ref as an unknown room would be (the ref then points at a room the asker cannot see, harmless as klatch never resolves a ref) so nothing is revealed, but a dropped or accepted ref gives no hint that it is dead; (3) refuse every room ref that names a room the asker cannot join, existing or not, which hides existence but also refuses refs to rooms not yet created. The same choice would apply to `message` refs.

The refs are stored in a side table `ask_refs(room, seq, pos, kind, value, label, snippet)` (schema 38, migration `migrate_v37`), one row per ref in the order given, not in the message and not in its text, as the scope of #1171 is. An ask with no rows carries none, so every existing ask and every old client reads as before. `AskStore` gets `set_ask_refs` and `ask_refs` (defaults that remember nothing), `open_asks` fills `OpenAsk.refs`, and the gateway overlays the refs on an ask message where it already overlays the scope, from the record and never from the text.

Wire: `post` takes an optional `refs`, allowed only on a body that starts `seeking:` and not with `kind` or `payload` (`invalid` otherwise, like `scope`); an unknown key inside a ref is refused so a misspelt `snippet` is never dropped. It goes through the new gateway method `post_ask` (which `post_scoped` now calls), whose checks all run before anything is posted and then the checks of `post_labeled` for the same `Post` operation, so it adds no capability. The refs come back as `refs` on the ask in `asks`, on the ask message in `read`, `history`, `wait` and the stream (an optional `refs` on the `message` frame, added within protocol version 1 and absent when there are none), and on `could_answer` (kind, value and label only, never a snippet, and no verdict depends on them). The CLI shows `[refs pr o/r#12, ticket #4 +2]` after the ask in `read`, `wait` and the hook digest, one inert `ref KIND VALUE (LABEL)` line per ref in `asks` and the board, and the lines with snippets in `read` and `wait`. `klatch find` also matches an earlier answered ask by its refs (kind, value, label and snippet), shown as `[ref ...]` in the reason. Refs are not filters in `could_answer`: it shows them, it does not match on them.

CLI: `klatch ask ROOM TEXT --ref KIND:VALUE` (repeatable), with `--ref-label LABEL` and `--ref-snippet-file PATH`, which go with the `--ref`s in order (an empty `''` leaves one without). The CLI reads a snippet file itself, refuses one over 8192 bytes or not UTF-8 text, and reads nothing else. A dm ask carries no refs: `--ref` with `--to` is refused and nothing is sent. That is the same limitation as the declared scope on a dm ask (#1322), kept for the same reason: the dm path is `dm`, not `post_ask`, and giving it refs would add a second path through the facilitator and dm checks for a case nobody has asked for; a dm ask can say the same in its text, or the asker can ask in a room. The Rust client (`PostRequest::refs`, `RefInput`, `Message.refs`), the TypeScript client (`post(..., { refs })`, `AskRef`) and the Python client (`post(..., refs=[...])`) carry them.
