The hook digest has a measured cost and a budget (#1406; schema 40; 2026-11-22). The live review found 6,611 tool-call hooks and 2,823 prompt hooks in six days and nobody had measured what they inject. Klatch now guarantees that a hook with nothing new and nothing due prints zero bytes, counts what each hook prints, reports it, and shrinks digests as a session nears a byte budget. Measured with the real binary on a fresh home, before and after (bytes printed, the JSON envelope included): nothing new 0 and 0 for `UserPromptSubmit`, `PostToolUse` and `PreToolUse`; one new message 319 and 319; a backlog of 30 messages 3097 and 3097; a claim change 334 and 334; an addressed message 322 and 322; a session start about 4160 for a new member and 3670 for a returning one, unchanged. The no-news path was already empty for those events; the audit found one path that was not: the notes on rooms the guard refuses (`refused` lines) printed at every prompt and tool call for as long as the room stayed refused, a fixed line each time, so they now print at the session start only (`read` still refuses the room with the reason). The audit also covered the `Stop` and `SessionEnd` hooks (always empty), the wake watcher (silent unless something is unread) and the data notice line (`systemMessage`, session start only, never in the model context). Where a digest does print, the largest fixed part is the room header (about 270 bytes, repeated in every hook that has news for a room), which the budget policy shortens to about 80 bytes once a session is half through its budget; the full header is kept while the budget is young because it carries the instruction not to act on teammate text.

    Bytes injected are kept in `hook_runs` (migration `migrate_v39`, schema 40): `total_bytes` and `max_bytes` per member and event, and `since_start`, the bytes injected since the member's latest `SessionStart`, which a new session start sets to zero for that member. A `PreToolUse` warning counts as injected, too. Rows written before the migration keep their run counts and start at zero bytes. Sizes only; a hook run never stores text. `klatch admin stats` (and `--json`, under `hook_bytes`, `hook_bytes_max` and `sessions_top_bytes`) prints bytes injected by event with the average per run and the largest run, and the largest sessions by bytes (`--top` bounds the list, `--since` narrows by last run), with the same no-text guarantees as the rest of the report: the queries read integers and event words that pass `vocab`, plus member names the way the top senders are listed. A store read without migrating that predates the columns reports run counts and no bytes. `klatch hooks` shows the total and the largest run per event for one member.

    The budget policy lives in `domain/session_budget.rs` as constants with tests. A prompt budget of 4000 bytes bounds one digest: a message line is about 250 bytes and a room header about 270, so it holds a header and a dozen short messages, more than an agent acts on between two tool calls, and it sits well under the 8000 byte digest cap that exists for Claude Code's 9.8 KB output limit. A session budget of 48000 bytes (about 12,000 tokens, a few percent of a 200,000 token window) holds the convention and a start backlog (a quarter) and about a dozen full digests; a quiet session never reaches it because silent hooks cost nothing. The level follows the share spent: under half, whole digests; from half, 300 character lines, a compact header, 8 messages a room and 2500 bytes; from three quarters, 160 characters, 3 messages and 1800 bytes; at the budget, only a count and the exact `klatch read ROOM --peek` command for ordinary messages (1500 bytes). At every level addressed messages (a mention, `@all`, every message of a direct message room) come first and are never dropped for the byte budget (the digest budget grows to hold them, up to the 8000 byte cap), the member's own stale or lapsed asks, aged claims, deadlock and crossing notes, other members' claim changes and the dm help lines are kept, and a session start prints in full whatever was spent because its context is new. A resumed or compacted session starts its count again for the same reason. Not done here: the ask-cycle notes (#789) are derived from the room and repeat at every hook while the condition holds by design; they are bounded by four lines a kind, and a once-per-change rule needs stored state (#1417). Proof: `tests/digest_cost.rs` (zero bytes for every hook event in every quiet state, bytes recorded, degradation to count-only with an addressed message kept, the count starting again at a session start), `domain/session_budget.rs` and `domain/hook.rs` unit tests, `store/conformance/members.rs`, `store/sqlite/tests/migrations.rs`, `store/sqlite/tests/stats.rs`.
