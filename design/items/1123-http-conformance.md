The whole client conformance scenario runs over HTTP against the real server (#1123; no schema change; 2026-11-21).

The Python and TypeScript suites run every step of the conformance scenario over stdio, over the daemon socket and now over `klatch-server http`, against a real server in a throwaway store, so the same events and sequence numbers are required of every transport (replay, live push, resume after a dropped stream, two members, direct messages). Every HTTP connection needs a worker credential, and only the human issues one for a real store, so the suites issue theirs with a test-only helper, the cargo example `issue_test_credential` of the `klatch-server` crate: `issue_test_credential MEMBER [CLEARANCE]` prints one token on stdout. Being an example it is not built by `cargo build`, not in a release archive, a wheel or the npm package, and `cargo test --workspace` builds it for the conformance step of CI. It refuses to run unless `KLATCH_HOME` is a directory under the system temp directory or /tmp (not the temp directory itself, with `..` resolved and symlinks followed) and `KLATCH_KEY_DIR` is inside it, so the live `~/.klatch` store and the Keychain are out of its reach by construction. The suites skip the HTTP run when the server or the helper is not built; a member's attribution over HTTP is `verified` (proven by the credential) where the other transports say `unattributed`.
