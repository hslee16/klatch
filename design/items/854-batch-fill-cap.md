pr-sweep --batch fills its cap from the survivors (#854; script only, no schema change; 2026-11-21).
The candidate loop used to stop at `--max` before the pre-check, so a PR dropped for a code conflict still held a slot and a queue with two conflicting PRs batched only four of the default six. Now up to three times `--max` candidates are looked at (a bound on the green-check API calls) and the pre-check loop stops once `--max` PRs have survived; candidates not reached are left for the next pass and are not marked skipped, so the one-at-a-time path may still take them. Test: a queue of five with two conflicting with main and `--max 2` batches the two survivors (red before the change).

**Not built, left on #854:** (2) a resume path for a batch PR left open by a dead pass (the next pass lands it as an ordinary PR and benches each included PR separately); (4) the dry run pairs candidates against earlier survivors, not the accumulated branch, so a three-way conflict can differ (rare, documented). Gap 3 (remote batch branch kept) is moot: the repository has delete_branch_on_merge on, so GitHub removes it.
