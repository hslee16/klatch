`klatch admin stats` is a counts-only report, and an admin read act (#1377; no schema change; 2026-11-22). The 2026-11-23 review of the live store had to be done by hand in SQL; `klatch admin stats` makes it a command. It prints counts, timestamps, room and member names and words from closed vocabularies, never a message body, ask text, claim reason or note, label or payload. It reads the store file through a separate read-only connection (the way the growth line of `klatch doctor` does, no migration, nothing created) and its sections are: messages per room and per UTC day (with a per-room per-day matrix in `--json`), distinct and top senders and attribution counts, message kinds, asks (created, answered, closed, how many declared a scope or carry refs, and the median and 90th percentile seconds to the first answer by someone other than the asker), live claims, claim notes and members waiting on a claim by class, claim yields, refusals by rule, direct message and private room counts with their messages, members (joined, never posted, marked done, muted, with a parent), hook runs by event, admin acts by name and worker credentials issued and revoked. `--since DAY` keeps rows at or after that UTC day (live claims and hook runs are current or cumulative, so they are kept by their own timestamp), `--room` narrows the room-scoped counts and leaves the store-wide ones (hook runs, admin acts, credentials) as they are, `--top N` sizes the sender list and `--json` prints one object for the benchmark ledger.

The access rule. By default it is an admin read act, in the keystore family beside `archives` and `export`: the human passphrase at the terminal, `admin_authorize` for `stats` (so the admin agent role is refused and audited like any other non-floor act it may not do), standard output and standard error must be the controlling terminal (`prints_stored_text`), and one audit row records that it ran, with the room and day arguments and no result. The reasons are three. First, counts are not text, but they are metadata: who talked in which room, how many direct messages exist and between whom (a direct message room is named for its two members), and which members never posted are things the zero-trust model keeps from an agent that is not allowed them. Second, a report an agent can run lets an agent profile the other members, and the same reasoning gates `audit`, `refusals` and `archives`. Third, the human runs it once a month, so the passphrase costs nothing. A narrower act is possible and is left for a later change: one room's own counts (messages, distinct senders, asks and answers) for a member of that room could be a plain member read through the gateway, since the member can already read every message there; it would need its own guard row, a member-scoped query that never reads a direct message room the member is not in, and a decision on whether a sealed room's counts are the member's to see. The first change adds only the admin act.

What is read and what is not. Claims are classed by name prefix only (`ticket:`, `ask:`, a name with no colon is a file, anything else is other); the reason and the note are never selected. Kinds, rules, hook events and admin act names are shown only if they are short name words (`domain::vocab`), else as `(other)`, so a free-text value in a column that should hold a word cannot print. The one place a body is selected is the ask fold, which takes at most the first 48 characters of messages that start with an ask word to read the ask number and the sender, outside sealed labels, and drops the text at once; a message under a sealed label is counted in its room and never opened, so asks in a sealed room are reported as `sealed_unread` and not counted as asks. What the store does not record cannot be reported: there is no history of claim conflicts (only the members waiting now), no per-claim history beyond the notes, and the count of messages after archiving excludes tombstones.
