Bench timings, a robust baseline with its machine context, and a per-run history with a drift trend (#920; no schema change, no wire change, bench tooling only; 2026-11-18).
The bench (`klatch-bench`, release build, about 110 scenarios) checks timings against `proto/klatch-bench/baseline.json`: a metric fails only above 3x its baseline and at least 200 ms (`--factor`, `--floor`). Three gaps: few metrics had a baseline, nothing was recorded per run so slow creep was invisible, and the baseline did not say what it was measured on. This item closes them without adding the bench to CI (CI stays light; the bench is run by hand).

Which metrics exist. A timing is a metric whose name ends in `_ms`. The runner's own `integrity_ms` (the store check after each scenario, 1 to 5 ms) is not a timing: it is left out of budgets, the baseline and the history, because nobody acts on it. Timings were added only where a latency or throughput is the point: the hook run on session start (`session_start_hook_ms`, `session_start_ms`), on every prompt (`digest_hook_ms`), before every edit (`claim_block_ms`) and after every tool call (`post_tool_use_ms`); the wake latency from a post to the watcher ending (`wake_ms`); eight processes opening a new store at once (`race_ms`); migrating an old store (`migrate_ms`); key rotation (`rotate_ms`); backup, restore and readable export (`backup_ms`, `restore_ms`, `export_ms`). Skipped on purpose: the clock-driven functional scenarios (asks, claims lapsing, labels, retention windows, receipts, roles, rate limit, identity, judge, reviewer, liveness and the like). They run on the test clock, so their wall time is process spawns, not a behaviour anyone would tune, and a metric nobody will act on is noise. The facilitator, mediator, router, room grantor, stuck query, ACP front end, harness negotiation, member attribute and Jev features have no scenarios in klatch-bench on main (their tests are in `proto/klatch/tests`), so there was nothing to time; a scenario for each can add its metrics when it lands.

The baseline. `baseline.json` stays committed in its old shape (`{"scenario": {"metric": ms}}`, the shape `--budgets` reads). It is made from three full runs, not one: for each metric the median of the three, but the worst of the three when the runs disagree (spread above half the median and at least 20 ms), so a baseline never hides behind a lucky quiet run and a noisy metric gets a wide budget. The machine it was measured on is in the sidecar `baseline.meta.json` next to it: the rule, the git sha, and for each run its time, verdict count, OS, core count and one-minute load average, plus the list of noisy metrics. Compare timings from another machine with that in mind.

The history. `klatch-bench --record` appends one JSON line per run to the history file: `time` (UTC, from `date`), `sha` (with `+dirty` when tracked files differ), `passed`, `total`, `partial` (a run limited by `--layer` or names), `machine` (`os`, `cores`, `load1` at the start) and `timings` (`"scenario/metric"` in ms, only from passing scenarios). The file is outside the repository and never committed: `$KLATCH_BENCH_HISTORY`, else `$XDG_STATE_HOME/klatch-bench/history.jsonl`, else `~/.local/state/klatch-bench/history.jsonl`; `--history FILE` overrides it. A line that cannot be read is skipped and counted, never fatal.

The trend. `klatch-bench --trend` does not run the bench: for every metric it prints the baseline, the median drift over the baseline and the last five recorded values, and flags `CREEP` a metric whose last five runs were all above 1.5x its baseline and at least 25 ms over it (so one slow run, fewer than five runs, and a 5 ms to 9 ms wobble are not creep). It exits 1 when any metric crept, so it can be run from a script. This catches the case the 3x rule cannot: a metric that sits at 2x for a week and never fails once. Reading it: the first lines are crept metrics; a drift near 1.00x is steady; a drift below 1 is faster than the baseline (a candidate for a new baseline).

Running it. Quiet machine first (`uptime`; the load average should be below the core count; rerun a noisy run). Each run: `cargo run -q --release -p klatch-bench -- --budgets proto/klatch-bench/baseline.json --record`. Then `cargo run -q --release -p klatch-bench -- --trend`. To rebaseline after an intended change (three runs recorded on the same sha): `cargo run -q --release -p klatch-bench -- --rebaseline 3 --save-baseline proto/klatch-bench/baseline.json`, which uses the last three complete (not partial, all passing) runs and writes the baseline and `baseline.meta.json`; commit both. `--save-baseline` alone still writes a single run, as before.

Relation to the pr-ledger bench ledger. `pr-ledger --record-bench PR --bench-ledger FILE` records only that a merged PR was benched (a set of PR numbers, for the `merged-not-benched` stage); it holds no timings and no verdicts. The history holds timings and verdicts per run and knows nothing of PRs. They do not overlap or contradict: the ledger answers whether a merged PR was benched, the history answers how the numbers moved. The sha in each history line ties a run to a PR when someone needs to. Neither is a copy of the other, so each is the one source of truth for its question.
