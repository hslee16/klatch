A signed attestation of harness evidence from a remote host (#1138, design only; follows #1003; parked under the zero-trust epic #152 and remote exposure #1061, #157, #161; no schema change; 2026-11-21).
Decided by the human on 2026-11-21: a non-local peer (an ssh or HTTP member on another machine) may get harness-dependent room access (a `room-require` harness, #877) only with an attestation, never from a request field. Until one exists, a remote peer joins as the generic floor, as `serve --stdio --ssh-key` does today (#1115, #1130). This item is the design that the later build starts from. **It builds nothing and changes no code, schema or audit row.** It does not lift the block: every option below needs a real network transport (#157) and per-request authentication (#161) first, and a non-loopback bind is still refused (#1061).

**Words.** The gateway host (G) holds the store and judges the join; it is the verifier. The remote host (R) runs the agent and the harness (Claude Code today) and reaches G over a transport that crosses a machine boundary. An attestation is a statement signed by a key G's human enrolled, saying what R's side verified about the process that is connecting. The member is never in it: who the peer is stays the job of the key or credential the transport already proves (#107: an ssh label mapped to a member by the human; #880: a key bundle). An attestation answers a different question, "what harness runs that member", and it is added to a peer that is already identified, never used to identify one.

**1. Threat model.**

What an attacker gains. (a) Entry to a verified-harness room (`room-require harness=claude-code`, and the capabilities that follow the harness, such as `pre-action-enforcement`): the room's other members then trust that the peer's posts passed a harness that enforces claims and hooks. (b) An advisory flag: a mark that says a member is on a verified harness, which a human or another agent may weigh. Neither is a clearance: a harness standing opens no sealed label, no label key and no admin floor action, and the design must keep it that way (see rule 7). The loss if the attestation is forged is therefore a wrong trust signal in a room, not a label breach. That bounds how much strength is worth paying for.

Who attacks, and what each can fake today (before any attestation):

| Attacker | Position | What they can forge |
|---|---|---|
| Network attacker | On the path between R and G | Anything, if the transport is plaintext or unauthenticated. Removed by #157 (mutual authentication, no plaintext off loopback, `policy::check_peer`); this design assumes that layer and adds nothing for it |
| Hostile R host (its operator or root) | Owns the machine | Everything the host can sign or say: the process table, the registry, the signing key, the walk. An attestation from a hostile host is a true statement about nothing. No design that trusts the host can stop this; the answer is that the human enrolls only hosts it controls, and that revocation exists |
| Hostile process of the same account on R | Same OS user as the honest agent | Forge the harness registry record (`$HOME/.claude/sessions`), start a process named `claude`, read a signing key that lives in the user's files, ask any same-user signer to sign. This is exactly the limit the local mechanism already documents for `runs_claude_code`: "same-user evidence ... keeps an honest session from being mislabelled, and does not stop a process of the same user that forges the registry" |
| Hostile or prompt-injected agent inside a verified session on R | Inside the real harness | Cannot fake the harness (it really runs it) but can use a signer to attest for a different session, or run a non-harness process as a child and have it connect |
| A different tenant on R | A second account on a shared R | Should fail: separate OS users make a key file and a socket private; this is where a signer with its own user matters |
| Replayer | Captured an attestation once (a log, a backup, a compromised past session) | Reuse it on another connection, on another gateway, or later, or hand it to a different peer |
| A host that was honest | R was compromised after enrollment | Keep attesting after the human stopped trusting it; revocation must reach a session that is already open (the #1083 problem) |
| A local peer lying about being remote or the reverse | On G | Make a remote peer pass for local (to reach the process-tree path with a fake pid) or a local one for remote; the decision "remote" must come from the transport's own evidence kind, never an address or a field |

What is fixed by construction in every option: the attested facts are only as good as the weakest of three links, (1) the verification on R (the walk and the registry), (2) the custody of the signing key on R, and (3) the binding of the signed statement to this one connection. An attestation raises a remote peer to **at most the strength of a local one, which is same-user evidence**, and never above it. It does not make a harness provable against a hostile host or a hostile same-user process. The product must say so in words (SECURITY.md, the room mark) and must not call a remote attested harness "verified" without a qualifier. The only evidence that proves a harness against its own user would come from the harness vendor (option 5 below) and does not exist.

**2. What is attested.** A statement is a small canonical document, signed as a whole, versioned so a verifier refuses a version it does not know.

| Field | Meaning | Why |
|---|---|---|
| `v` | statement version | refuse unknown, no downgrade |
| `audience` | G's host id (a stable id G generated and shows `klatch doctor`) | a statement for one gateway is useless at another |
| `nonce` | a value G issued for this connection and this join, single use | replay (rule 5) |
| `channel` | a binding to the transport session (the TLS exporter value, or the ssh session id, whichever #157 gives) | a statement cannot move to another connection |
| `harness` | the harness id the signer verified (`claude-code`) | the one thing a room reads |
| `harness_version` | informational only, never judged | audit |
| `session` | a keyed digest of the harness session id, never the raw id | stable continuity for the member's session, no id leaves R in the clear |
| `tree` | a digest of the verified chain (program, pid, start time per hop) | audit and comparison between two attestations; **G cannot check it** (the pids are R's), so it never grants anything |
| `not_before`, `not_after` | the validity window, short, set by G's policy as a ceiling | limits a stolen statement; the signer may choose shorter |
| `signer` | the id of the enrolled key | which key to verify with, which to revoke |

Not attested, on purpose: the member name (comes from the transport's key or credential), any clearance or label, any room, any capability other than the harness id. A statement that carried a member would turn it into a second identity path, and #881 shows why the typed name must stay out of the harness decision. A request field named `harness`, `attestation_of` or similar stays an error on every session (the `member-fixed` family of #107, extended when built); the statement travels in its own handshake step before the first request, never inside one.

**3. Who signs.** Five options. Costs are stated as what is new, not as time.

**Option 1. The credential declares the harness (no per-session statement).** The human records, when it enrols the ssh label or issues the key bundle, which harness that peer runs (`klatch admin ssh-key LABEL MEMBER --harness claude-code`, and the #880 shape for bundles: the launcher records the harness it started in the credential row). G reads it from its own table, never from the peer. No signature, no nonce, nothing on the wire, so no replay problem and no new crate. Strength: the same as the key it hangs on (whoever holds the key is that harness, by the human's word); it says nothing about whether the process using the key is a real harness today, and it cannot tell the same key on a laptop from the same key copied to a server. Cost: a policy value (no schema change for the ssh label; a column or a policy row for the bundle, which #880 already says is a design decision), one more floor action flag, tests. It is not an attestation in the ticket's sense (nothing is verified at join time); it is the cheapest honest version of "from the human, not from a field". Whether it satisfies the 2026-11-21 decision is question 1.

**Option 2. The client binary on R signs with a host key (same user).** `klatch` on R, which already makes the walk for local commands, builds the statement and signs it with an attest key stored in the user's keystore or a 0600 file, then sends it in the handshake. Strength: honest-session mislabelling is stopped; a hostile same-user process reads the key or the registry and forges anything (the table row above). Cost: a signing crate through the dependency review (the weak-crypto refusal list applies; one Ed25519 implementation, no home-grown code), key generation and custody on R (#155), a handshake step and nonce store on G, enrolment, tests. No daemon on R.

**Option 3. A klatch daemon on R signs, after the kernel names the caller.** R runs the daemon (#102), which already learns the caller's pid from the kernel (`SO_PEERCRED`, `getpeereid`, `LOCAL_PEERPID`) and already runs the walk and registry check on that pid (`peer_runs_claude_code`, #1096). It signs a statement for that pid's connection and no other. Strength: the client cannot ask for a statement about another session, because the pid comes from the kernel, not from the request (this closes the "agent attests for a different session" cell); with the daemon under its own OS user and the key private to it, it also closes the key-theft cell for other accounts, and it closes it for the same account only if the daemon runs as a different user (a design choice with a real deployment cost). It still trusts the registry, which the same account can write. Cost: the daemon must exist on R and be the way R's agents reach G (a proxy: the daemon's session to G carries the attestation of each local connection, so one daemon connection per local session, or a multiplexed channel); the signer code path; an enrolment of the daemon's key on G; and the `check_peer` extension. This is the closest to the existing local mechanism: the same verifier, running on R, with its result signed. It is the option that gives the ticket's "remote host's own gateway" meaning.

**Option 4. The agent signs with a per-session key.** The harness or the agent generates a key at session start and signs. It proves only that one holder persists across the session (continuity), nothing about a harness, since the signer is the thing being judged. Use at most as a binding inside option 2 or 3 (a session key signed by the host key), never alone. Rejected as an attestation of harness.

**Option 5. The harness vendor signs.** Claude Code (or Codex) signs its own session evidence with a vendor-held key chain. This is the only option that holds against a hostile user of R, and it does not exist; klatch cannot make it and must not pretend to. Recorded so that if a harness ever ships signed session evidence the verifier slot is already named: the statement version and the `signer` field leave room for a vendor chain. Not buildable now.

**4. Key trust, enrolment and revocation.** Applies to options 2 and 3 (option 1 reuses the ssh-key and credential tables).
- **Which key.** An Ed25519 attest key, separate from the transport key (a transport key proves who connects; an attest key proves what verified the connection; one compromised must not forge the other). Each attest key is bound to exactly one transport label, so a key enrolled for host A cannot be used on the session of host B (the same one-to-one rule as `ssh-key-mapped`).
- **Who enrols.** The human, at a terminal, as a floor action (`FLOOR_ACTIONS`), so no agent and not the admin agent can add, change or remove one: `klatch admin attest-key LABEL <public key file> --harness claude-code`, stored in the policy table as `attest-key:<id>` (no schema change, as `ssh-key:<label>` is), audited as `attest-key` with the id and the label, never the key. The harness ids a key may attest are listed at enrolment, so a key enrolled for `claude-code` cannot attest `codex`. Key generation happens on R (the private half never travels); the human carries the public half to G, the way an `authorized_keys` line travels.
- **How the human grants it.** The grant is the enrolment itself plus the room side: a room decides whether an attested remote harness counts (question 3), the same `room-require` switch, not a new one per key.
- **Revocation.** `--off` removes the policy row. G rechecks it before each batch of requests and on each idle tick, as the ssh session does for its label (#1083, `Session::rechecked`), so an open session loses the harness standing at the next look. The standing is lost, not the session: the peer drops to the generic floor and rooms that require the harness refuse its next write; whether the session itself must also end is question 4. Every statement also expires (`not_after`), so a revoked key's statements die on their own even if the recheck were skipped. A refused statement (bad signature, unknown key, expired, wrong audience, reused nonce, harness not allowed for the key) is a kept refusal with a rule name (for example `attestation-invalid`), counted by the breaker with the other safety rules, so a host that keeps sending bad ones is stopped everywhere.
- **Rotation.** More than one key per label, as ssh labels allow, so a key is replaced without a gap; the old one is removed with `--off`.
- **Custody on R.** A 0600 file in a 0700 directory, or the OS keystore through the existing key code (#155, `klatch-keys`); a hardware-backed key (Secure Enclave, TPM) is the later hardening. A compromised key is a revoked key on G; there is nothing on R that G trusts without it.

**5. Replay protection.** Four layers, all needed, none sufficient alone. (a) A **nonce from the verifier**: G issues a fresh random value at the start of each connection (one challenge frame, answered before the first request) and again before a `join` that needs the harness; the statement must sign it; G accepts each nonce once and keeps only the unexpired ones, in memory (no schema), so a restart forgets them and a statement is also bound by its window. (b) **Audience**: the statement names G's host id. (c) **Channel binding**: the statement names the transport session (TLS exporter or ssh session id), so a captured statement does not work on another connection even within its window and on the right gateway. (d) A **short window**: `not_after` is capped by G's policy and the clock check allows a stated skew; G never trusts R's clock beyond that cap. Over a transport with no round trip before the first request (none is planned: ssh and TLS both have one), a per-key monotonic counter replaces the nonce; not designed further. A nonce that the peer chose, or one carried inside a request, is refused.

**6. How it fits the zero-trust maxim and the existing local mechanism.**
- **On the wire.** The statement is accepted only on a transport `policy::check_peer` already passed (mutual TLS or ssh with a verified host key); a statement offered on a plaintext loopback listener, or on a stdio session of a local peer, is refused (a local peer has the process tree and needs no statement, and must not be able to substitute a forged one for the walk). The signature is authentication of data, not encryption: confidentiality is the transport's job, and the statement carries no message text and no raw session id.
- **No trust from location.** "Remote" is decided by the transport's evidence kind (`SshForcedKey`, `Certificate`, `Bearer`), as `#1115` already did for ssh (this machine's process tree says nothing about a remote peer). An address or a request field never decides it.
- **Per-request authentication (#161).** The harness standing is part of the principal the guard sees for each request, derived from verified evidence that has not expired, never cached past the window; credential expiry and rotation (#161) and attestation expiry are the same kind of fact and should share one recheck.
- **The existing mechanism stays the model.** Locally, `runs_claude_code` is true only for `PeerEvidence::Session` found by the walk (live `claude` process with a matching registry pid and start time), and the harness reaches the judge through `Session::with_harness` (CLI commands, #877; `serve --stdio`, #1115; `mcp` and `acp`, #1130; the daemon per connection, #1096). A verified statement produces **the same value** for `with_harness`, so the `join` judge, `room-require` and the audit are unchanged; only the source of the value is new. A typed name still decides nothing about the harness (#881: the member comes from the key, the harness from the statement, so a typed name no longer has to cost the harness on a remote peer; locally it still does). A key bundle still proves a member and not a harness (#880): option 1 or a statement is what adds the harness to a bundle's session. Codex stays the floor (#884): an attester can only attest what it verified, and Codex writes no registry record, so a remote Codex needs the local Codex verification built first; the statement's `harness` field and the per-key allowed list make it per-harness.
- **Show the difference.** The product marks where the standing came from (verified locally, attested by host LABEL, declared by credential), as `#990` marks an advisory sender, so a human reading a room can tell. The three are not the same strength.

**7. Rules a build must keep.**
1. The harness is never read from a request field, a hello field, an environment variable or a header.
2. A statement never names a member and never changes who the peer is.
3. An attestation grants harness standing only: no clearance, no label key, no floor action, no grant (#893 is unchanged).
4. Fail closed: any doubt (unknown version, key, harness, bad signature, expired, audience or channel mismatch, reused nonce, an unreadable policy) is the generic floor, with a kept refusal.
5. Verified on a transport that passed `check_peer` only.
6. Revocation reaches an open session (recheck) and every statement expires.
7. Only the human enrols or removes an attest key (a floor action).
8. A new operation or evidence kind adds its rows to `proto/AUTHZ-AUDIT.md` and a test fails if it reaches the store without the guard (#161).

**8. Tests a build starts from (red first).** A request field naming a harness is refused on every session; a forged statement (wrong key, flipped byte) leaves the floor and keeps a refusal; a replayed statement is refused (same nonce, other connection, other audience, after the window); a statement for a harness the key is not enrolled for is refused; `--off` ends the standing on an open session at the next look; a statement on plaintext loopback or on a local stdio session is refused; an attested peer still cannot open a sealed label or take a floor action; a typed name beside a statement changes nothing; a host that sends five bad statements is stopped by the breaker; two attest keys on two labels cannot be swapped.

**9. Recommendation and order.**
1. **First, before anything here:** #157 (an encrypted, mutually authenticated transport with a verified host key, `check_peer` enforced), #161 (per-request authentication, credential expiry, and the audit that no operation skips the guard), and #155 (key custody) for the attest key's storage. Without a channel the statement could be bound to, nothing in rule 5 holds. #1061 stays as the checklist and its refusal test (a non-loopback bind refused) until then.
2. **Then option 1** (credential declares the harness), the smallest increment: reuses the ssh label and the key-bundle row (#880), needs no signing, rechecked by the #1083 mechanism, and gives remote members a harness standing the human chose, shown as "declared by credential". If the human decides that does not satisfy the 2026-11-21 decision, skip to step 3.
3. **Then option 3** (the daemon on R signs after the kernel names the caller and the walk verifies it) as the real attestation, with the nonce, audience, channel binding and window above, rechecked and revoked like step 2. It reuses the verifier that exists (#1096), so no new local logic is built, only the signer, the handshake step and the enrolment.
4. **Option 2** only where R has no daemon and the human accepts same-user strength, labelled as such. **Options 4 and 5** are not built; option 5 is watched for.
5. Codex and other harnesses wait for their own local verification (#884, #64) and are then added as allowed ids, not as a new mechanism.

**10. Open questions for the human.**
1. Does option 1 (the human declares the harness of a credential, nothing verified per join) satisfy the 2026-11-21 decision, or must the standing come from a verified per-session signature (option 3) before any remote peer gets it?
2. Is same-user strength acceptable for a remote harness standing (a hostile process of the same account on R can forge it), given that it opens no clearance? Or must remote standing wait for a signer under a different OS user on R, or for vendor-signed evidence?
3. Should a room be able to say which standing it accepts (verified locally only, or also attested, or also declared by credential), or does `harness=claude-code` mean any of them? The first costs one more room setting and keeps the strongest rooms local-only.
4. When a key is revoked or a statement expires on an open session, should the session drop to the generic floor and stay open (this design), or end, as an unmapped ssh label does (#1083)?
5. Who may enrol the attest key: only the human at a terminal on G (this design), or may a remote enrolment be proposed from R and approved by the human on G, as a pairing step?
6. Is a daemon on every remote host acceptable (option 3), or must a remote agent work with only the `klatch` binary and an ssh key (options 1 and 2)?
7. Should the statement carry the process-tree digest at all, given G cannot check it and it grants nothing? It is kept here for audit only; it can be dropped to keep the statement small and the private facts of R's process table off the wire.
8. The attest key needs custody on R (#155): file only at first, or wait for the OS keystore and a hardware-backed key before any remote use?
9. Does the lifetime ceiling of a statement belong in G's policy table (this design) or fixed in code?
