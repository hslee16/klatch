The optional daemon: one shared gateway over a local Unix socket, `klatch-server daemon --socket PATH` (#102, step 2 of epic #13; no schema change; 2026-11-20).
**Question.** What is the smallest daemon that serves the session protocol of `klatch serve --stdio` to several local connections over one gateway, takes who each connection is from the operating system, and adds no network code to the `klatch` binary?

**What was built.**
- `klatch-server daemon --socket PATH [--max-connections N] [--first-frame-secs N]` (`proto/klatch-server/src/daemon.rs`, the only file allowed to name the Unix socket types and the peer-credential calls). It owns ONE `SharedGateway` (#140: one owner thread, the store opened by `klatch::member::spawn_shared_gateway`, which opens it as `klatch mcp --stdio` does: `KLATCH_HOME`, the keystore or `KLATCH_KEY_DIR`, the same guards and `for_members()`). It never prints the key, and it refuses to start, before it touches the socket, when the store cannot be opened. One thread per accepted connection runs the real session loop.
- To run the session loop over a gateway that another thread owns, the loop was made generic over a `session::Backend` trait (`now`, `change_token`, `head`, `ack`, `poll`, `handle`, `verify_credential`): `Gateway` implements it by calling itself (so `klatch serve --stdio`, `mcp` and `acp` are the same code with the same output), and `SharedGateway::session_backend()` implements it by sending each call to the owner. A subscription goes to the owner for the length of one poll, as in #140; any request bumps the handle's post count so a waiting session's change token moves. `Session::over` and `Session::without_hello` are the two additions to the session API.

**Who a connection is (the tiers).** The kernel reports the peer (`SO_PEERCRED` on Linux; `getpeereid` and `LOCAL_PEERPID` on macOS). A peer whose uid is not the daemon's own is closed before a byte is read or written (no refusal frame either: it learns nothing). The evidence is the existing `PeerEvidence::Process { pid, uid }` (item 53: same-host evidence, never proof; no new variant was needed). The pid is for the record and is never a name. Three cases, each tested:
1. No `identify`: the principal is what the empty evidence table gives a local process, `unmapped-process`, **Unattributed** (R23: its messages read `(unverified)`). All such connections share that name (the documented gap of item 53).
2. `identify` with `{"name": "alice"}`, the first request: the typed name, validated by the rules `KLATCH_NAME` has (1 to 40 characters, not reserved, never echoed back in an error). **Unattributed**, like the CLI today. A bad name is refused and the connection closes.
3. `identify` with `{"member": "w-1", "token": "..."}`: the credential token, checked by `Gateway::verify_credential` (the check `klatch serve --stdio` makes for a key bundle: token, expiry, revocation, a refusal recorded without the token). A live credential gives a **Verified** principal, and every later request is checked live again like any verified principal's. A bad token, another member's name with the token, a name given together with a token, or a token without a member each end the connection with an error: nothing falls back to a weaker name. The bundle file itself (which also holds the store key) is never sent; only the member and the token are.
The `hello` frame goes first, at once, with the case 1 principal, so a client that waits for it never waits for anything else. `identify` is recognised only as the first request; the daemon answers it with the member and attribution, then the session starts without a second `hello`. After any other first line, `identify` is an ordinary unknown method. This frame is the one thing the daemon adds to the protocol (PROTOCOL.md section 9); a session of `klatch serve --stdio` has no such method. Choosing `identify` over a preamble line before `hello` was settled by reading the Rust client, which waits for `hello` before it sends anything (a preamble the server waits for would deadlock it).

**The socket file.** The directory must exist, belong to the daemon's uid and not be writable by group or others (a named refusal: "not safe"); the path must fit `sun_path` (a refusal naming the limit in bytes: 103 on macOS, 107 on Linux; see #778); the file is created with mode 0600 (umask 0177 for the bind, then set again); a file that is not a socket is never removed; a socket nobody listens on (a connect probe is refused) is removed; a LIVE daemon (the probe connects) makes startup fail ("already listening"), the socket is never stolen; the file is removed on a clean exit, and only if it is still the file this daemon made (device and inode). A directory owned by another uid is refused by the same function; it is unit-tested, not tested with a real second user.

**Limits.** A frame is at most `MAX_LINE_BYTES` (1 MiB): the first line over it gets a `frame.too_large` refusal and the connection closes; a later one meets the session's own refusal and is skipped to its newline, never stored. A connection that sends no first frame within `--first-frame-secs` (default 10) is closed; one that has spoken is never closed for silence (a subscriber waits for pushes; a dead peer shows at the next heartbeat write). At most `--max-connections` (default 32) at once: the excess gets one refusal frame (`daemon.connections`) and is closed. Output goes through the session's bounded queue and stall limit (#147), so a consumer that stops reading is closed.

**Stopping.** SIGTERM and SIGINT stop accepting, close every open connection (its session ends), join every thread, drop the gateway (the owner thread closes the store), remove the socket and exit 0. Nothing runs after the process ends.

**Network-free.** The only listener is a Unix socket. The `klatch` binary gained nothing (its `no_telemetry` test is untouched). `klatch-server`'s scan test was changed deliberately: `UnixListener`, `UnixStream`, `getsockopt`, `getpeereid`, `SO_PEERCRED` and `LOCAL_PEERPID` are allowed in `src/daemon.rs` and nowhere else; the module has exactly one `UnixListener::bind` and one `UnixStream::connect` (the probe of its own path); TCP types stay forbidden in it; the uid check is asserted to come before the connection thread; outbound connects, name resolution, HTTP clients and `Command` stay forbidden everywhere.

**Tests** (`klatch-server/tests/daemon.rs`, the daemon as a child process against a temp store and a short socket directory under /tmp; `src/daemon.rs` unit tests; `gateway/shared_session_tests.rs`). Written first for the daemon (all 18 were red because the subcommand did not exist); the `Backend` refactor and its library tests were written code first, guarded by the existing session tests. Covered: two concurrent connections post through one gateway with dense sequence numbers 1 to 20 and a third reads them in order as a stream; each identity tier; mode 0600; SIGTERM and SIGINT remove the socket; unsafe directory modes, a missing directory and a regular file in the way; the too-long path; a stale socket and a live daemon; the frame cap (first line and later line); the connection cap and a freed slot; the first-frame timeout; garbage on one connection with another unaffected; a store that cannot be opened. **Conformance run:** one scripted scenario (join, three posts, a handoff post, history, subscribe from 0, ack, read, claim, an unknown method) for two members in turn, through the session loop in the test process (what `klatch serve --stdio` runs over a `Gateway`) and through the daemon: every frame after the identity, with times and message ids removed, is equal, and the sequence numbers are 1 to 4 then 5 to 8 in both. What that does not cover: the consumer libraries' own conformance suites (`clients/`, `proto/klatch/tests/client.rs`) cannot run over the socket until the client libraries can connect to it (#1095); a connection from another uid and a socket directory owned by another uid cannot be made here (unit tests with a fake credential); Linux `SO_PEERCRED` was written and compiled on macOS only.

**Not done.** The client libraries' socket connect (#1095, the Rust client was not a small change: it holds a child process). Sealed labels and the harness requirement per connection (#1096: the shared gateway loads no per-member label keys, and a connection joins as the generic floor). A bench scenario: the bench cannot drive a `klatch-server` child yet (#1078). No TCP, no TLS, no proxy identity: those are the later steps of epic #13 (#109, #110, #108).
