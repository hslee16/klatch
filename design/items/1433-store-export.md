The coordbench K arms' run store is exported as counts without the admin passphrase (#1433; no schema change; 2026-11-23).
The benchmark epic (#1362) needs the claim conflicts, asks and hook bytes of each K-arm run, and `klatch admin stats` (#1377) has them but is an admin read act: the human passphrase at a terminal, which a harness cannot give and a fresh run store does not have. A new subcommand of the bench tool, `klatch-bench store-stats --home DIR --key-dir DIR [--json] [--room R] [--since DAY] [--top N]`, prints the report `klatch admin stats` prints for the same store: it calls the same library function (`SqliteStore::read_usage_stats` over `StatsOptions`, which the admin act also calls, so the admin act is unchanged and the output cannot drift), counts only, with no message text, ask text, claim detail, label or payload.

    It does not weaken the admin gate, by where it lives and what it refuses. It is in the klatch-bench crate, which is never part of the shipped binary, so no klatch install has a way round the passphrase. It reads a run store a harness made in a temporary directory, so it refuses the default live store (`$HOME/.klatch`), anything under it and any directory that contains it (paths are resolved first, so a symbolic link does not get past), and it refuses a key directory that is not mode 700, the way a `KLATCH_KEY_DIR` is held. The key is read from that directory only, never from the keystore. The store is opened read-only (nothing created, no migration), a missing store is an error and not an empty report, and a wrong key is an error. A bench test seeds sentinel strings into messages, asks, refs, claim reasons and claim names and checks that none appears in the output for any combination of the room, day, top and format options, and another test checks that the JSON equals `klatch admin stats --json` for the same store (apart from the audit row that the admin act writes after it reports).

    The harness (`experiments/coordbench`) calls it after each K-arm run, writes the object into the run record as `artifacts.store_export`, and derives the metrics that were null: `claim_conflicts` (claims refused and later granted to the same member, the report's handled conflicts), claims granted, refused by rule, released and expired, asks created, answered and closed with the median time to the first answer, members who posted and never read, and hook bytes injected. The ask counts are cross-checked against the counts of the streams (`asks.py`: a `klatch ask` that printed `asked #N`, a `klatch answer` that printed `answered #N`); both are recorded and a mismatch is flagged in the notes. A B arm has no store and keeps null with a reason. A missing tool or an unreadable store keeps null and a note and never invalidates the run, and the harness tests with fake agents still pass with no klatch binary (the export is skipped with a note).
