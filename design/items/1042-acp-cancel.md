`klatch acp --stdio` reads its input on a helper thread so `session/cancel` ends a running prompt with `cancelled` (#1042; no schema or wire change; 2026-11-24).
What the ticket asks. #1042 was opened from #869 for two gaps. The first, `resource_link` blocks, was settled on 2026-11-21 (a link is read as its text form, design item 239, #1148). The second is cancel: `session/cancel` was read only after the current prompt was answered, because `serve` read stdin one line at a time. The decision of 2026-11-21 deferred the reader thread until a slow look exists or a real editor run (#1041) shows the need; the triage of 2026-11-24 asked for it to be built now, as the remaining gap. #1041 (a run against Zed or JetBrains) needs a human with an editor and is not part of this.

What the ACP spec requires (prompt-turn page, as checked in #869, design item 188). `session/cancel` is a notification with only a `sessionId` (no reply, not even an error). The agent should stop the work as soon as it can and MUST answer the pending `session/prompt` request with `stopReason` `cancelled` (not an error); it may send its last updates first. A client may send the cancel at any time, so the agent has to be reading its input while it works.

What the code did. A cancel between prompts was read as a line with no `id` and ignored: correct. A cancel during a prompt was not seen until the prompt ended, so it could never produce `cancelled`; looks are store reads and instant, so the gap was invisible. A cancel for a session that is not running anything has no effect, which is also the spec.

The smallest design. `session/acp_reader.rs` reads the input on a thread (`crate::sync::thread`, so Shuttle models it) and passes each non-empty line, in order, to the handler over a bounded channel (`mpsc::sync_channel`, 64 lines). It looks at each line only to (1) give every `session/prompt` request that names a session a cancel flag (an `AtomicBool`), passed on with the line, and (2) when a `session/cancel` notification (no `id`) arrives, raise the flag of every prompt of the named session that is still outstanding, and not pass the notification on (the handler never answered one). "Outstanding" is a prompt whose flag the handler still holds: the reader keeps its own copy and drops the entries whose count shows the handler let go, so the list is no longer than the queue. Everything else, a malformed line included, is passed on untouched, so the handler still produces the same parse error, error replies, notification handling and ordering as before. A cancel names a prompt by its place in the stream: a prompt that was read before the cancel (running, or read and waiting) is cancelled; one read after it is not; a cancel for a session with no outstanding prompt, an unknown session, or no `sessionId`, does nothing; a cancel that carries an `id` is a request, not the notification, and is answered `-32601` as before.

The handler (`AcpServer::serve`) waits for the next line with `sync::recv_within` and a one second tick, so even an idle wait is bounded and has a shape Shuttle can explore. `prompt` looks at the flag after the request is validated and before the look (a prompt that was read but not started when its cancel came makes no backend call), and again when the look returns (the answer is dropped). A cancelled prompt sends no `session/update` and responds `{"stopReason":"cancelled"}` with the request's id; its `session/update` and response order for every other prompt is unchanged. Validation errors (unknown session, bad params) are still errors.

Ending. End of input: the reader drops its end, the handler sees the channel close after the lines before it, finishes them, joins the reader and returns `Ok`. A read error (invalid UTF-8 is the reachable one): the reader passes it on as the last item and ends; the handler answers every line before it, then returns that error, as `lines()` did. An output failure: the handler drops its end and returns the error without joining, because the reader may be blocked in a read of a pipe that nothing can interrupt; it ends when its input does or at its next send, like the reader of `serve_guarded` with no closer, and the process exits right after in `klatch acp`. A reader that panicked is reported as an error, not lost. Queue full: the reader waits in `send` and stops reading until the handler takes a line; a client that sends 65 requests behind a running prompt waits too, and its cancel is read when room is made. An ACP client keeps one prompt per session outstanding, so a full queue is a client off the protocol, and the bound keeps memory fixed. One line is still read whole with no cap on its length, as before (a limit on line length is not part of this).

Limit, said plainly. The cancel is seen at once, but a look that is already inside the backend is not interrupted: the handler checks the flag when the look returns. For the in-process gateway a look is a bounded store read, so that is a store timeout at worst. The prompt path has no other wait. A backend whose look can block for long (a remote one; none is used by `acp` today) needs a cancel hook of its own on the `Backend` trait; that is not built and is ticketed rather than guessed at.

Tests. `src/session/acp_cancel_tests.rs` plays the client over channels against a backend whose looks wait for the test, so every order is made by the test and every wait has a limit (a broken build fails an assertion in at most 5 seconds). It was written first and run red: the cancel mid-look, another-session, request-id cancel, queued-prompt, cancelled-then-next, malformed-line and read-error tests failed (the harness waits for the reader to read the cancel while the look runs, which the sequential reader could not do). Green already, pinning today's behaviour: a cancel with no prompt running, two prompts in sequence and in order, end of input mid-prompt, and the input released on every way out (the last was not red first). Shuttle (`shuttle_tests.rs`): in every schedule the cancelled session's flag is up before the channel reports closed, other sessions' and later prompts' flags are not, the order is kept and no cancel is passed on; the reader ends quietly when the handler stops listening. Two plants were added to `scripts/shuttle mutations`. Mutations of the unit tests, each caught by assertion: the flag never raised, a cancel matching any session, a cancel with an `id` treated as a notification, no flag check after the look, no flag check before the look, a read error not passed on, a read error turned into a clean end. One mutant survived and is equivalent: passing the cancel notification on to the handler (it answers a notification with nothing). Not mutation-checked: the join on end of input (a missing join leaks a thread and no assertion sees it) and the idle tick (a hang, not an assertion).
