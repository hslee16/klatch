One list of the wire methods, checked against the server, PROTOCOL.md and the three clients (#1069; no wire change; 2026-11-24).
What the ticket asks. #1069 (part of #1064) reads: "Generate the three client wrappers and the PROTOCOL.md method table from one machine-readable method list (for example a single JSON spec file) so adding a method is one edit plus generated output, checked by tests/client_methods.rs. Large; design first." The problem it names: one wire addition touched `client.rs`, `klatch.ts`, the Python client, `PROTOCOL.md` and `transport.rs` together. Before this item the only machine check was `tests/client_methods.rs`, which read the method names out of the PROTOCOL.md tables and looked for a wrapper of that name in each client: it saw no params, and it saw only what the prose table listed, so a wire method missing from PROTOCOL.md was missing from the check too.

    The list. `proto/wire/methods.json` (schema 1) holds one entry per method the session loop accepts, sorted by name: `name`; `mode` (`read` changes nothing; `act` changes state, and moving a read cursor or opening a stream counts); `room_arg` (the param that names the room, or the member for `dm`, or null when the method is not about one room); `params` (each `name`, `type` of `string`, `integer`, `boolean` or `array`, and `required`); `result` (a short shape); an optional `role` (`reviewer` or `admin`, the three role-gated methods) and `open_params` (`role_act`: the wrappers pass any further param of the act through); and `wrappers`, the wrapper each client names for it (`set_status`, `setStatus`, `set_status`). A client that differs on purpose says so in `clients.<client>.aliases` (the name a client shows a param under, for example Python `item_id` for `id`, the Rust `handoff` that carries `kind` and `payload`) and `clients.<client>.gaps` (a param the client cannot send yet). `identify` is a connection handshake of the daemon and the Rust, Python and TypeScript connect functions, not a method of the session loop, so it is not in the list.

    What is checked, each by a test that fails by assertion. `tests/wire_methods.rs` reads the dispatch arms and the params structs of `src/session/methods.rs`, `role_methods.rs` and `mod.rs` as text and requires the same methods and, per method, the same param names, the same `required` (no `serde(default)` and not an `Option`) and the same type; a new arm, a new struct field, a changed default or a method only the list has fails. A method with no `|p: Type|` closure in its arm must be added to the test's `IRREGULAR` table (the test says so), and a serde `rename`, `alias` or `flatten` in a params struct panics so that a wire name cannot differ from a field name unseen. The same file requires every listed method and param to appear in the PROTOCOL.md section 5 row (the method name and each param in backticks) and every row to be listed. `tests/client_params.rs` finds each client's wrapper and requires that it calls the method by its wire name, exposes every listed param (camel-cased in TypeScript), sends it under its wire key, and exposes no param the list does not have; a recorded gap that has been closed fails, so a gap cannot outlive its fix. Negative tests hand each check a source that drifted (a method missing, an extra or renamed param, a method sent under another name). `tests/client_methods.rs` stays as it was: the PROTOCOL.md tables name a wrapper in each client.

    Generate or check? The ticket says generate. This item implements the check and leaves generation as the owner's decision, because it changes how the clients are maintained. Option A, check only (built): the clients and PROTOCOL.md stay hand-written, with their docstrings, typed results (`Vec<Member>`, `Message`) and request builders; adding a method is one list entry plus the hand-written wrappers, and the checks name every place that was forgotten. Cost: three wrappers and a table row are still written by hand. Option B, generate: a script writes the wrappers (and the PROTOCOL.md rows) from the list, with a `--check` mode in the gate so a committed file cannot drift. It removes the hand edit but the list would then carry what the wrappers now carry by hand: result decoding (the Rust client returns typed records, `claim_owners` and `claims` differ), per-client call shapes (a Rust `PostRequest` builder, TypeScript option bags, Python keywords), docstrings, and the prose of the PROTOCOL.md rows, which are paragraphs of rules (the `post` row is about 40 lines). Every change to those would be a change to the list and to a template, and the generated files would sit in every wire pull request as review noise. A middle path is to generate only the plain methods (a room and strings in, the result passed through) and keep the shaped ones by hand, which needs a second list of which are which. The recommendation is A, and B only for the plain wrappers of one client if the owner wants it; the list is the same either way, so nothing built here is thrown away.

    Drift found when the checks first ran on the real repository, all fixed here without a wire change: the wire methods `label_order` and `scrub_check` (decision on #740) had no row in PROTOCOL.md and no wrapper in any of the three clients (the old check missed them because it read its method names from PROTOCOL.md); they have both now. Left as recorded gaps in the list with ticket #1565: no client wrapper of `read` takes `max_messages` and `max_bytes` (#1390), and the Rust `ClaimRequest` has no `shared`; both need a decision on the return shape or the public struct.
