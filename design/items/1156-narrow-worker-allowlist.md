The worker allowlist no longer covers a push to main or any gh api call (#1156; no schema change; 2026-11-21)
The default allowlist of `proto/scripts/team` (#594) matched `git push -u origin` and `gh api` by prefix, so `git push -u origin main` and any mutating `gh api` call were inside it. Decision of the human (2026-11-21): narrow it. Branch protection on main is applied on GitHub separately and is a second guard, not this change.

What a Bash rule can express (Claude Code permissions docs, checked 2026-11-21): `*` stands for any text, spaces included, anywhere in the rule; a rule with no `*` is an exact command; the rule has no notion of flag order, so a trailing wildcard cannot say "no `-X`" or "no `-f`". A pattern such as `git push -u origin alee/*` also matches `git push -u origin alee/x:main` and `alee/x main`. So GET-only `gh api` cannot be expressed with a wildcard, and a branch pattern is only safe as an exact string.

The default allowlist is now built per worker: `Bash(git push -u origin alee/NAME)` (exact, the worker's own branch only), and for a worker with a ticket the exact `gh api repos/hslee16/klatch/issues/N` and `.../issues/N/comments` (a plain `gh api` is a GET). The broad `gh api` and `git push -u origin` rules are gone; `gh pr create`, `gh pr view` and `gh pr checks` are allowed with arguments (they cannot merge or edit). A worker can no longer file tickets with `gh api`; the brief tells it to post a `friction:` line in the room and the human files it. `TEAM_ALLOWED_TOOLS` still replaces the whole list. The tests assert that no `gh api` wildcard, no wildcard push, no `origin main` form and no other worker's branch appears in the list.
