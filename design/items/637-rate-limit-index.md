The per-member rate limit reads an index, not the whole table (#637; store schema 33; 2026-11-19).
The rate limit (#187) counts a member's posts in the window with `SELECT ts FROM messages WHERE sender=? AND ts>=? ORDER BY ts`. The table had only `(room, seq)` and `(mid)` indexes, so the plan was `SCAN messages; USE TEMP B-TREE FOR ORDER BY`: a full scan per post once a human sets a limit. Schema 33 adds `messages_sender_ts` on `(sender, ts)`; the plan is now `SEARCH messages USING COVERING INDEX messages_sender_ts (sender=? AND ts>?)`, with no sort, because the index is already in ts order. A test asserts the plan with `EXPLAIN QUERY PLAN` on the real query (`POSTS_SINCE_SQL`), so a change to the query or the index that brings the scan back fails it.
The migration (`migrate_v32`) is `CREATE INDEX IF NOT EXISTS`, so it is safe to run again; it changes no rows. It has its own test, and the migration property test (#603) covers it through the chain and the fresh-schema comparison. The index adds one small b-tree write per post even when no limit is set. The other half of the ticket, a per-member or per-role limit instead of one limit for all, is a design change and is not part of this item.
