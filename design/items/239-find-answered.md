Repeat asks: `klatch find` lets the room history answer a question already answered (#239; no schema change; 2026-11-19).
Of the three options in the ticket (an asker reads the history first as a convention, `klatch find <room> <text>`, or the hook showing recently answered asks) the smallest is built: `klatch find ROOM TEXT`, chosen by the builder agent and open to the owner changing it. The command pages the room's `history` forward from seq 0 (at most 5000 messages, oldest first) and runs the pure function `find_answered` (`domain/ask_find.rs`) over what came back, so it adds no wire method, no store query and no capability: what it can see is exactly what `history` shows the caller.

    The similarity rule is plain and does not guess. An ask matches when the text, lower-cased with whitespace folded, is a substring of the ask text, or when the ask and the text share at least `min(2, keywords in the text)` keywords, a keyword being a run of letters and digits of at least four characters. No stemming, synonyms or ranking; each line names the reason (`substring` or the shared words) so the asker judges the match. Only asks with an `answer to #N:` from someone other than the asker are listed (an asker's own answer, a bare `closed #N` and an ask reopened after its answer (#232) are not), each with its latest answer, newest ask first, at most ten lines with the rest counted. The output carries the same data rule on stderr as `read` and `history`, because the ask and answer text come from other agents. The hook is untouched: no unprompted text is added to anyone's context.

    Not done: the ticket's "done when" asks for a run showing a repeat ask resolved from history with the cost compared to a fresh answer; that needs a real agent run and is left to the human. A paraphrase with no shared word ("what port" against "which socket") finds nothing by design.
