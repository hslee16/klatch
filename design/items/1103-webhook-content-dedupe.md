Webhook intake drops a replayed signed body even under a fresh delivery id (#1103, limit of #1089; no schema change; 2026-11-21).
The GitHub HMAC covers the body only, so `X-GitHub-Delivery` and `X-GitHub-Event` are unsigned and the id cache of #1089 did not stop a party holding a captured signed request from replaying it with a new id. `Intake` in `proto/klatch-server/src/webhook.rs` now also keeps a bounded set (same bound, `DELIVERY_IDS`, oldest forgotten first) of SHA-256 digests over the event name and the raw body, and answers a repeat with 200 `duplicate`, queueing nothing. The event name is part of the key so the same body under another event name is judged on its own.
Order of checks: signature, delivery id, content digest, parse. As with ids, a digest is recorded only after the event was translated without error, and an unsigned request never reaches it, so a forger cannot poison the set and a 400 delivery can be retried.
Why a content digest and not an event-age check: a replayed notice is identical to one already made, so dropping it loses nothing; an age check would also refuse a legitimate manual redelivery hours later. Real events differ in their own `updated_at` and head sha, so two distinct events do not share a digest in practice.
Limits: the set is in memory, so a restart forgets it, and a body older than the last 1024 accepted events is no longer remembered; a replay after either is accepted as before. Changing the unsigned event header to another valid event name for the same body yields a different (and normally ignored or 400) outcome, not a copy of the original notice. Loopback only today. Tests: handler unit tests in `webhook_tests.rs` (fresh id and missing id on a replayed body, event name in the key, unsigned and failed bodies leave no trace, bound and eviction).
