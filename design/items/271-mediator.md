The rules-only mediator proposes for what rules cannot settle, from structured stuck-case events (#271, DESIGN 24, 25.12, 25.15; wire method `stuck`, commands `klatch stuck` and `klatch mediator`; no schema change; 2026-11-18). Steps 1 to 3 of the order of work in #271 are built; step 4 (a model) is not, and #190 (the facilitator) and Jev (#898) are separate jobs.

**The events (step 1).** `klatch stuck [room]` and the wire method `stuck` (`{ room }`, result `{ events: [...] }`) list the stuck cases of a room as structured events, derived on every call and stored nowhere: `stale_ask` (`ask`, `asker`, `age_secs`; an unclaimed ask older than the room's stale window or its stated deadline, not waiting on its asker, with no active working room; #225), `nobody_capable` (`ask`, `asker`, `cannot`; enough helpers declined as `cannot`, none busy, failed or partial; #230), `ask_cycle` (`members` from the member that yields, `asks`; #273, 25.15) and `claim_deadlock` (`members`, sorted; a standing cycle of claim waits, the 25.12 deadlock as a fact that can be read and not only as the refusal flag or the once-told hook line). Each carries a stable `key`. The read is guarded exactly like `open_asks` (`Operation::read`, so a room above the caller's clearance is refused with `clearance`), changes no cursor, presence, message or claim, and an event holds ids, member names and numbers, never message text.

**The member (step 3).** `klatch mediator [--room lobby] [--once] [--interval N]` runs deterministic passes as the caller's own member. `domain::plan_proposals` is a pure function of `StuckEvent` values and presence; the event has no text field, so no wording of an ask can steer it (decision 8). It posts a fixed template per case, once per key per run: for an ask cycle that by a fixed rule the first name yields (post what it has for the ask it holds, release it, wait), with a room `mediate-<lowest ask number>` created and each present cycle member invited; for a claim deadlock that klatch's own rule (the member whose attempt closed the cycle yields) stands, and otherwise the first name releases and retries; for a stale ask that the asker could narrow or repeat it or a member could claim it; for a nobody-capable ask that the asker could tell its user or a human could add a member that can. At most five proposals a pass; a case about the mediator itself, or with a name that is not a valid member name, is skipped.

**Contract and clearance.** It only proposes. It calls `join`, `stuck`, `who`, `post` and `invite` through the guarded gateway as itself, and nothing else: no release, cancel, grant, clearance, label or admin act. Creating a room and inviting are the capability of #188 (`klatch admin grant-rooms`), audited under its name, and an invite below the room's label is refused (`clearance`), so it never acts above a member's clearance. A refusal is reported once per run and not retried. Cost limits: no model, no network, one read of the lobby per pass. A restarted run may post a proposal again for a case that still stands (the key set is per run); a case that stops standing stops being proposed.

**Collected stuck cases (step 2).** `fixtures/stuck-cases.json` records the cases as CLI step lists with the events and proposals expected: the ask cycle (#273), the claim deadlock (25.12), the overwrite after a deadlock (#272) and two tasks that need the same result. The overwrite case became detectable in #909 (option C, `possible_overwrite`; see the design item for #909). The last case is marked `detectable: false`: duplicate asks in different words are compared by neither number nor path. It is the case the rules cannot settle, which a model-backed mediator (step 4) would take, still as a member that only proposes, with its output as data like any message.
