The release workflow checks tags through the one mapping, and the tap formula is compared with the staged copy (#1260; no schema change; 2026-11-21).
Every tag check in `.github/workflows/build-release.yml` now goes through `release/pep440.sh` (`tag_matches`), so a tag in either spelling of a release (v0.2.0a1 or v0.2.0-alpha.1) passes all four jobs and any other tag fails them. Before, the two Python steps compared the tag with the PyPI version by plain equality. The wheel job also refuses a Python version that is not the same release as the crate (the wheels are named by the PyPI version, the archives by the crate version), which nothing checked. `release/test-tag-checks.sh` reads the real steps out of the workflow file and runs them against fixture version files for every kind of release, so what is tested is what CI runs.

The staged formula (`release/homebrew/klatch.rb`) and the tap's formula can no longer drift unseen. `release/compare-formula.sh` fails with a diff on any difference beyond the version, the URLs and the hashes. `release/bump-formula.sh` runs it against the tap checkout before it rewrites anything (so a drifted tap or staged copy stops the bump), and writes the bumped formula back to the staged copy, which is then committed with the release. `release/verify-published.sh` reads the tap formula over REST (`gh api`) and runs the same comparison as its `tap-drift` check. The dry-run workflow itself was not run from this session; the tag steps were run through their real script bodies instead.
