A label key can be rotated, sealing a label converts what is already in it, and claim text stays plain (#378, closes the gaps in item 12; no schema change; 2026-11-21).
Three gaps of item 12 were one mechanism: protect stored text under a key, atomically, with the store lock held. The sealed value already binds `klatch message <id> under <label> field <field>`, and every move below keeps that binding, so a text moved to another message or label still fails to open. **Decided by the human on 2026-11-21.**

**Rotating a label key.** `klatch admin rotate-label-key <label>` (terminal gate, the label typed back, audited as `rotate-label-key`, the lowest and any unsealed or unknown label refused) is modelled on `rotate-key`. Under the exclusive directory lock: (1) every sealed body and payload of the label, in the store and in every archive file, is checked to open with the current key or the new one, and one that opens with neither (or an archive file that does not open with the store key) refuses the rotation with nothing changed; (2) the new key is stored under `<label key name>-next`, so a crash leaves both keys; (3) each archive file is rewritten through a temp copy that is opened and checked before it replaces the original, so every file is whole under one of the two keys at every moment; (4) the store is rewritten in one transaction (reveal with the old key, protect with the new, same id, label and field); (5) the new key takes the main name and `-next` is deleted. A text that already opens with the new key is skipped, so a repeated run finishes a crashed one. The label twin of `open_keyed`'s repair runs where the label ring is loaded (`label_ring`): if the main key opens no sealed text of the label and the `-next` key opens all of them, `-next` is promoted; a `-next` equal to the main key is removed; a `-next` that opens only some texts is left alone. The command prints the new recovery code and says to relaunch workers that hold the label (a key bundle written at spawn holds the old key, and klatch keeps no list of outstanding bundles, so it neither checks nor refuses while workers are live). Backups and archive copies made earlier keep the old key's text; the command says so. **Proof:** `store/sqlite/tests/label_keys.rs`, `member/custody/label_rotation_tests.rs` (a crash injected after each step and inside the transaction, the old key opens nothing afterwards, a moved body still fails, an unopenable row or archive row refuses with nothing changed, an unsealed label is refused), `admin/command_tests.rs`.

**Sealing a label converts earlier messages.** `klatch admin seal-label <label>` now makes the label's key first, then marks the label sealed and protects every earlier plain body and payload of the label in one transaction (`PolicyStore::mark_label_sealed_converting`); with something to convert and no key the whole step is refused and nothing is marked. Archived tombstones are left alone. `--keep-plain` marks the label only (the old behaviour, `admin_seal_label_keep_plain`), and a later `seal-label` without it converts what was kept. The audit outcome says how many texts were converted. Archive files made before the label was sealed still hold those messages as plain text, and restoring one puts them back plain; that is #1153.

**Claim text stays plain.** Claim reasons, release notes and member statuses are not sealed: they have no label of their own, they are read on every board, `who`, `wait` and hook digest path, and sealing a status would add a key read to the hottest path. SECURITY.md says claim text must not carry secrets. A per-claim label (`claim --label L`, sealing only the reason and the note, never the path, owner or expiry) stays the design if the need returns.
