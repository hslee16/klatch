Issued credentials renew on use and have a hard cap (#161, epic #152; schema 31; 2026-11-19).
**Decision (the human, 2026-11-18).** An issued credential renews automatically on use, with no human step. The idle timeout is the credential's `ttl` (`klatch worker issue --ttl`, default 3600 seconds): each successful request pushes the expiry out to now plus the timeout. A hard cap from issue (`--max-life`, default 24 hours, at most 30 days, the existing `MAX_CREDENTIAL_TTL_SECS` ceiling) is never passed by renewal. Revoke still stops the credential at its next request, and each renewal is audited. **Tradeoff accepted:** a stolen credential that its thief keeps using lives until the cap or a revoke; a dormant one dies at the idle timeout.

    **Where.** `check_credential_live`, the first step of `check_guard`, already looks at the credential on every request of a `Verified` principal (item for #161, the authorization audit). When it finds the credential live it calls `renew_credential_on_use`, which reads the record and asks the store to renew: `CredentialStore::renew_credential(member, now, step)` moves `expires` to `min(now + idle, cap)` in one write transaction and returns the new expiry, or `None`. It renews nothing for a credential that is revoked, expired, unknown, or from before schema 31 (`cap` 0), and a refused request never renews, so an expired credential is not brought back by trying. A first expiry is the idle timeout or the cap, whichever is nearer.

    **Write and audit rate.** Renewing on every request would write and audit once per request. A renewal is written only when it gains at least `step` seconds, a tenth of the idle timeout clamped to 1 to 60 seconds, or when it reaches the cap. A burst of requests is therefore one write and one `renew-credential` audit row (`expires=N cap=M`, never the token); the expiry is at most `step` seconds shorter than "a full idle timeout from the last request". This is the one deviation from "each successful request pushes the expiry out", chosen so a busy worker does not fill the audit log; the idle timeout and the cap are exact.

    **Schema 31.** `credentials` gains `idle` and `cap` (both 0 by default). An existing credential keeps its own expiry and is never renewed, which is the behaviour it was issued under; reissue gives it the new rules. `NewCredential.max_life` 0 means no renewal (the store-level default); the gateway always passes the cap (24 hours when the launcher gives none).

    **Rotation.** Unchanged and explicit: revoke, then issue again (a reissue starts a new cap). There is no rotation in place and no refresh of the token itself; the token stays the same for the credential's life.

    **Not done.** The own-record methods skip `check_guard` and so neither check nor renew a credential (#835); `klatch worker list` still shows the current expiry, not the cap. **Tests (the renewal tests failed on assertions before the code):** `gateway/gateway/tests/credential_renewal.rs` (renewal by use, idle death, the cap second, the 24 hour default cap, revoke, audit once per burst, untouched principals, cap range, rotation), `store/sqlite/tests/credentials.rs` (first expiry, renewal and cap, the step, never renewed when revoked, expired, unknown or legacy), the schema 30 to 31 migration test, and `tests/worker.rs` (a real process kept alive past its idle timeout and stopped at its cap; `--max-life` limits).
