Sealing a label seals its archive files, and a restore never puts plain text under a sealed label (#1153; no schema change; 2026-11-21).
`klatch admin seal-label` (without `--keep-plain`) already sealed the plain bodies and payloads of the label in the live store (#378); it now does the same in every archive file, through `wrap_archives` in `store/sqlite/archive_keys.rs`. Each file is rewritten as `rotate-label-key` rewrites it: a temp copy beside it is changed in one transaction, opened and checked with the store key, and only then renamed over the original, so a file is whole at every moment and a text that is already sealed is skipped, which lets a repeated run finish a crashed one. The step runs after the store is sealed, under the store directory lock (`custody::wrap_label_archives`), and prints how many files it changed. `--keep-plain` leaves the archive files as they are, as it leaves the live rows.

    The other half is the way back. `restore_archive` used to copy the archived text into the row unchanged, so an archive made before a label was sealed put plain text under it again. It now reads the rows to restore, and for a label that is sealed it protects each plain body and payload under the label key, bound to the message, label and field as every sealed text is. When the key is not held it refuses with nothing restored (rule `label-key`), the same refusal a post to a sealed label gets. Already sealed archived text is written back as it was. The change closes the limit note that #378 added to SECURITY.md. A backup or an archive copied elsewhere before the label was sealed still holds the plain text, as it does for a rotated key.
