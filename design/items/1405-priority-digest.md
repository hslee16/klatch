Priority-ordered read, wait and digest within the output cap (#1405, epic #1400; schema 41; 2026-11-23).
After the output cap (#1390) a busy room showed its oldest unread messages and left the rest unread, so an ask addressed to the reader that arrived after 300 messages of chatter was the 301st message and took eight capped reads, or sixteen capped waits, to reach. The metric is the position of an addressed ask in the first capped page: on the fixture of the tests (300 messages of 400 bytes, then an ask to the reader, chatter, an open ask it could answer, a message to it, chatter) it was 301 (not on the first page of 39 messages) and is now 1. The change is only to which messages a capped view shows first; the cap, the count of what was left, the continue command and the rule that nothing is marked read that was not shown are unchanged.

    The classes come from structured facts only, never from words in a message (message text is data) and not from a new heuristic: who the message is addressed to (the same mention, broadcast and direct-message rules as the digest, #185, #674), the kind of room, the ask records (an ask is a body that starts `seeking:`, the existing convention; whether an open ask is one the reader could answer is the answer of `could_answer`, #671, #1171, so a claimed ask, the reader's own and one in another scope are not), and the role of the sender. In order: (1) an ask addressed to the reader, an open ask it could answer, and an answer or close that points at one of its own asks; (2) any message of a direct message room it is in; (3) claim events that touch files the reader holds or waits on; (4) any other message addressed to it, and a post by the admin agent or the integrator; (5) the rest. Inside a class messages keep their seq order, oldest first, so a room with only chatter reads exactly as before. Class 3 is empty for read and wait: claims are not messages in the room's log, and the hook digest already prints claim changes before every message and never drops them for the byte budget (#1419), which is what that class means there. Class 4 uses the roles that can post to a room; klatch has no other notion of a coordinator (the facilitator may not post to a room), so a session that coordinates by convention is ranked like any member; that is the honest limit of "structured fields only".

    Where the order applies. `klatch read` and `klatch wait` (the first call and every later one), the wire `read` with `max_messages` or `max_bytes` (which is what the MCP tools `klatch_read` and `klatch_wait` send), and the hook digest. `history` stays strictly chronological, and the wire `read` without limits is unchanged. In the hook the byte budget policy of #1419 is untouched: the digest keeps the messages by class, newest first inside a class, and prints the kept ones in seq order as before; the never-dropped set is still the addressed messages (a message ranked as an ask only because the reader could answer it is ranked first but, at the count-only level, counted like any message that is not addressed); rooms with news print the room holding the most important message first, after the rooms with items of the member's own. When several rooms are named, `klatch wait` shows the room with the most important message first (the first named on a tie) and leaves the others untouched for the next call, so a direct message is not kept behind a busier room named before it; an ask for the reader in one room outranks a direct message in another. The MCP wait ranks inside each room and keeps the rooms in the order named (it consumes every room it reads, so it cannot pick one beforehand).

    The cursor. Showing a page by importance means the shown messages are no longer a prefix of the unread ones, and a single read cursor cannot say what was shown. The invariant of #1396 stays: nothing is marked read that was not shown, nothing shown is shown twice, and nothing is lost. A new table `read_shown(room, member, channel, seq)` (migration `migrate_v40`, schema 41; seqs only, never text) holds the seqs shown beyond the cursor, per member, room and channel (`read` for the read cursor, `wait` for the wait position of a peeking or filtered wait). The cursor (`last_seq`, or `wait_seq`) moves over the longest run of messages from others that were all shown, starting at its value, and a remembered seq is deleted as soon as the cursor passes it. Reads, waits and the hook skip the remembered seqs, so the unread count falls by exactly what was shown (`read --count`), a full unbounded `read` takes the rest once and clears the record, and an acknowledgement past them clears it. Own messages and archived rows are not messages to show and never stop the cursor; a canary is never shown and counts as shown once a later message was. A peeking or filtered wait marks seen everything it looked at except the matches it did not show, so the next wait shows the rest. The store call is `mark_shown(at, channel, seqs)`, the gateway call `mark_shown`, with `read_ranked` and `rank` for the order; the default of a store that cannot remember seqs is the prefix case, refusing a set with a gap. A peek still moves nothing and its continue command is `klatch history ROOM --since SEQ`, since the oldest unread message when the page is not a prefix. The default behaviour of a room without any addressed item is the old one in every observable way, and the tests that proved it (`output_cap`) did not change.

    Wire and docs. The wire `read` result gains the optional `by_importance: true` only when the page is out of seq order (additive; a client that reads rows in order should treat such a page as data about what to read first), and the MCP wait result carries the same key. A page that is out of order prints one fixed line first, `[shown by importance, not in sequence: ...; the seq of each row is exact]`. `PROTOCOL.md`, `INTEGRATION.md`, the changelog fragment and `VERSIONING.md` (schema 41) carry it. Tests (`tests/priority_digest.rs`, `tests/mcp.rs`, the store, gateway and hook unit tests) cover a large mixed room: the addressed ask first, three successive reads and waits showing every message once and losing none, a peeking and a filtered wait, the continue command, a hook and a read not repeating each other, MCP parity, and a seeded random walk of the store call. One existing test of #1396 that pinned "addressed messages are not promoted" now pins the opposite, and one of `wait_filters` no longer relies on room order. Not done: claim events as messages (class 3 for read and wait), a cross-room order for the MCP wait, and measuring time to first answer in S4 (#1369) and DM adoption (#1376), which need the benchmark's multi-agent runs; the offline measure is the fixture rank above.
