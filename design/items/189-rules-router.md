The reference rules-based router is an ordinary member (#189, DESIGN 24.1 decision 7, #271; no schema or wire change; 2026-11-18). `klatch router [--room lobby] [--rule prefix=member]... [--once]` runs deterministic passes as the caller's own member. A pass reads the lobby's open asks, live claims and presence through the same guard-checked calls every member has (`join`, `open_asks`, `claims`, `who`), plans with `domain::plan_routes` (a pure function), creates the topic room by joining it and invites with `invite`. No model, no state beyond a set of invites it already made in this run.

**The rule.** The topic of an ask is its asker's first live claim by path order, other than the bookkeeping claims `ask:` and `pr:`. The room is `topic-<slug of the topic>` (so asks on one topic share a room). The members invited are present members (seen within the board window, not `done`, not parked) with a live claim that overlaps the topic by path component, or that an operator `--rule prefix=member` names, at most three, in name order; never the asker, the router, or a member that declined that ask as `cannot`. An ask a helper holds, an ask of the router itself, an ask whose asker holds no topic claim, and a topic that makes no room name are left alone: nothing is guessed from words.

**Zero trust.** (1) It reads structure only: `AskFacts` carries an ask's number, sender, whether it is held and who declined it as `cannot`, and has no text field, so no wording of an ask can steer it (decision 8: messages are data). A claim path is the only text compared, as everywhere else. (2) It holds no capability a normal member lacks beyond create and invite, the guard-checked and audited capability of #188: under `room-creation granted` a router without `grant-rooms` is refused both and creates nothing; with it, the audit names the router for `create-room` and `invite`. It has no admin act, sets no label and no clearance, and posts only the content-free invite pointer. (3) Clearance: it cannot read clearances, so the gateway now refuses `invite` of a member below the room's label (rule `clearance`, recorded as a refusal, nothing posted). That check is for every inviter, not only the router. (4) A refused act is reported and not retried in the same run, so a refused router does not fill the refusal record or trip the breaker.

**Limits, honestly.** Claims of two members in one scope cannot overlap (the claim itself refuses), so the evidence "holds a claim on the topic" arises between members with different scopes (repositories), with shared claims, or from an operator rule. It does not use the repository attribute of #181 (not on main when this was written); a router that invites by repository is a follow-up. It routes by claims, not by what an ask asks for, so an ask whose asker holds no claim is not routed (a model reading text is the later, propose-only mediator of #271). The set of invites made lives in memory: a restarted router invites again a member that is not yet in the room. It watches one room.
