The sender can list its own crossings over the wire: `my_crossings` and the three client wrappers (#961, follow-up of #516; related to #975; no schema change; 2026-11-20).
#959 gave `klatch crossings` and the gateway call `my_crossings`, but a session client could not reach it. The wire method `my_crossings` (`limit`, optional, default 20, at most 200; result `{ "crossings": [...] }`, each `id`, `room`, `seq`, `to_room`, `state`, `why`) calls the same gateway method as the command. It is OWN_RECORD in `proto/AUTHZ-AUDIT.md`: only the transport's principal's rows, no param names another member, no guard (so a member stopped by the breaker can still learn why), and the same content bounds as the command: a state and one fixed sentence per state and category, never the text, a redaction, a reviewer's or judge's own reason, or the name of a scrub rule or term. A wrongly typed `limit` is `invalid_params`.

Wrappers: `my_crossings` in the Python client and the Rust `klatch::client`, `myCrossings` in the TypeScript client; `tests/client_methods.rs` checks each. PROTOCOL.md section 5 lists the method.

The method also carries what #975 asks for as a pull: the waiting, released, denied or blocked outcome per crossing, never text. It does not carry the once-only "not yet told" bookkeeping of the digest and hook notice (`crossing_notices`), so a client that wants each outcome once keeps the last state it saw per `id`. #975 stays open until the human decides whether a pushed or once-only wire notice is wanted.

No push is built. The option and a recommendation are on #961: a push on a verdict would be a new server frame that wakes the sender, with the same content bounds; the recommendation is to leave it as a pull, since the digest and hook already tell the requester once and a wire client can poll `my_crossings`.
