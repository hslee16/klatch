Revocation of client certificates by a CRL file on the mutual TLS listener (#1491, refs #108, #157; no schema change; 2026-11-25).
`klatch-server https ... --tls-client-ca PEM [--tls-client-crl PEM]`: the optional file holds one or more X.509 CRLs, signed by the CA of the client CA file, read once at start. It is handed to the same rustls `WebPkiClientVerifier` that `tls.rs` already builds (`with_crls`), so there is one verifier and one listener and the CRL covers every route behind the handshake: HTTP, the event stream, MCP and the WebSocket route. The `klatch` binary is untouched and links no TLS; no new dependency, feature flag or unsafe code.

    What a revoked client sees. A certificate whose serial the CRL of its issuer lists fails the handshake: the client gets a fatal TLS alert (certificate revoked; with TLS 1.3 the client may finish its own side first and learn of it on its first read) and no byte of HTTP. No session exists and no connection slot is held beyond the handshake deadline. The server logs `client certificate refused: revoked (listed by the client CRL)`, at most one such line every ten seconds, with no subject or serial.

    The file. Refused at start, with a message that names the file and the failure (never its content), before the store is opened: missing or unreadable, a symbolic link, not a regular file, writable by group or other (whoever can write it can un-revoke a certificate), empty, not valid PEM, no CRL in it, or a CRL rustls cannot parse. The checks mirror the key file's (opened with `O_NOFOLLOW` and `O_NONBLOCK`, checked on the open file); there is no owner check, because a CRL is public and a root-owned file is normal. `--tls-client-crl` without `--tls-client-ca`, or given twice, is refused in words.

    Expiry: enforced (`enforce_revocation_expiration`). When a CRL passes its `nextUpdate`, every client certificate its issuer signed is refused, because a stale list proves nothing. The alternative (ignore expiry) would keep a revoked certificate working for as long as nobody renewed the list, which is the silent failure this option exists to end. So the lock-out is loud: the start line says that expiry is enforced and what to do, and each refusal logs `the CRL has expired ... replace the CRL file and restart the server` (once per ten seconds). The fix is a fresh file and a restart; reload without one is #1492 and is not part of this item.

    Unknown status: allowed (`UnknownStatusPolicy::Allow`, rustls `allow_unknown_revocation_status`). rustls's other setting, deny, refuses any certificate in the chain that no configured CRL covers, which includes an intermediate CA when the operator lists only the CRL of the CA that issues clients (checked up to, not including, the trust anchor). Allow gives the rule the ticket asked for: a certificate is denied when a CRL of its issuer is configured and lists it (or is expired), and is otherwise accepted as without the option. Cost, stated: a CRL signed by the wrong CA does nothing and nothing says so (#1614, which also asks for a read of `nextUpdate` at start).

    Tests. `tests/tls_crl.rs` builds certificates and CRLs with rcgen relative to now (no literal dates): a revoked certificate is refused on five routes and sees the revoked alert while an unlisted one connects; an expired CRL refuses a certificate it does not list (the test fails without `enforce_revocation_expiration`) and the log says why; a CRL by another CA does not apply (the documented hazard); nine kinds of bad file stop the server before it listens; the option needs a CA; the start line. `tests/no_network.rs` pins that exactly one place builds the client verifier and that it sets `with_crls` and expiry enforcement.

    Not covered. OCSP and CRL download (the server makes no network request for any of it). Delta CRLs and CRL scoping beyond what rustls-webpki does. Reload without a restart (#1492). A start-time check that a CRL belongs to a CA in the client CA file (#1614).
