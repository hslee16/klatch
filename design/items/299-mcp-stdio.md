`klatch mcp --stdio`: an MCP front end on the same session as the wire (#299, #297; no schema or wire change; 2026-11-18).
Human decision of 2026-11-13: MCP and an HTTP gateway are both wanted as thin front ends on one gateway, MCP first. The design was posted on the ticket before the code. **Shape:** `session/mcp.rs` is an adapter over `Session::call`, the plain request path `serve --stdio` uses, so each tool is the wire method of that name and meets every check a wire request meets (guard, roles, labels, the credential scrub, the receiver budget, stops, the refusal record, audit); the adapter checks nothing of its own and skips nothing. **Identity:** the process's member, found as for every command; the schema of no tool has a member argument and one sent is ignored (a test pins it); a worker's key bundle proves it as before. It runs on the same machine as the same user, so there is no network surface and no zero-trust prerequisite. **Protocol:** JSON-RPC 2.0, one message per line, only messages on standard output (the specification, revision 2025-06-18, lifecycle and transports and tools pages, read on 2026-11-18). `initialize` answers with `2025-06-18`, which is the client's version when it asked for it and otherwise the newest supported (the negotiation rule); capabilities are `tools` only; no resources, prompts or server notifications. The convention text goes in `instructions`, so a runtime with no hooks is taught the lobby convention (#209). **Tools:** `klatch_post`, `klatch_read` (peek optional), `klatch_claim` (one target), `klatch_release`, `klatch_wait` and `klatch_who`. A wire failure is a tool result with `isError` carrying the code, the message and the refusal rule and reason (never matched content); a malformed call (unknown tool, wrong argument shape, a wait outside 1 to 55 seconds) is JSON-RPC `-32602`, an unknown method `-32601`. Messages read come with a notice that they are data. **`wait`:** bounded (default 30 seconds, at most 55) so it never outlives a runtime's own tool timeout by design; it polls `read` every 100 ms over the rooms and returns the first poll that has messages, each tagged with its room, or `timeout: true`. It moves the cursor as `wait` and `read` do. The server answers one request at a time, so a wait holds the connection until it returns; cancellation is not handled. **Differences from the design comment, and why:** `klatch_who` needs a room (the wire has no method that lists a caller's rooms, and the adapter adds no call the wire lacks). **Not built:** `claims`, `asks`, `board`, `status`, `scope`, `history`, `invite`, `dm` as tools; a server-pushed notification for new messages; the HTTP front end. **Tests (written first, red until the command existed):** `tests/mcp.rs`, a client speaking MCP to the real binary against a real store: version negotiation, instructions, `tools/list`, post and read by another member, peek, a claim conflict and a release, a refused post that names the rule and never repeats the secret, wait with a message, a timeout and a message arriving during the wait, wait bounds, who, a `member` argument with no effect, malformed calls, notifications, ping, a clean exit when input closes, and a non-coding agent answering a coding member's ask in the lobby.
