The WebSocket connector is one route on the listeners that exist, `GET /v1/ws`, and the frame layer of tungstenite (#112, epic #13; no schema change; 2026-11-23).
The owner's decision of 2026-11-23 is what is built: after the mutual TLS listener (#108), on its acceptor; `wss` only off loopback (there is no other way to a WebSocket off loopback than `klatch-server https` and its flag), `ws://` only on the loopback listener of `klatch-server http`; tungstenite, synchronous, matching the thread per connection design; one route; no new identity source. SSE plus POST already covers streaming, so the connector is small: `wire_ws.rs` (about 450 lines), `inbox.rs` (the session's input, moved out of `wire_http.rs` and shared), and a few lines in `wire_http.rs` and `wire_https.rs`. No handler changed and no schema changed.

    What it is. `GET /v1/ws` upgrades the connection inside `wire_http::serve_connection` (so the head is read under the HTTP limits, the forwarded header counter sees the request, and the connection holds a slot of `--max-connections` shared with every other route, the excess being the same `503`), then runs the session loop every transport runs: `Session::over` the one shared gateway, `serve_guarded`, the same `hello` first, the same frames. One frame line is one text message each way; a text message holds the lines of a POST body, so a message of several lines is several frames. Over TLS the connection is the plaintext end of the in-process pair of #108, so the pump's windows, its stall deadline and its `close_notify` are unchanged and `wire_ws.rs` names no TLS type and no socket type. Resume needs nothing new: a `subscribe` with `from_seq` on a new connection gets the same messages with the same numbers (tested on loopback and over TLS), and the conformance scenario (requests, events, an acknowledgement, a handoff post, history, read, claim, an unknown method) gives frame for frame what the same client gets over SSE on loopback and over mutual TLS (`tests/ws_wire.rs`, comparing responses in order and stream frames as a set, as `tls_wire.rs` does).

    The library, and why only its frame layer. `tungstenite` 0.30 with `default-features = false`. Its default feature `handshake` brings `http`, `httparse` and `sha1`, and `sha1` is a crate `proto/deny.toml` bans, so the feature stays off and `proto/deny.toml` passes unchanged (`cargo deny check`: advisories, bans, licences and sources ok). What remains is the protocol over any `Read + Write`: masking, fragmentation, the size limits, ping and pong, the close handshake. It adds `bytes`, `log`, `rand` (with `rand_core`, `getrandom` and `chacha20`) and `thiserror` to the tree, all MIT or Apache-2.0, all already allowed. The upgrade request is read by `loopback::read_head` like every request, and the one thing the handshake feature would have given, the `Sec-WebSocket-Accept` value, is the SHA-1 of the client's key and a fixed GUID (RFC 6455 section 4.2.2) made with ring's `SHA1_FOR_LEGACY_USE_ONLY` (ring is already in the tree under rustls; it is a direct dependency now, for this one call). The digest proves only that the server understood the handshake: it is not a secret and no check depends on it. No async runtime and no hyper: `tests/no_network.rs` still forbids every other networking crate, `tokio-tungstenite` and a runtime among them; its list lost the name `tungstenite` and a new test holds the crate to what it is here (present, no `http`, `httparse`, `sha1`, `tokio` or `mio` beside it, named only in `wire_ws.rs`, the dependency line without the handshake feature), and the ring test now lets `klatch-server` itself depend on ring and checks that only `tls.rs` and `wire_ws.rs` name it and the latter for a digest only.

    Who is calling. The credential, checked live, at the upgrade, by the function `GET /v1/stream` uses (`wire_http::authenticate`): `Authorization: Bearer` with `X-Klatch-Member`. Every refusal is the one `401 unauthorized`, before the origin and the upgrade headers are looked at, with no `Sec-WebSocket-` header and no frame; a client certificate gates the port and names nobody; forwarded identity headers give nothing (tested with them alone); the certificate's subject is not read; message text is data. The credential is checked once per connection, as for a stream, and then by the gateway on every request the session runs (`check_credential_live`, the fix recorded in the audit), so a credential revoked or expired mid-connection stops working at once; there is no per-message token. Trust tier and policy are the session's: the member is `Verified` (`hello` says `attribution: verified`, tested), and every frame is a wire method that meets the same guards, clearance and role checks. A post that names another sender is the connection's member's post (tested).

    Origin is not an identity. A browser cannot set `Authorization` on a WebSocket, and a page has no credential and no certificate, so it cannot pass the checks above; but a page on another site can still open a connection to `127.0.0.1`, and a DNS rebinding page can reach a loopback port under its own name. So a request that carries an `Origin` header is refused with `403` unless the operator named that exact origin with `--ws-allow-origin` (on both `http` and `https`; off by default; repeatable; exact bytes; no wildcard; a value that is not `http` or `https` with a lower-case host and an optional port refuses to start, naming the flag). The check comes after the credential, so a stranger learns nothing about origins, and it counts every `Origin` header: an empty one, `null`, a loopback page and a second header are all refused. A client that is not a browser (every worker) sends none. Tested red first, and by removing the check (`tests/ws_wire.rs`).

    Frames and limits. Client frames must be masked (an unmasked frame is a protocol error, close 1002); a message is at most 1 MiB, whole or in fragments (the HTTP body limit and the session's line limit): a frame that declares more is refused at its header with close 1009 and nothing of the payload is read or held, and fragments are counted as they arrive; binary is refused (1003), text that is not UTF-8 is 1007, control frames are at most 125 bytes and never fragmented, reserved bits and unknown opcodes are 1002. No extension and no subprotocol is offered (a client that asks gets neither, and the answer has no `Sec-WebSocket-Extensions` header). A client that sends faster than the session reads is not read from: its messages go through an inbox of 16 and the rest waits in TCP. The write backlog is capped at 4 MiB. Pings are answered with their payload, and a flood of them keeps one reply (the library replaces a queued pong), tested with a thousand.

    Every wait is bounded, and the lessons of #108 apply. The reader owns every read, the session's writer owns every write, and both take the one lock around the protocol state for the length of one call, never across a wait: the socket is non-blocking, the reader polls with a 100 ms tick, and a writer that finds the socket full polls for writability with the lock released, so a connection that is being written to can still be read (its close, its pongs). The head: the HTTP deadline of 5 seconds. Afterwards: the server pings every 20 seconds and closes (1001) a connection that sent no complete frame for 60 seconds (any pong or frame counts; a half frame never completes the clock, so a client that sends half a frame and stops is closed at the same time); a write that cannot finish within the session's stall time (30 seconds) ends the session (the stall deadline of the pump of #108 applies as well over TLS); a close, from either side, is waited on for 2 seconds and then the socket is shut, so a client that never answers a close cannot hold the connection. A debug build with the environment variable `KLATCH_TEST_SHORT_LIMITS` (the knob #108 has; a release binary has none) takes 3, 1, 1 and 3 seconds so the tests need not wait a minute. No thread or descriptor leaks on any exit path: a guard shuts the socket whenever the connection function is left, a panic included, before the scope that owns the reader thread waits for it; the slot of `--max-connections` is given back when the handler returns, and a test opens and ends connections five ways, four times over (a proper close, a dropped socket, a protocol error, a frame header and a disconnect, an idle timeout) against a cap of two, then fills the cap and gets the `503`, and compares the server's open descriptors before and after (`lsof`, skipped when it is not there).

    Mutation checks (each by removing the check, then watching a test fail by assertion, with a timeout on the test's own sockets and on the child process): the Origin refusal, the credential check at the upgrade, the frame size cap, the masking requirement, the stall deadline, the idle deadline and the close wait. The results are in the pull request.

    Not covered, honestly. No run against a second machine or a browser; every test connects over loopback with throwaway certificates (rcgen) and a hand-written client (so a conforming library that this client disagrees with was not tried: the RFC's example key gives the RFC's accept value, tested). No `permessage-deflate`. No per-message token and no re-authentication on a long connection beyond the gateway's live check of each request. No client in the Python, TypeScript or Rust libraries (`clients/README.md` shows the connection for any WebSocket library; adding a transport to the libraries is a ticket of its own). Denial of service by volume is bounded as in #108, not removed: a peer that reaches the loopback port can hold connections up to the cap (each needs a credential to get past the upgrade, but an upgrade-less connection holds a slot for the 5 second head deadline). A ping or a pong keeps an otherwise silent connection open indefinitely, by design: a client that answers is alive. The slow-reader test shows the connection is cut once the buffers are full, not that a client that reads one byte a minute is cut (its bytes move; as in #108, cutting it would need an application-level acknowledgement).
