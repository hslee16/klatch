The B1 and B0 baseline arms of the coordination bench are defined from the documentation, proposed and pending the human's approval (#1365; no schema change; 2026-11-22).
Native cross-session messaging is documented to work under `claude -p`: a `-p` session binds an inbox socket like an interactive one, appears in `ListAgents`, and reads a message between tool calls (docs: cross-session-messaging.md, "Non-interactive sessions"). It needs Claude Code 2.1.224 or later (2.1.248 on every provider or with flag fetching off), nothing to enable, `SendMessage` and `ListAgents` not denied, no `--bare`, and an inbound policy that delivers: a `-p` session cannot answer the approval dialog, so a held message expires after `dialogExpiry` (5 minutes), and the docs advise `crossSessionInbound` set to `accept` in the worker's `--settings`. A session answers to `--name`. A finished `-p` session has exited and cannot be reached, and nothing in the docs gives a blocking wait, so a waiting agent keeps making tool calls (`sleep 20`). Agent teams are not usable: they need `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` and an interactive session, and under `-p` Claude does not spawn teammates (agent-teams.md). Named subagents message each other only inside one parent session, which is not the bench's topology of separate sessions in separate clones. How the audience coordinates without klatch is partly documented (worktrees and cross-session messaging for sessions you run yourself: agents.md, worktrees.md) and partly unknown (which of a shared task file, pull requests and an issue tracker they actually use; no public data was found, so this is the human's call).

B1 is therefore: separate `claude -p` sessions, one clone each, `--name NAME`, `--settings '{"crossSessionInbound":"accept"}'`, `SendMessage`, `ListAgents` and `Bash(sleep:*)` allowed on top of the common tools, and a harness-seeded `TASKS.md` with one line per piece of work, `- NAME | STATUS | FILES | TITLE` (STATUS `working`, `done`, `blocked`, `handoff`). B0 is the shared bare repository with the common tools and `Bash(sleep:*)` only. Every non-B1 arm has `SendMessage` and `ListAgents` denied and inbound messages refused, so nothing native leaks into B0 or the K arms, and the tool schemas are a measured cost of B1 alone. B1-roles (an integrator and a supervisor done with the same native means, mirroring K3) is proposed beside K3 so roles are not credited to klatch; B1-teams is not built. The prompts are `experiments/coordbench/arms/B0.md`, `B1.md` and `B1-roles.md`; `check_parity.py` (tested) enforces the equal-quality rule (sections within 15 percent of their mean in words, the same six-topic outline, one shared common prompt, no klatch words or other arms' tools in a B arm); `REVIEW.md` is the checklist for a reviewer who did not write the arms, with the places where bias could enter; `PILOT.md` is the pilot plan for the human (a messaging probe and one run per arm on the trivial fixture, about $0.20 to $2.50 including caps). Unknown until the pilot: whether per-run HOME and `CLAUDE_CONFIG_DIR` and `--no-session-persistence` still let the two sessions see each other, and whether `ListAgents` leaks the user's own interactive sessions into a B1 run. The harness has no launcher for role members yet (K3 or B1-roles). Nothing was run and nothing was spent.
