The Harness trait and room capability requirements (#61, epic #12; no schema change; 2026-11-18).
`harness::Harness` is two methods, `id()` and `level(Capability)`, and an adapter only declares: it holds no key, opens no socket and decides nothing (section 20 rule 1). **Capabilities** are the rows of the section 20 table less the hook trust step: `context-injection`, `session-identity`, `wake`, `pre-action-enforcement`, `permission-mode`, `headless-worker`, `pull-path`. **Levels** are `native`, `degraded` (partial, conditional or unverified) and `absent`; only `native` satisfies a requirement, so an unverified claim never opens a room. **Adapters on main:** `ClaudeCode` is the hook tier that already exists (its `wake` follows the version probe of #482; `permission-mode` is degraded until section 22 confirms what hooks receive), `Codex` is a paper adapter built from the #548 findings (RESEARCH-NOTES 49.3, SURVEY 12) that never runs `codex`, and `Generic` is the floor of rule 3. **Codex on paper:** every hook-backed capability (`context-injection`, `session-identity`, `pre-action-enforcement`, `permission-mode`) is `native` only when the hooks are known trusted (`HookTrust::Trusted`) and `degraded` for `Untrusted` and `Unknown`, because Codex skips an untrusted hook silently in `codex exec`; `wake` is degraded (`codex queue` is absent from 0.147, has no sender or acknowledgement, and needs a probe by running `codex queue --help`, not by version); `headless-worker` is native (`codex exec --json` observed); `pull-path` is degraded (MCP client is a report). The check against Codex changed one thing in the first draft: session identity and permission mode are not assumed to be free, since both ride on hooks that may not run.

**A room requires a capability** with `klatch admin room-require ROOM MODE:CAP[,CAP...]` (human only, audited as `room-require`, stored as the policy key `room:ROOM:require`; `--off` lifts it). `refuse` keeps a member whose harness lacks one out (rule `harness-capability`, recorded in the refusals log); `flag` admits it and records the gap (rule `harness-flagged`, same log). **Fail closed:** an unknown capability or mode is invalid at set time, and a stored value this build cannot read (a hand-written key, a newer build's capability) refuses every joiner whatever its mode. `Gateway::join_with_harness` takes the harness; `Gateway::join`, which names none, is the generic floor, so a room that requires a capability the floor lacks refuses a plain join. Rooms with no requirement behave as before.

**Not built, ticketed:** the CLI, wire and hook paths still call `join` and so are the generic floor; nothing yet tells the gateway which harness a session runs, and a harness id the caller supplies would be a claim by an untrusted conveyor, so it needs the identity evidence of rule 5 behind it (#62 and #64 own this). A flagged member is recorded but not shown as advisory in `who` or `read`. **What the conformance suite (#62) will need:** for each adapter, `level` is total over `Capability::ALL`; a `native` level must name the observation or document that backs it (a field the suite can read, not prose); `id` is stable and unique; an adapter that cannot be probed declares `degraded` or `absent`, never `native` (the suite checks the unknown input case: `HookTrust::Unknown`, `Support::Unknown`); and each `native` capability has one end-to-end check run against the real harness or its recorded transcript. The trait stays at two methods so the suite has one thing to check per capability; adding a probe method belongs to #62, not here.
