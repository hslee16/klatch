Codex has no registry record, so a Codex join is the generic floor: what the ticket asks, the minimal safe design, and the decisions it waits on (#884, with #880, #881, #341, #590, #783; design only, nothing built; no schema change; 2026-11-24).
**What the ticket asks.** The verified-harness join (#877) lifts a session above the generic floor only on evidence klatch checked itself: a live process whose program is `claude`, found by the walk up the process tree, and a registry record (`<pid>.json` under `~/.claude/sessions`, written by Claude Code itself) whose pid and start time match that process. `identity::runs_claude_code` is that test, and it is false for Codex on purpose: a Codex session is named by its hook `session_id` or `CODEX_THREAD_ID` (`identity::codex_session`, #341), which is a name, not a verified process, and no Codex registry record exists. #884 asks for the two missing parts, a Codex record writer and a walk that matches a process named `codex` against it, "with the same fail-closed rules". The ticket's last comment adds that the change needs a human decision (should Codex be a verified harness at all, and who runs the check), a real Codex session to see the process name and tree, and a verified-harness id with a capability set. This item writes the design down so those decisions are one question each. It builds nothing and changes no prompt, refusal, golden text, audit row or SECURITY.md rule; Claude Code sessions and every existing path stay byte for byte as they are.
**What would change.** Today every Codex caller is `Caller.claude_code == false`, so `Direct`, `serve --stdio`, `mcp --stdio`, `acp --stdio` and the daemon peer check (`peer_runs_claude_code`) all join as `Generic`, and a room with `room-require` for any capability the floor lacks refuses it (DESIGN item 20 rules 3 and 6). After the build a Codex session whose process tree verifies would join as the `Codex` harness (`harness::Codex::paper(trust)`), so it would satisfy exactly the capabilities that adapter declares `Native` and no others. That is a change in who counts as verified, which is why it is not built before the owner answers.
**The minimal safe design.**
1. A Codex SessionStart hook step, inside the SessionStart command `init --codex` already installs (`klatch --codex session-start`, no new hook and no new event), writes one record. It walks up from the hook process to the nearest ancestor whose program is `codex` (same walk as `find_session`: bounded depth, no pid 1, no revisit, any unreadable table is no record), reads that process's start time from the same process table, and writes `<pid>.json` with the same fields a Claude record has (`pid`, `sessionId` from the hook's standard input, `cwd`, `name`, `procStart` in UTC with whitespace collapsed, `pidDomain`). The record goes in klatch's own registry directory (`<klatch home>/harness/codex/`, mode 0700, file 0600, written to a temporary name and renamed), never under `CODEX_HOME` or any other Codex state, and klatch never reads Codex's directory for it.
2. The reader is `FsRegistry` over that directory with the same rules as the Claude one: only `<pid>.json` is opened, the pid inside must equal the file name, a malformed file is skipped and counted, a missing directory has no records.
3. The walk is `find_session` with a program test for `codex` beside `is_claude_code` (`liveness::is_codex`, the program name exactly `codex` or a path ending in `/codex`, nothing looser). The test is a parameter of `check` so the Claude path keeps calling it with `is_claude_code` and is not touched.
4. A record counts as evidence only if all of these hold: the pid domain is this machine's; the pid exists in the process table; its start time equals the recorded `procStart` (a reused pid has another start time); its program is `codex`; for a hook, the record's session id equals the session id on the hook's own standard input (the rule #284 applies to Claude). Any other outcome (`OtherDomain`, `Dead`, `Reused`, `NotHarness`, `Unreadable`, a table that cannot be read, no home, no record) never raises the session above the generic floor, and none of them is an error that stops the command: the join simply stays the floor, as a Claude miss does.
5. Nothing is trusted from the environment alone. `CODEX_THREAD_ID` stays data that names a member (#341); it never selects a record, never marks a session verified and never reaches the harness choice. A typed `KLATCH_NAME` keeps winning over discovery and stays the floor (#881), a key bundle stays the floor (#880), and a record is looked for only at the pids of the caller's own ancestors, never by a session id the caller supplies.
6. No credential is created or read. The record holds no key, token or secret, there is no `.key` file beside it and the walk never opens one; the record writer touches no keychain and no key store.
**Forgery, matched to the Claude path.** The Claude path is same-user evidence: anything running as the user can write `~/.claude/sessions/<pid>.json`, so a process of the same user that forges a record for a live `claude` ancestor is believed (DESIGN item 20 rule 5; SECURITY.md says the principal stays unattributed and that this keeps an honest session from being mislabelled and a plain script from claiming enforcement). The Codex design matches that grade and claims no more. A forged file is not enough on its own: it must name a pid that is alive, started at the recorded time and running a `codex` program, and it must sit at an ancestor of the caller, so a record for an unrelated process, for another user's process (a pid this user cannot be the ancestor of; the walk is from the caller's own parent chain), for another session's process, for a dead pid or for a reused pid is never evidence. What it does not stop is an agent inside the real Codex session writing a record for its own `codex` ancestor with any session id; for a hook, the session id on its standard input must also equal the record's. The record writer lives in klatch's registry directory, so an agent that can write there can also write the store; the same-user boundary is the boundary, as for Claude.
**What a verified Codex would be allowed.** `Codex::paper(trust)` declares `HeadlessWorker` native always and `SessionIdentity` native only when the hooks are trusted (RESEARCH-NOTES 49.3, 49.7); every other capability is degraded and never satisfies a room. The hook trust the harness is built with comes from a Codex file read, which is a second decision (below); until it is decided the safe value is `HookTrust::Unknown`, which makes `SessionIdentity` degraded.
**Tests the build must have, written first.** A hook run writes the record in a temporary registry (and never writes under a temporary `CODEX_HOME`); the walk matches a live `codex` process in a fake process table; a dead process, a reused pid, another program with the right pid and start, another pid domain, an unreadable table and a table that fails partway up are each the floor; a record filed under another pid, a record naming a process that is not an ancestor, a record for another session on a hook, a malformed record and a missing registry are each the floor; a forged file for an unrelated pid is the floor and a forged file for the real `codex` ancestor is believed exactly as the Claude path believes it (with the ticket recording that grade); `CODEX_THREAD_ID` alone, a typed name and a key bundle are each the floor; every refusal is mutation-checked so it fails a test by an assertion, not a hang; the Claude walk, `runs_claude_code`, the golden consent and discovery texts (`tests/golden*`, pinned byte for byte) and `tests/authz_audit.rs` pass unchanged before and after. Because the record writer is a new write path and the verified join is a new evidence kind, the build adds its row to `proto/AUTHZ-AUDIT.md` (with its `proto/audit` fragment) and its rule to SECURITY.md.
**What is not known and cannot be learned without Codex.** (a) The program name `ps -o comm=` prints for a Codex session on macOS and Linux: the npm package starts a Node shim and then a native binary, so the tree may hold a `node` process running `codex.js` above or beside a native `codex`, and a hook may run under a shell the tree does not show; no run of a hook with its process tree was ever observed (RESEARCH-NOTES 49.3 ran hooks only under the bypass flag and did not look at the tree). (b) Whether a hook under `codex exec`, a hook in a resumed or forked session and a hook in a session started by the app server all have a `codex` ancestor. (c) Whether the same hook runs after `/clear` or `compact` with the same session id (the `source` field says so; the record would need to be refreshed, not duplicated). The check that answers (a) and (b) is a hook run under a temporary `CODEX_HOME` with a recording hook and a trusted hook state, which runs a hook only and needs no login, but `codex exec` goes on to a model call that fails with 401, so it was not run for this item (a model call, even a failing one, is out of bounds for this work). Until it is run, step 3's program test is a guess about the name, and a wrong guess fails closed (no match, the floor), never open.
**Decisions the owner must make (the build waits on them).**
- Q1. Should a Codex session be a verified harness at all, given that its evidence would be same-user, like the Claude one, and that an interactive session the human did not start (`codex exec`, a worker) also has a `codex` ancestor? Options: (A) yes, as designed here; (B) no, Codex stays the floor and #884 is closed as a documented gap; (C) yes, but only for a hook that is trusted (the record is written by the trusted SessionStart hook only, so an untrusted hook, which Codex skips, never produces one; this is already what step 1 gives, so C is A with that stated as a rule).
- Q2. Which capabilities may a verified Codex satisfy? Options: (A) the `Codex::paper` set as declared (`HeadlessWorker` always, `SessionIdentity` only when trusted); (B) none yet (a verified Codex joins as `Generic` plus a recorded `codex` label, so `who` can show it but no room requirement changes); (C) only after a real Codex run observed each one.
- Q3. Where does `HookTrust` come from for the harness? Options: (A) `Unknown` always (safe, `SessionIdentity` stays degraded; the question #590 and #783 leave open becomes irrelevant here); (B) read `config.toml` trust state the way `klatch doctor` does, which is not verified for several hook layouts (#590, #783) and must never be a reason to raise a level; (C) the human states it in `init --codex`.
- Q4. Who runs the check: the CLI edge on every command (a walk costs a `ps` per ancestor and is skipped when a name is typed, `walk_wanted`; the same trade as #881), or only the transports that join (`join`, `serve`, `mcp`, `acp`, the daemon peer)? The design takes the second, because only a join reads the harness.
- Q5. May the record writer be an extra step of the existing SessionStart hook (this design), or must it be a separate hook entry the human reviews in `/hooks`? A separate entry changes `init --codex` output and so its golden text (`tests/golden_consent_hooks.rs`, pinned byte for byte) and asks the human to trust one more hash. The extra step leaves the hook's command line, and so the hash Codex trusts, unchanged.
**Recommendation.** Option A of Q1 with the C rule, Q2 option B for the first release (record and show the harness, change no room requirement), Q3 option A, Q4 as designed, Q5 as an extra step; then Q2 moves to A once the real Codex check in the previous paragraph has recorded the process names and the tree. #880 (a credential names a member and says nothing of its harness) and #881 (a typed name inside a verified session is the floor) are unchanged by this design and keep their own tickets.
