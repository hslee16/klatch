**What the ticket asked.** The verified-harness join (#877) lifts a session above the generic floor only on evidence klatch checked itself: a live process whose program is `claude`, found by the walk up the process tree, and a registry record (`<pid>.json` under `~/.claude/sessions`, written by Claude Code itself) whose pid and start time match. `identity::runs_claude_code` is that test and stays false for Codex. A Codex session was named only by its hook `session_id` or `CODEX_THREAD_ID` (`identity::codex_session`, #341), which is a name and not a verified process, and no Codex record existed, so every Codex join was the generic floor. #884 asked for a Codex record writer and a walk that matches a process named `codex` against it, with the same fail-closed rules.
**Decisions of the owner (2026-11-24, recorded on the ticket).** 1. Codex is a verified harness only through the trusted SessionStart hook: only a record written by that hook counts as evidence. 2. Capabilities: none yet. A verified Codex is recorded and shown as its harness, and no room requirement changes. 3. `HookTrust` is always Unknown: klatch never asserts Codex hook trust and does not read `config.toml` for this. 4. The walk runs only where a join is judged, not on every command. 5. The record writer is an extra step inside the existing SessionStart hook: its command line, and so the hash Codex trusts, is unchanged, there is no new hook entry, and the `init --codex` text (golden) does not change.
**What is built.**
1. The writer. `klatch --codex hook --event SessionStart` (the hook `init --codex` already installs) calls `member::record_codex_session` before it runs. It writes only when the call is a Codex session and the hook's own standard input names that same session id (the environment's thread id alone never does). It walks up from the hook process to the nearest ancestor whose program is `codex` (`harness::write_session_record`: bounded depth, never pid 1, never a pid twice, an unreadable table at any step is no record) and writes `<pid>.json` with the fields of a Claude record (`pid`, `sessionId`, `cwd`, `name`, `procStart` in UTC with whitespace collapsed, `pidDomain`), so `parse_record` reads both. It goes in klatch's own directory `<klatch home>/harness/codex/` (`$KLATCH_HOME`, else `$HOME/.klatch`), never in Codex's state: the directory must not be a symlink and must be the user's own (else nothing is written), is set to 0700, and the file is written 0600 under a temporary name and renamed, so a half-written record is never read and a symlink at the final name is replaced, not followed. A write also removes the records of processes that are gone (dead, pid reused, no longer `codex`); a record that cannot be judged (another pid domain, an unreadable table) is kept. Nothing is written, not even the directory, unless a `codex` process is found above the hook. Errors are never reported to Codex: a hook must not fail a session.
2. The check. `harness::find_session_with` is `find_session` with the program test as a parameter (Claude Code's calls it with `is_claude_code`, byte for byte as before); the Codex walk passes `is_codex`, which is exactly the name `codex` alone or at the end of a path (`CODEX_PROGRAM`, a constant; nothing reads it from the environment, a file or a flag). Unlike the Claude test it accepts no retitled process (`codex something`), so a doubt is a miss. The registry is `OwnRegistry`: a record is read only if its file is a plain file (not a symlink) owned by the user and no one else can write it (mode & 022 is 0), then parsed by the Claude reader (only `<pid>.json`, the pid inside must equal the file name).
3. The rules. A record counts as evidence only if its pid domain is this machine's, its pid is alive, its start time equals `procStart`, its program is `codex`, it sits at an ancestor of the caller (never a record found by id), and it names the session id the call acts for (`verified_session`; the nearest live record decides, so the record of another session above is a miss). `OtherDomain`, `Dead`, `Reused`, `NotHarness`, an unreadable table, a malformed or misfiled or foreign or group-writable record, a missing registry, no home and no record are each `generic`, and none is an error. `CODEX_THREAD_ID` is data: it names the member (#341) and is compared with the record, never selects it and never marks a session verified. A typed name, a key bundle and a Claude Code session never reach this code (`codex_harness` is `None` without a Codex session), so every Claude Code prompt, refusal and golden is untouched. No credential is created or read: the record holds no key or token and nothing opens a `.key` file.
4. The shown harness. A join from a Codex session is judged by `CodexRecorded`, whose levels are always those of `Generic`, whatever the walk finds (a verified Codex satisfies no more than the floor does, and a room requiring `headless-worker`, `session-identity` or `pre-action-enforcement` still refuses it). Only `id()` differs: `codex` when the walk verifies the record, else `generic`, so a refusal reads "codex lacks wake" rather than "generic lacks wake". The walk runs once, the first time the name is asked for, which is only when a room has a requirement or a refusal is written; a command that joins no gated room costs nothing. It is wired where a join is judged: `join` and the SessionStart hook (through `Direct`), `serve --stdio`, `mcp --stdio` and `acp --stdio`. The daemon peer path (`peer_runs_claude_code`) is not changed: a daemon peer sends no Codex session id and stays the floor.
**Forgery, matched to the Claude path.** The Claude registry is same-user evidence: anything running as the user can write `~/.claude/sessions/<pid>.json`, so a process of the same user that forges a record for a live `claude` ancestor is believed (DESIGN item 20 rule 5). The Codex record matches that grade and claims no more. A forged file is not enough on its own: it must name a pid that is alive, was started at the recorded time, runs a `codex` program, is an ancestor of the caller and names the caller's session. Tested: a forged record written by a process that is not `codex` is the floor; a forged record for another pid, a guessed start time, another session, another machine or another user's file is the floor; and a forged record written from inside a live `codex` process for itself is believed, as the Claude path believes the same thing. Because the record grants no capability, a believed forgery changes only the name shown.
**NOT OBSERVED.** The program name `ps -o comm=` prints for a real Codex session on macOS and Linux, and the tree of a real hook: the npm package starts a Node shim and then a native binary, and a hook may run under a shell. No run of a hook with its process tree was ever observed (RESEARCH-NOTES 49.3 ran hooks under the bypass flag and did not look at the tree; 49.9 probed hook trust without running a hook). Also not observed: whether a hook under `codex exec`, a resumed or forked session or an app-server session has a `codex` ancestor, and whether `/clear` or compaction runs SessionStart again with the same id (the writer is idempotent, so a repeat rewrites the same file). The program test is therefore a constant that is a guess about the name; a wrong guess fails closed (no record, no match, `generic`), never open. The check that answers it is a recording hook under a temporary `CODEX_HOME`, which needs no login but whose `codex exec` goes on to a model call, so it was not run. The tests use a copy of the shell named `codex`.
**Tests.** Unit tests (`src/harness/codex_record/tests.rs`, `src/member/codex_harness.rs`) and the real binary (`tests/codex_registry.rs`): the record written by a hook in a fake process table and by a real hook in a program named `codex`; a live `codex` found; a dead process; a reused pid; the right pid and start under another program; another pid domain; a record naming a process that is not an ancestor; a record misfiled under another pid; another session's record; a malformed record; a missing registry; an unreadable table, and one that fails partway up; a parent loop; a symlinked directory, a symlinked record and a directory of another user; a record another user owns or others can write; a forged record by a non-`codex` process and by a `codex` process; no capability granted; and the floor for a thread id alone and for a hook outside `codex`. Tests were written after the stubs and seen red for every positive case (14 of 30 unit tests failed against stubs that fail closed); the negative cases passed against those stubs, so each key refusal was mutation-checked instead (17 mutants, each killed by an assertion; see the pull request). The integration tests were written after the implementation and were not seen red individually; the mutants run against them were. The Claude walk, `runs_claude_code`, the golden texts, `tests/authz_audit.rs` and the harness tests pass unchanged.
