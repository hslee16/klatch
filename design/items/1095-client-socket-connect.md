The client libraries connect to the daemon's Unix socket (#1095; no schema change; 2026-11-21).
**Question.** What is the smallest change that lets the Rust, Python and TypeScript clients connect to `klatch-server daemon --socket PATH` and say who they are, without putting a socket or a credential into the `klatch` binary?

**What was built.** Each library has a connect over a socket path with an identity argument. The identity is the `identify` first request of the daemon (item 102): a typed name (unattributed), a member and a credential token (verified), or none (`unmapped-process`). After the connect, `member` and `attribution` are what the daemon answered; the clearance stays the one the `hello` carried (the generic floor). The `hello` is read first, so a client that waits for it never deadlocks, and `identify` is sent only after it. A refused identity is an error with code `identity.refused` (Rust `Error::Api`, Python `ApiError`, TypeScript `ApiError`), and the library never repeats the name or the token. A name together with a credential, or a member without a token, is refused locally before anything is sent (Python `ValueError`, TypeScript `TypeError`; the Rust `Identity` constructors make it unrepresentable). Only the token is sent, never the key bundle file that also holds the store key.

- Python: `Client.connect_socket(path, name=None, member=None, token=None)`, standard library `socket`. The pipe, the pump thread and `request` are the stdio ones; `close` shuts the write side, waits for the pump to see the daemon's end, and returns 0.
- TypeScript: `Client.connectSocket(path, { name | member, token })`, `node:net`. The constructor takes a readable, a writable and an exit promise, so the child and the socket share every other line; a write error on a gone transport is answered by the closed session, not an unhandled event.
- Rust: `Client` held a `Child` and a `ChildStdin`. It now holds an optional child, a boxed writer and an optional shutdown action, and `Client::over(reader, writer, shutdown, &Identity)` starts a session on any transport; `Client::connect` is `over` with a child. `close` over a socket shuts it, waits (10 seconds at most) for the daemon to end the session and returns 0; `Drop` never waits for a child that is not there. `Client::connect_socket(&path, &Identity)` is the one function that names `UnixStream`.

**Why the binary stays network-free.** `UnixStream` is named in exactly one file of the `klatch` crate, `src/client/socket.rs`, declared `mod socket;` under `#[cfg(all(unix, feature = "client-socket"))]`. The feature `client-socket = ["client"]` is in no default feature, so the shipped `klatch` binary, the wheels and the npm package do not contain it (the Python and TypeScript libraries are separate source and never link the binary). `tests/no_telemetry.rs` allows `UnixStream` in that file only, and only while the parent declares it under that cfg (no `UnixListener`, no TCP type, anywhere), and a new test asserts that `default`, `client` and `cli` do not turn the feature on and that it brings in nothing but `client`. The `klatch-server` crate asks for the feature in its dev-dependencies only, so the daemon binary does not link the client either.

**Conformance.** The connect-dependent steps of `proto/klatch/tests/client.rs` moved unchanged into `proto/klatch/tests/client_scenario/mod.rs`, written against `home()` and `connect(&home, name)` of the including crate. `client.rs` provides them over `klatch serve --stdio`; `proto/klatch-server/tests/client_socket.rs` includes the same file by path and provides them over the daemon (a daemon child per throwaway store, a short socket directory under /tmp). The Python and TypeScript suites run their scenario twice, with a store that starts a daemon for the second run; the test bodies are the same, so the events and sequence numbers match by assertion (history seqs, `1, 2, 3` then `4` live then `5` on resume, `dm.alice.bob`, the dense numbers). Over the socket, the scenario also ran against a credential: only Rust issues one (the test builds a gateway on the temp store, as the daemon tests do), so Python and TypeScript test the refusal path with a token that is not live.

**What this does not cover.** A verified connection from Python or TypeScript (no credential can be issued from those suites without running `klatch worker issue`, which only the human does); Linux (the suites ran on macOS); the sealed-label keys per connection (#1096); the daemon refusing a uid that is not its own (no second user in a test).
