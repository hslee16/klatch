The daemon carries sealed-label keys and harness evidence per connection (#1096; no schema change; 2026-11-21).
The daemon (#102) holds one gateway on one owner thread, so the two things `klatch serve --stdio` settles once per process could not be done per connection: the keys of sealed labels (#160) and the harness a room's `room-require` judges a join by (#877). Both are now carried per request to the owner thread, and both are bounded by the same rules a process of its own gets.

Keys. `SharedGateway::spawn_keyed` takes a key source in addition to the build closure. For each request the owner asks the gateway which sealed labels the request's principal is cleared to (`sealed_labels_within`, the rule `open_member` uses), asks the key source for those keys and no others, puts them on the store for that one request and takes them off after it. A member never holds a key above its clearance, one connection's keys are not on the store for the next request, and a label with no key in the keystore stays sealed (a write fails closed as before). The source (`member::spawn_shared_gateway`) reads the same keystore as a process of its own, afresh for each request that needs a key, so a rotated key is seen at once and the daemon keeps no copy of a key between requests. A request that reaches no sealed label never touches the keystore. The key rule still reads the global clearance, so a room grant (#893) opens no key (#896 is unchanged and still waits for the human).

Harness. `SharedBackend::with_harness` binds a harness to one connection's backend, and `Backend::handle_as` carries it to the one wire method that reads it, `join` (`join_with_harness`; `None` is the generic floor, which `handle` is). The daemon learns the harness from the pid the kernel reports for the peer: `member::peer_runs_claude_code` runs the walk up the process tree and the registry check that a command runs for itself (#877), and only a connection that never sent `identify` and whose pid is inside a verified Claude Code session joins as Claude Code. A connection that identified with a typed name stays the floor (a typed name proves nothing, #881), and so does one that identified with a credential (a credential proves a member and not a harness, #880). Anything the peer sends is never read for it, and any doubt (no home, an unreadable table, a stale record) is the floor.
