A global alarm on admin passphrase failures across all terminals (#1310; no schema change; 2026-11-24).
With #1274 the failure count is per terminal, so a program that opens new pseudo-terminals gets three free guesses on each and nothing bounds the total. The human decided on 2026-11-23 that the backstop is an alarm only: no lockout and no extra delay, because any ceiling low enough to matter is again a way for an agent to lock the human out, the thing #1274 removed. The alarm makes a slow brute force visible; it stops nothing.

The rule: when the failed proofs inside a rolling 24 hours reach `CEILING` (50), the proof path writes ONE audit row, action `proof-failed-many`, target `alarm`, detail `failures=50 terminals=17 window=24h` (the count, the number of distinct terminals among the failures, the window; counts only, no terminal label, nothing typed). `klatch doctor` shows a warning while the count in the last 24 hours is at or above `CEILING`: `proof failures: 63 wrong admin passphrases or recovery codes in the last 24 hours, from 21 terminals (the alarm level is 50); nothing is locked by this, the per-terminal wait is unchanged`, with a fix line that points at `klatch admin audit`. A wrong recovery code typed for `reset-passphrase` is a `proof-failed` row too and counts. The store-less `recover` and `restore` limit (#1281) is a file beside the store and writes no `proof-failed` row, so it is not counted (ticketed).

The count is read from the audit table itself (`proof-failed` rows with `ts` in the last 24 hours; the window is `ts > now - 86400`, so a failure exactly 24 hours old no longer counts), one new read-only store method `audit_census` (a COUNT and a COUNT DISTINCT of the `terminal=` field of the detail, on the existing `admin_audit_action_target_ts` index). No migration, no new policy key: the audit is already written only by the proof path, so nothing an agent can reach is the input of the alarm, and an agent cannot suppress the row or forge one (the only code that writes the action is `proof/alarm.rs`, pinned by a test that scans the source). The per-terminal counters, waits, lockouts, prompts and every existing audit row are untouched.

Once per crossing: the `proof-failed` row and the check are one write transaction, so two processes failing at once cannot both miss the crossing. The row is written only when the count after this failure is exactly `CEILING`. Later failures make it 51, 52 and write nothing. When enough old failures roll out of the window the count falls below `CEILING` and the next time a failure brings it back to exactly `CEILING` the alarm fires again (re-armed). A success does not reset the count: a guesser who gets one right ends the guessing, but the person who typed it wrong 50 times should still see the day's failures. If the census cannot be read the failure row is still written and the alarm is skipped; the alarm never changes what a proof does. A program that keeps the count hovering at exactly 50 by failing at the rate the window drops them can write at most one row for each time it re-crosses, one per failure at the very most, and every one of them is a row the human wants to see.

Why 50, with the numbers from `proof/limit.rs`. A terminal gets 3 free guesses, then waits 30, 60, 120, 240, 480 seconds and then 900 seconds each, so one terminal that never gives up makes about 3 + 5 + (86400 - 930) / 900 = about 103 guesses a day; a program that opens a new terminal for every 3 guesses is bounded only by how fast it can verify (Argon2id at 19 MiB and 2 passes, tens of milliseconds a guess), so 50 failures are 17 fresh terminals and well under a second of its time. A ceiling of 1000, the number the ticket gave as an example, would never fire for the single patient terminal (about 103 a day) and would fire after 334 fresh terminals for the fast one, long after the harm of a guessing run. A human mistypes a handful of times a day at most, so 50 is far above ordinary use, and the cost of a false alarm is one warning line and one row that say nothing was locked. The constant is `proof::alarm::CEILING`; the window is `WINDOW_SECS`.

Tests: `proof/alarm_tests.rs` (N-1 failures across terminals give no row; the Nth gives exactly one; the N+1th none; the window boundary; the re-arm; a success does not reset; per-terminal locks and policy keys unchanged; recovery code failures count; no secret in the row; only the proof path writes the action), `tests/doctor_proof_alarm.rs` (the real binary on pseudo-terminals: no warning at 49, the warning at 50, no secret in it). The golden tests of #1480 are unchanged: none of them reaches 50 failures.
