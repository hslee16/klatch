A global alarm on admin passphrase failures across all terminals (#1310; no schema change; 2026-11-24).
With #1274 the failure count is per terminal, so a program that opens new pseudo-terminals gets three free guesses on each and nothing bounds the total. The human decided on 2026-11-23 that the backstop is an alarm only: no lockout and no extra delay, because any ceiling low enough to matter is again a way for an agent to lock the human out, the thing #1274 removed. The alarm makes a slow brute force visible; it stops nothing.

The rule: when the failed proofs inside a rolling 24 hours reach `CEILING` (50), the proof path writes ONE audit row, action `proof-failed-many`, target `alarm`, detail `failures=50 terminals=17 window=24h` (the count, the number of distinct terminals among the failures, the window; counts only, no terminal label, nothing typed). `klatch doctor` shows a warning while the count in the last 24 hours is at or above `CEILING`: `proof failures: 63 wrong admin passphrases or recovery codes in the last 24 hours, from 21 terminals (the alarm level is 50); nothing is locked by this, the wait of each terminal is unchanged`, with a fix line that points at `klatch admin audit`. A wrong recovery code typed for `reset-passphrase` is a `proof-failed` row too and counts. The store-less `recover` and `restore` limit (#1281) is a file beside the store and writes no `proof-failed` row, so it is not counted (ticketed).

The count is read from the audit table itself (`proof-failed` rows, on the targets `""` and `recovery`, with `ts` in the last 24 hours; the window is `ts > now - 86400`, so a failure exactly 24 hours old no longer counts) through one new read-only store method, `audit_census(action, targets, since, cap)`. No migration, no new policy key: the audit is already written only by the proof path, so nothing an agent can reach is the input of the alarm, and an agent cannot suppress the row or forge one (only `proof/alarm.rs` names the alarm action and the proof path names `proof-failed`; a test scans the source for the text and the constants).

The census runs inside the write transaction of every failed proof, so its cost must not grow with the audit. The failure path asks for a count capped at `CEILING + 1`: for each target it reads at most that many rows of the `(action, target, ts)` index as a range (`action=? AND target=? AND ts>?`), the union is cut at the cap too, and the distinct `terminal=` labels are counted over those few rows only (the row is written when the capped count is exactly `CEILING`, so the rows counted are all of the window). At most 2 x 51 index entries are touched however large the audit is; a test fills the table with 5000 old rows outside the window and pins the answer and, with `EXPLAIN QUERY PLAN`, that both table accesses are `SEARCH`es of that index by range and none is a scan. A first version counted every `proof-failed` row of the window in one query (a count and a distinct count, with a temporary tree for the distinct): 782 ms with 1,000,000 rows in the window on the development machine, paid with the write lock held on every failure; the capped one takes 0.25 ms on the same rows. `klatch doctor` keeps the exact count, outside any write lock, on a read-only connection (`alarm::read_recent`): its cost grows with the failures inside the window (about 845 ms for a million, which only an attacker could make) and is paid by a person who asked for a report.

Once per crossing: the `proof-failed` row and the check are one write transaction, so two processes failing at once cannot both miss the crossing. The row is written only when the count after this failure is exactly `CEILING`. Later failures make it 51, 52 and write nothing. When enough old failures roll out of the window the count falls below `CEILING` and the next time a failure brings it back to exactly `CEILING` the alarm fires again (re-armed). A success does not reset the count: a guesser who gets one right ends the guessing, but the person who typed it wrong 50 times should still see the day's failures. If the census cannot be read the failure row is still written (once, without rolling back and writing again) and the alarm is skipped; the alarm never changes what a proof does. If the transaction cannot start at all (another process holds the write lock past the busy wait of 5 seconds) the failure row is written on its own as before the alarm existed; under that contention the fallback write can wait another 5 seconds, so an answer can be delayed up to about 10 seconds instead of 5. The busy wait is a property of the connection and a shorter one for the alarm transaction alone is not cheap, so it is left as it is; the delay only happens when the store is already stuck for every other writer too. A program that keeps the count hovering at exactly 50 by failing at the rate the window drops them can write at most one row for each time it re-crosses, one per failure at the very most, and every one of them is a row the human wants to see.

Why 50, with the numbers from `proof/limit.rs`. A terminal gets 3 free guesses, then waits 30, 60, 120, 240, 480 seconds and then 900 seconds each, so one terminal that never gives up makes about 3 + 5 + (86400 - 930) / 900 = about 103 guesses a day; a program that opens a new terminal for every 3 guesses is bounded only by how fast it can verify (Argon2id at 19 MiB and 2 passes, tens of milliseconds a guess), so 50 failures are 17 fresh terminals and well under a second of its time. A ceiling of 1000, the number the ticket gave as an example, would never fire for the single patient terminal (about 103 a day) and would fire after 334 fresh terminals for the fast one, long after the harm of a guessing run. A human mistypes a handful of times a day at most, so 50 is far above ordinary use, and the cost of a false alarm is one warning line and one row that say nothing was locked. The constant is `proof::alarm::CEILING`; the window is `WINDOW_SECS`.

Failures from before the upgrade count toward the window: an install that already has 50 or more `proof-failed` rows inside the last 24 hours on upgrade day shows the doctor warning at once but writes no alarm row until the count falls below 50 and crosses again. A wall clock moved backwards keeps rows stamped in the future counting until the clock passes them; moved forwards, it lets failures drop out early. Both only shift when the alarm fires and neither locks anything.

Tests: `proof/alarm_tests.rs` (N-1 failures across terminals give no row; the Nth gives exactly one; the N+1th none; the window boundary; the re-arm; a success does not reset; per-terminal locks and policy keys unchanged; recovery code failures count; no secret in the row; only the proof path names the action or `proof-failed`), `proof/alarm_faults.rs` (a census that fails changes no answer and loses no row; a transaction that cannot start still writes the failure row; two failures racing at the line from two connections write exactly one alarm row), `store/sqlite/tests/audit_census.rs` (5000 old rows, the cap, the query plan), `tests/doctor_proof_alarm.rs` (the real binary on pseudo-terminals: no warning at 49, the warning at 50, no secret in it, nothing when the store key is gone) and the unit test in `doctor/mod.rs` (nothing when the census could not be read). The golden tests of #1480 are unchanged: none of them reaches 50 failures.
