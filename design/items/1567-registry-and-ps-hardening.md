The Claude registry and the process table are read defensively, and the process table is read once per walk (#1567, #1568, #1569; no schema change; 2026-11-25).
**What the tickets asked.** The security review of #884 found three weaknesses in the evidence behind a verified session, all same-user and so availability and fail-soft problems, not escalations. 1. `FsRegistry` read `~/.claude/sessions/<pid>.json` with `read_to_string` on the path: it followed symlinks, a FIFO named like a record blocked the reader for ever and there was no size cap. 2. `PsTable` ran `ps` through PATH, so a `ps` earlier on PATH answered every liveness and walk question. 3. `PsTable` ran `ps` three times per pid.
**What is built.**
1. The Claude registry reader opens each record through `own_records::read_regular_named`: `O_NOFOLLOW | O_NONBLOCK | O_CLOEXEC`, then the descriptor must be a regular file (`fstat` on the descriptor, not the path) of at most 64 KiB, read with a one byte over-read so a file that grew after the check is still refused. A symlink, a FIFO or an oversized file is a record that did not read: it is counted as malformed by `records()` and is `None` for `record_for`. At most 256 `<pid>.json` names are read in one pass (other files in the directory do not use up the bound). The liveness probe's turn read (`SysHost::turn`, the same files) uses the same reader. Unlike the Codex registry (klatch's own directory), no owner or mode rule is added: Claude Code writes these files under its own umask and the mode it picks is not observed here, and the ticket required that no existing record stop counting as evidence.
2. `ps` is found at a fixed path: the first regular, executable file of `/bin/ps` and `/usr/bin/ps`; a bare name is never accepted and PATH is never searched. With none there is no process table: every lookup is `Unreadable` (unknown, never dead, never live), as when `ps` cannot run. The child runs with a cleared environment, only `TZ=UTC` and `LC_ALL=C` (a fixed `lstart` format; the registry records UTC), with standard input and error closed. `SysHost::procs` (the probe's process tree) uses the same fixed program.
3. One snapshot per walk. The `ProcessTable` trait gains `pin()`, a copy of the table as it is now (default `None`, so made-up tables are unchanged). `PsTable::pin` runs `ps -A -o pid=,ppid=,lstart=,comm=` once, parses it once and answers every lookup from the copy: a pid in it is `Found` with the same ppid, start time and program name as the three per-pid reads gave (`comm` is the rest of the line, so a name with spaces is kept; whitespace is collapsed as before), a pid not in it is `Missing`, a table that could not be read is `Unreadable`. `find_session` and the Codex walk, `unregistered_agent_below`, `find_parent`, `list`, `self_test` and the Codex record write (walk and prune) each pin once, so a walk of any depth costs one `ps`. A single `PsTable::lookup` is one `ps -A` run (was three `ps -p` runs). A pid above the system's pid limit is still `Missing` without running `ps`.
4. Bounds. The run is killed after 5 seconds and gives `Unreadable`; output past 16 MiB (read with a one byte over-read, then the pipe is closed) is `Unreadable`; a non-zero exit, output that is not text, an empty table or a row that does not parse makes the whole table `Unreadable` (a partial table would call a live session dead). A row with no program name is left out, so that pid is `Missing`, as the per-pid read said. The walk keeps its depth bound (64), its never-pid-1 rule and its seen-pid check.
**What is not changed.** Which records count as evidence for any walk, liveness, listing or Codex verification; the `Lookup` meanings (Missing and Unreadable stay different facts, #525); the Codex registry's own owner and mode rules.
