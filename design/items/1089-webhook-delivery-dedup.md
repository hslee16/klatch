Webhook intake drops redelivered events by delivery id (#1089, follow-up to #1058; no schema change; 2026-11-21).
GitHub redelivers an event (a manual redelivery, or after a timeout) and `gh webhook forward` may reconnect and replay; the same `X-GitHub-Delivery` id used to produce a second channel event. `Intake` in `proto/klatch-server/src/webhook.rs` now keeps a bounded set of recent delivery ids (`DELIVERY_IDS`, 1024, oldest forgotten first) and answers a repeat with 200 `duplicate`, queueing nothing.
Order of checks: the signature first (an unsigned request never reads or records an id, so a forger cannot poison the cache), then the id lookup, then the parse. An id is recorded only after the event was translated without error (a notice or an ignored event), so a 400 delivery can be redelivered and succeed. A missing id, an id over 64 characters or one with characters other than ASCII letters, digits and hyphen is not cached and the event is processed as before (GitHub sends a GUID).
Limits: the id header is not covered by the HMAC (only the body is), so a party holding a captured signed body can replay it with a fresh id; replay of a captured signed request remains undefended on loopback. The cache lives in memory and a restart forgets it. Tests: handler unit tests in `webhook_tests.rs` (repeat queued once, distinct and missing ids, unsigned repeat does not poison, failed delivery can be retried, bound and eviction, odd ids not cached).
