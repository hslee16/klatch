The integrator can merge clean PRs without updating their branch, verify main after each merge and revert a red merge through a branch and a PR (#867, step 4 of epic #863; no schema change; 2026-11-20).
Policy change, stated plainly: until now the integrator kept the up-to-date rule (merge main into the PR branch, run the gate, push, wait for the checks of the new head, merge), which costs a re-merge, a gate and a round of checks per PR per merge. The owner's pick of 2026-11-18 replaces it, for those who turn it on: a PR that merges into CURRENT main with no textual conflict is merged as it is, and main is checked after the merge instead. Decision: this is a capability, OFF BY DEFAULT, a mode of `proto/scripts/integrator` (`--merge-without-update`); the up-to-date flow stays the default and is unchanged, and turning the mode on is the human's decision. The klatch binary is untouched: the work is in the helper, with its own `gh` and `git` login.

    Merging. For a queued PR whose `git merge-tree --write-tree` against current `origin/main` reports no conflict at all, the integrator posts `integrating:`, does not merge main into the branch, runs no gate on the branch, pushes nothing, posts `checking:`, waits for green check runs on the PR's CURRENT head sha (never an earlier green), re-checks the merge-tree (main may have moved; a conflict drops the PR with `conflict`) and merges with `gh pr merge --match-head-commit`. A docs-only conflict is not clean and takes the default flow; a code conflict still drops with `conflict`.

    Verifying. The merge commit sha is read from the PR. The signal is the `check_suite` and `workflow_run` events of that sha on main (no PR attached, already routed to the side log by #866) plus a read of that sha's check runs. All green posts nothing. A failed run is red; a cancelled run is not a failure and leaves main unverified. `--verify-gate` also runs the project gate on main at the merge commit and `--verify-bench` the bench (both optional because they take minutes; either failing is red).

    Reverting. Only a red attributed to the merge this run just made (same sha) is acted on; a red check on another sha, or a merge the run did not make, is never reverted. The revert is never a direct update of main: branch `revert-N` from `origin/main`, `git revert -m 1` of the merge commit with a fixed commit message, a plain push of that branch, `gh pr create` with a fixed title and body (no text of the reverted PR, nothing but an integer), a wait for the revert PR's own checks on its current head, the same pinned merge, then main is verified again. Success posts `reverted: #N`. Any failure, or a main still red afterwards, posts `halted: main red after #N`; a main that cannot be verified posts `halted: main not verified after #N`. Either way the claim is released, nothing more is merged and the process exits 5. It never reverts twice and never reverts a revert.

    Words. `reverted: #N` and `halted: main red after #N` or `halted: main not verified after #N` are fixed templates of an integer, in the style of item 864. Klatch does not read them: the fold needs no new word (a merged entry stays merged, `dropped:` ends only active entries), so `CONVENTION_WORDS` and the fold are unchanged, and the words are plain lobby lines. A board line for a halt or a revert is ticketed (#1094). The dry run (`--dry-run --merge-without-update`) prints this plan.

    Limits. The PR's checks cover the PR alone, not the PR combined with the main of the moment; the verification and the revert are what take the place of the up-to-date rule. Verification holds `merge:main` while it waits. A revert can conflict with a later merge by someone else, which halts. After a halt the process must be restarted by the human, who looks first. No bench scenario (the bench drives klatch members, not `gh` or a git remote). Tests: `proto/scripts/test-integrator.sh`, against a fake `gh`, a git wrapper that logs pushes, a fake `klatch` and temp git repositories: a clean merge-tree merges with the branch untouched, a conflict still drops, a green main posts nothing extra, a red main runs the branch push, the PR create and the PR merge in that order and never updates main directly, a failed revert halts with exit 5 and no further merge, a red revert PR is not merged, a still-red main halts, a red check on another sha is not reverted, an unverified or cancelled main halts, the gate and bench flags, the usage error, the dry run, and hostile text that never reaches a word, a command or the revert. Tests were written first and failed (24 failures) before the flag existed.
