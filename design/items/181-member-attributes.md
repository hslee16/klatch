The member model: a stable id with the repository and directory klatch observed, and the default clearance of a new repository (#181, #191; schema 30; 2026-11-18).
**What exists.** A member is a harness session, and its name is the key of every table (the first name a session gets is kept, a second session with the same name gets a suffix from its session id, #170). That already meets "same-named sessions stay distinct" and "a rename keeps one member". **What this adds (R41, R42):** the table `member_attrs(member, member_id, repository, directory, ts)` (schema 30, an existing member has no row until it next acts), written by `ensure_member_attrs` each time a member runs a command: `member_id` is `m-` and the FNV-1a hash of the session id (the member name when there is no session), made once and kept for the member's life; `repository` is the `git:<name>-<hash>` id of the directory, empty outside a repository; `directory` is where the session started. Two sessions in one repository are two members that share a `repository` value, and `Store::members_in_repository` lists them. **The repository id is derived, never typed:** `git_common_dir` reads the files git lays out (a `.git` directory, or a `.git` file saying `gitdir:` whose `commondir` points back at the common directory) and runs no git process, so a worktree shares the id of the repository it was made from, and nothing in a directory can execute at that step. The scope a member works in uses the same derivation, so the two agree (a test). **Zero trust:** the attributes are observations by the host, not authority. A directory can hold a `.git` file naming another repository's git directory, so a member can make its repository value equal another's; therefore no check reads the attributes, and sharing a repository grants no clearance, room or access. Clearance and labels stay as they were (R8, R23). **Left out, and why:** the member name stays the key (the store keys, claims and messages are by name, and a change of key would touch every table; the id is a stable handle beside it, for display and for the repository grouping), and no wire method or command shows the attributes yet (a later change that does needs a row in `proto/AUTHZ-AUDIT.md`). Delivery and claims still use the scope, which a caller may declare; moving them onto the derived repository is not done. **Default clearance of a new repository (#191, open question 39, decided by the human on 2026-11-18):** a repository's first session keeps the lowest clearance (public); nothing above public crosses until clearance is granted. Pinned by `a_first_seen_repository_session_holds_the_lowest_clearance_and_cannot_read_above_it`, which also shows that sharing a repository with a cleared member lifts nothing. No grant process is built; whether a judge in the lobby and in channels (the channel creator as the first judge) should grant clearance is a separate question ticket. **Tests:** `scope/attr_tests.rs` (a hand-made git layout with a worktree, absolute and relative gitdir, two sessions in one repository, a rename, a move, no directory), a real `git worktree` test, store tests for the table and its migration from schema 29. They were written before the code and failed to compile first (the functions did not exist), not on an assertion.
