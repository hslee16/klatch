The integrator stops on TERM even when bash loses the signal (#1099; script only; no schema change; 2026-11-20).
`proto/scripts/test-integrator.sh` failed now and then in the gate with `rc=142`: the integrator did not stop after `kill -TERM`, and the 90 s alarm of the test launcher ended it. The cause is a bug of bash 3.2 (the macOS `/bin/bash`): when a trapped signal lands while the shell is expanding a command substitution, the trap string cannot be parsed (`trap: line 2: unexpected EOF while looking for matching ')'`) and the signal is dropped. A 12-line loop of `$(...)` loses about 0.5% of the TERMs sent at random times; the integrator loop is full of command substitutions, so under load it lost one in about a hundred. The six `claim` lines in the failing log were not a busy loop: every posted word renews the claim.
The integrator now runs its loop in a worker child (`INTEGRATOR_WORKER=1`). The parent runs no command substitution, only `wait`; a TERM, INT or HUP sets a flag, and the parent then sends TERM to the worker once a second until it is gone (after 60 sends it uses `kill -9`). The worker's signal handler is idempotent and ignores a repeated signal once the cleanup has begun, so the resends never cut the release of `merge:main` or the stop of the forwarder short. When the parent is killed with `kill -9` the worker notices at its next loop turn and stops by itself. The exit code is the worker's. `--dry-run` and the filter modes do not use a worker. Waits were already interruptible (the long command runs in the background and is waited for), and no loop busy-waits: the claims in the failing log were renewals, so `INTEGRATOR_REQUEUE_SECS` is unchanged.
Tests: a worker that is told to lose two signals (`INTEGRATOR_TEST_DROP_TERMS=2`, a test knob) still stops after the resends; a TERM during a 40 s `klatch wait` stops it in under 3 s; the worker stops by itself when the parent is killed. The first two do not fail on the old script (the knob does not exist there, and the old script already left a long wait at once): the reproduction is the loop count, 3 failed runs in 320 under 40 CPU spinners before the change. A count after the change under the same load was not made, because the load starved the machine of processes; the supervisor shape (a loop that only waits) lost 0 of 400 random TERMs where the command-substitution loop lost 2 of 400.
`proto/scripts/test-team.sh` had the same kind of race: its wait for the worker's exit marker gave up after 20 s, so on a loaded machine it read the fake `claude`'s files before they existed or were complete (`claude args missing`, `FAIL brief`). The wait is now about 2 minutes and the fake writes its argument file whole (write, then `mv`). The other script tests wired into the gate were read for the same pattern (a file written by a background fake read without a wait); none has it (`test-sweep.sh` only starts `sleep` holders).
