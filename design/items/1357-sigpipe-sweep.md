Shell scripts never pipe into an early-exit consumer under pipefail (#1357; no schema change; 2026-11-22).
Under `set -o pipefail`, `producer | grep -q X` (also `grep -m1`, `head -1`, `head -n 1`, `sed -q`) fails spuriously under CPU load: the consumer exits at its first match, the producer is still writing, dies of SIGPIPE (141), and pipefail fails the whole pipeline. This was fixed script by script (verify-published.sh, test-rollback-rehearsal.sh, test-team.sh #1323) and is now removed from every shell script in the repository. Text held in a variable is fed with a here-string (`grep -qF want <<< "$text"`); a command's output is read to the end (`cmd | grep want > /dev/null`, `cmd | sed -n 1p`), which keeps a failing producer failing the check. Product code is unchanged.

`release/check-sigpipe.sh` is the guard: it fails on any tracked script that sets pipefail and pipes into `grep -q`, `grep -m`, `head -1`, `head -n 1` or `sed -q` (a pipe at the end of a line is read as one line; comments and the text of quoted strings are not code and are skipped, but a pipe inside `$(...)` is code; new untracked scripts are scanned too). A reviewed exception carries `# sigpipe-ok: <reason>` on the same line or the line above. `release/test-check-sigpipe.sh` tests the guard on fixtures and on the repository, and the gate runs both. Workflow run blocks are not scanned; the default `run:` shell on GitHub runners is `bash -e {0}` without pipefail, so only blocks that set pipefail themselves are at risk.
