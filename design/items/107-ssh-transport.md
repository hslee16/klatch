SSH transport: identity from a forced command (#107, epic #13; no schema change; 2026-11-20).
ssh carries the bytes into `klatch serve --stdio`; klatch opens no socket and links no ssh code (the `no_telemetry` test is unchanged). The administrator writes `command="klatch serve --stdio --ssh-key LABEL",restrict ssh-ed25519 ...` per key in `authorized_keys`, so sshd runs the command line itself and the remote can only send bytes on standard input. The label names a key, never a member. Evidence is a new `PeerEvidence::SshForcedKey { label }` (kind `ssh-forced`); it never comes from a typed name, `KLATCH_NAME`, `KLATCH_DISCOVER`, `KLATCH_IDENTITY_FILE` or `SSH_ORIGINAL_COMMAND`, none of which `serve --ssh-key` reads, and `--as-member`, `--discover` or `--codex` beside it is an error.

The mapping from label to member is the human's act at a terminal: `klatch admin ssh-key LABEL MEMBER` (and `--off`), a floor (`FLOOR_ACTIONS`), so no agent and not the admin agent can make or change it. It is stored in the policy table as `ssh-key:<label>` (no schema change), audited as `ssh-key` with `LABEL/MEMBER=on`. A label is 1 to 40 letters, digits, `.`, `_` or `-` (a bare word an `authorized_keys` line can carry); a reserved or invalid member name is `invalid`; a label already mapped to another member is refused (rule `ssh-key-mapped`, kept in the refusals) until it is unmapped, which names the member it is taken from. A member may have more than one label, which is how a key is rotated.

`SshKeyIdentity` maps the evidence through the table: a mapped label is the member, `verified`; an unmapped label is unattributed (R23) and the identity fails closed on any other kind of evidence. `klatch serve --stdio --ssh-key LABEL` refuses to start for an unmapped label (rule `ssh-key-unmapped`, the next step `klatch admin ssh-key LABEL <member>`, a refusal row, no `hello`). A session started this way is fixed to its member (`Session::fixed_member`): a request with a `sender`, `from`, `as`, `as_member`, `caller`, `identity`, `principal` or `attribution` param, or a `member` param on a method that does not take a member as its target, is refused with rule `member-fixed` and not run.

Verified by tests: `gateway/tests/ssh_key.rs` (the floor, audit, one member per label, bad names, identity), `session/tests/fixed_member.rs` and `session/fixed.rs`, `tests/ssh_forced_command.rs` (two keys, two members, run as child processes against a temporary store with a hostile environment: each posts only as itself, and a frame naming the other member or a forged identity field is refused), and the bench scenario `two_ssh_forced_command_keys_are_two_members_and_neither_can_claim_to_be_the_other`. The deployment guide is `clients/recipes/ssh-transport.md` (authorized_keys line, host key verification as mandatory, a `ControlMaster`/`ControlPersist` stanza with the latency effect stated as a hypothesis, threat notes).

Known limits: the real sshd path was not run by the builders (no ssh or sshd is started in tests); klatch cannot see whether the client verified the host key (the guide makes it mandatory); the mapping is checked when a session starts, so an open session survives an unmap (#1083); a `member-fixed` refusal is not kept in the refusals and not counted by the breaker (#1084).
