The dm nudge is an imperative with the exact command, repeats at 6 messages, and also fires at the second need-info round (#1222, #1223; part of #1183; no schema change; 2026-11-21).
The measurement of 2026-11-21 (comments on #1194 and #1183) found that with the nudge reaching wait and read readers, haiku moved to a dm in 3 of 5 runs and sonnet in 3 of 3; in the two haiku runs that stayed, both agents posted their pending lobby reply right after the nudge and never moved. **Wording (#1222):** `domain::move_to_dm_nudge` now says `klatch: you and PEER exchanged N messages in ROOM. Do this now: klatch dm PEER "<text>" (send your next message there, not in ROOM)`. It is still a fixed template over a validated name, a count and the room; no message text. The line still starts `klatch: you and`, so the digest, `wait` and `read` print it in the same place, and the mediator proposal (#1191) is unchanged. **Repeat at 6 (#1222):** `crossing_exchange` now asks for each threshold in `DM_NUDGE_THRESHOLDS` (4, then 6): a run that reached a threshold whose crossing message (the first message of the peer at or past that place of the run) was handed over now. A pair still exchanging with no dm when it reaches 6 messages is shown the line once more, once per threshold, so at most two lines per unbroken run; a handover that carries both crossings prints one line. Nothing is stored: the rule is derived from the room's newest `DM_NUDGE_WINDOW` (64) messages and the messages handed over, as before. **Second need-info round (#1223):** `domain::clarification_round` reads the structured words only, through `parse_clarification` (`need-info #N:` at the start of a body, `info #N:`, never prose): when the peer posted a `need-info #N:`, the caller answered `info #N:`, and the peer's second `need-info #N:` is among the messages handed over now, the caller gets the same line (the count is the messages the two sent from the first need-info through the second, 3 for the plain case). It is the pair's first such second round in the window, so a third round does not trigger it again (the 4-message crossing may, as it does for any run), and an info from a third member or a need-info for another ask does not count. `domain::dm_nudge` is the one entry point for both rules; the gateway digest (`long_exchange`) and the `wait` and `read` commands (`dm_help_lines`) both call it, so the same room, no-dm and three-member checks apply and the hook digest, `wait` and `read` all deliver it, once per handover as in #1209. **Once per pair per room:** held by the handover, not by a record: a message is handed over once, so each trigger shows once; the pair can see the line at the 2nd round, at 4 and at 6 if it has not moved, which is the bounded repeat the ticket asks for. **Bounds:** the added line is one fixed line per room in the digest and a trailing line after the capped rows in `wait` and `read`; the digest and wait/read byte bounds and every other line are unchanged. **Why no schema change:** every input is a message already in the room. **Metric (#1222):** `experiments/dm-adoption/metric.py` counted nudge lines in hook events only and read 0 for agents that met the nudge through `wait` or `read`. It now also reads `tool_result` blocks of the stream-json (a string or text blocks) and reports `hook_nudge_lines`, `tool_result_nudge_lines` and their sum `nudge_lines`; a line counts only at the start of a line, in a hook response or a tool result, never in model text, and the earlier wording still counts. **Duplicates (#1211):** unchanged in kind. A message the hook showed first is still handed again by a later `wait` or `read`, and the client cannot see the hook position, so any of the new triggers can print twice in that order too; the second-round trigger and the 6-message repeat add two more lines that can duplicate that way, and nothing makes the existing duplicate better. **Limits:** the clarification trigger needs a room of three or more members, like the long-exchange one; a need-info and info pair split over two windows of 64 messages is not seen. No operation changes, so the audit table is unchanged.
