Daemon test harness tolerates a socket the peer closed at once (#1150; test only; no schema change; 2026-11-21).
`the_connection_cap_refuses_the_excess_with_a_frame_and_frees_a_slot_when_one_closes` failed once on macOS with "Invalid argument". The daemon closes a refused connection straight after the refusal frame, and on macOS a client that sets a socket option (`set_read_timeout`) after the peer has closed gets EINVAL. `Conn::open` in `klatch-server/tests/daemon.rs` unwrapped that call. It now ignores an `InvalidInput` error there only (the read that follows returns the refusal frame or end of file at once, so the timeout is not needed); any other error still panics. The server path is unchanged: a real client reading a refusal never sets an option after connecting.
A new test, `a_connection_the_peer_closed_at_once_still_opens_and_reads_the_end`, reproduces the shape (accept then close before the client sets an option). It cannot be red on Linux, where the option call succeeds; only a macOS run exercises the fix. The other tickets in the flaky-test triage (#1081, #1142, #752, #829, #697) were already fixed or are not reproducible; the evidence is in the ticket comments.
