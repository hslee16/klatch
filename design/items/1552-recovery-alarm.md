Failed recoveries through the file limit count toward the proof failure alarm (#1552; no schema change; 2026-11-25).
`admin recover` and `admin restore` of a store that cannot be read are limited by a file beside the store (#1281), because the limit of #1233 lives in the store. Before this item those attempts wrote no `proof-failed` row, so a program guessing the recovery code that way was invisible to the alarm of #1310. Now `filelimit::settle`, which runs when the store opens again after a successful recovery, writes one `proof-failed` row on the target `recovery` for every attempt in the file but the last (the last one is the approved one), each stamped with the time of its own attempt, through `alarm::failed`: the same transaction, the same census and the same crossing rule as a wrong passphrase. The detail is the fixed text `failures=1 via=file-limit`: no terminal label, no code, nothing typed, no verifier. The census query is unchanged (same capped read under the write lock, still at most 2 x 51 index entries; nothing was re-measured because no query or index changed, the 0.25 ms at 1,000,000 rows of #1310 holds), and the alarm row is still written only by the proof path.

One threshold, one alarm, one counter. The owner decided N=50 for passphrase failures and the code shows no reason to split: both are guesses at an admin credential, the recovery code is the stronger secret (so a wrong guess is no more dangerous per attempt), the doctor warning already says "wrong admin passphrases or recovery codes", and the census already counts the target `recovery` for wrong codes typed to `reset-passphrase`. A second counter would need a second constant, a second doctor line and a second row, and would let a mixed attack stay under both lines (30 passphrase guesses plus 30 recovery guesses is 60 guesses and should alarm). The file limit's own schedule (3 free, then 30 to 900 seconds) is per store, not per terminal, so it is stricter than the passphrase limit: 3 free attempts, one wait of 930 seconds and then waits of 900 seconds allow 50 attempts in about 10.8 hours. That is a rate the alarm can catch inside its 24 hours, so the line stays 50.

Known limits, all because the store is unreadable while the guessing happens. The rows appear only when a recovery succeeds and the store opens, so a run of failures that never succeeds is never counted (the attempts stay in the file only; `klatch doctor` does not read it); when a recovery does succeed and the store opens, the rows are written with their real times and the doctor, which counts only the 24 hours before it runs, shows what falls in that window; the alarm row is stamped with the attempt that crossed. An attempt that was approved but whose command then failed (for example a wrong typed confirmation) is charged and not settled, so at the next settlement it is counted as a failure: a conservative over-count of an alarm that locks nothing. A settlement writes at most `CEILING` of the newest failure rows (more add nothing to an alarm that fires at the ceiling); the `recovery-attempts` summary row still gives the true number of attempts. These rows carry no terminal label, so `terminals=` in the alarm detail counts only the labelled passphrase failures. A file that is damaged reads each bad line as an attempt made now, as before.

Where a failed recovery is recorded: (1) `proof/mod.rs` `reset` (the recovery code typed for `reset-passphrase`), a `proof-failed` row on `recovery` with `failures=N terminal=LABEL` (#1310, unchanged); (2) `proof/filelimit.rs` `settle`, the new `proof-failed` rows with `failures=1 via=file-limit`, plus the existing `recovery-attempts` row with a count; (3) the attempts file itself, which holds unix times only. `recovery_proof_for_restore` and `recovery_proof_for_recover` write nothing else and log nothing. For `restore` the typed code is read into a zeroizing string and compared in constant time; for `recover` the code is a command-line argument (as it always was) and counts by trying to open the store with the key it makes; in neither case does it reach a row, a log or the attempts file, which holds times only.

Tests: `proof/alarm_recovery_tests.rs` (50 failed recoveries raise the alarm exactly once, 49 do not, a success is not counted, recovery failures add up with passphrase failures, attempts outside the window are not counted, at most a ceiling of rows per settlement, the rows carry counts only and no code or terminal label, a damaged file still settles), the source scan of `alarm_tests.rs` (the proof path files only name the action) and the golden of `audit_rows_of_reset_and_recovery`, which now shows the one failed attempt before the `recovery-attempts` summary.

Hardening after the independent review. (1) The attempts file is plain and anything running as the owner can write it, so a time outside the last 24 hours, or more than 5 minutes ahead, is dropped (never clamped) and the `recovery-attempts` summary says how many were dropped; a time up to 5 minutes ahead is clock skew and reads as now. Without this, a file of far-future times would write rows that count in the doctor for a year and keep the count above 50, so a real crossing at exactly 50 never fired. (2) The census has an upper bound, `ts <= at`, on the failure path and in the doctor's read: a back-dated row used to count every later row (30 passphrase failures plus 21 rows stamped 40 hours earlier raised an alarm the doctor did not show). It is the same index range with one more bound, so the cost is unchanged: 0.14 ms a query in a debug build over 1,000,000 rows in the window, capped at 51. (3) Settlement is at most once: the file is renamed to `<store>.recovery-fails.settling` and removed before any row is written, and if either step fails nothing is written; an unwritable directory settles zero rows. A crash after the removal loses the counts not yet written and never counts one twice, which is the chosen side of the trade for an alarm. (4) The approved attempt is the last line of the file, whatever its time says (a clock that went back), the newest 50 failures are the ones written, a file that is not UTF-8 counts the lines it has, and the smallest possible time no longer overflows the window arithmetic.
