Failed recoveries through the file limit count toward the proof failure alarm (#1552; no schema change; 2026-11-25).
`admin recover` and `admin restore` of a store that cannot be read are limited by a file beside the store (#1281), because the limit of #1233 lives in the store. Before this item those attempts wrote no `proof-failed` row, so a program guessing the recovery code that way was invisible to the alarm of #1310. Now `filelimit::settle`, which runs when the store opens again after a successful recovery, writes one `proof-failed` row on the target `recovery` for every attempt in the file but the last (the last one is the approved one), each stamped with the time of its own attempt, through `alarm::failed`: the same transaction, the same census and the same crossing rule as a wrong passphrase. The detail is the fixed text `failures=1 via=file-limit`: no terminal label, no code, nothing typed, no verifier. The census query is unchanged (same capped read under the write lock, still at most 2 x 51 index entries; nothing was re-measured because no query or index changed, the 0.25 ms at 1,000,000 rows of #1310 holds), and the alarm row is still written only by the proof path.

One threshold, one alarm, one counter. The owner decided N=50 for passphrase failures and the code shows no reason to split: both are guesses at an admin credential, the recovery code is the stronger secret (so a wrong guess is no more dangerous per attempt), the doctor warning already says "wrong admin passphrases or recovery codes", and the census already counts the target `recovery` for wrong codes typed to `reset-passphrase`. A second counter would need a second constant, a second doctor line and a second row, and would let a mixed attack stay under both lines (30 passphrase guesses plus 30 recovery guesses is 60 guesses and should alarm). The file limit's own schedule (3 free, then 30 to 900 seconds) is per store, not per terminal, so it is stricter than the passphrase limit and 50 failures through it take at least a day; that is a reason the alarm will rarely fire from this path alone, not a reason for a lower line.

Known limits, all because the store is unreadable while the guessing happens. The rows appear only when a recovery succeeds and the store opens, so a run of failures that never succeeds is not counted until it does (the file holds them, and the owner can read it); the alarm and the doctor warning then show them at once, stamped with the real times, and the alarm row is stamped with the attempt that crossed. An attempt that was approved but whose command then failed (for example a wrong typed confirmation) is charged and not settled, so at the next settlement it is counted as a failure: a conservative over-count of an alarm that locks nothing. A settlement writes at most `CEILING` of the newest failure rows (more add nothing to an alarm that fires at the ceiling); the `recovery-attempts` summary row still gives the true number of attempts. These rows carry no terminal label, so `terminals=` in the alarm detail counts only the labelled passphrase failures. A file that is damaged reads each bad line as an attempt made now, as before.

Where a failed recovery is recorded: (1) `proof/mod.rs` `reset` (the recovery code typed for `reset-passphrase`), a `proof-failed` row on `recovery` with `failures=N terminal=LABEL` (#1310, unchanged); (2) `proof/filelimit.rs` `settle`, the new `proof-failed` rows with `failures=1 via=file-limit`, plus the existing `recovery-attempts` row with a count; (3) the attempts file itself, which holds unix times only. `recovery_proof_for_restore` and `recovery_proof_for_recover` write nothing else and log nothing. The typed code is read into a zeroizing string and compared in constant time; it reaches no row, no log and no file.
