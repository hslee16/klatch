The 5 second first Keychain read is now a one-time migration cost, bounded and unavoidable without signing (#372; no code change in behaviour; 2026-11-18).
The ticket measured 4.5 and 5.3 seconds for the first Keychain read of a newly built unsigned binary (later reads 17 to 30 ms). That was written before #480 (item 28), which moved macOS key custody to a 0600 key file (`FileFirst`). **What is true now:** (1) a key the file already holds never reaches the Keychain (a new test, `file_first_never_asks_the_older_keystore_for_a_key_the_file_holds`, whose older keystore panics if asked; a mutant that asks the Keychain first is caught); so after the first successful read of an install's key the Keychain is never touched again, by any rebuild or deploy, and a rebuilt binary pays nothing; (2) a new install, with no Keychain item, asks the Keychain once for an item that does not exist, which is a miss without any access-control check: measured 10 ms (`security find-generic-password` for a name that is not there, three runs, 0.01 s each; the live item was not touched); (3) only a store whose key is still in the Keychain from before #480 reads the item, once, copies it into the file and is done. That read is the one that waits for the access-control prompt (the item's partition list names the code hash of the binary that stored it, and a different unsigned binary is a stranger until the login password is given), and it is bounded by `READ_LIMIT` (5 seconds), after which the command fails with the reason instead of hanging. **Does the hook timeout cover it?** klatch sets an explicit `timeout` only on the wake hook (3600 s, `init.rs`); every other hook runs under the harness default, which is longer than the 5 second limit, so a hook that hits the limit fails with the message and does not get killed first. I did not re-read the harness default in this change. **Is there a cheaper path that keeps custody?** None was found. Reading the legacy item through `/usr/bin/security` instead of the framework does not avoid the prompt for an item an unsigned program created (the partition list is the program's, not `apple-tool`), and widening the item's access list needs the login password too (item 28). Signing with a stable identity removes it for later releases (a `teamid:` partition list), which is #371 and the human's decision #424; ad hoc signing does not, since its identity is still the code hash. **Not measured:** the prompt case itself, because it raises a dialog on the developer's machine (item 28 dropped that test for the same reason) and the live item must not be touched. The ticket's two measurements stand as the figure. **Result:** the claim "every rebuild and every deploy pays it once" is no longer true; only the migration of an old install pays, once. #372 stays open for the signing question (#424) only.
