Jev as judge and facilitator advisor: its own integration, off by default, advice to a deterministic guard (#898, part of #180 and #10; no schema change, no new wire method or command; 2026-11-18).
What Jev is (vendor docs, and the live check of 2026-11-19 on #911, see below): a decision model, not a text generator. One request is `POST /v1/systemone` with `{model, state, questions}`, `questions` a dictionary keyed by question id; the reply is `{model, answers, usage}` with `answers` keyed by question id, and carries no reasoning. Question kinds: `choice` (returns choice, probabilities, confidence), `noul` (is a statement true, 0 to 1), `score` (rubric; not used, it is not cheap to make safe), `box` (images; not used).

Where it plugs in. It is its own module (`klatch::jev`, feature `client`, no new dependency; it uses serde_json only) and is kept apart from the Claude-session facilitator of #190 so neither shapes the other. Two adapters, one per consumer. (1) The judge: `JevJudge` implements the existing `HostedTransport` of #53, so it sits under `HostedJudge` and the label gate there is unchanged (`label_below_ceiling` is that gate, now a shared function used by both paths). (2) The facilitator and router: `pick` is a pure helper that takes the rules router's candidates and decision and a Jev choice answer. The transport to the network is the `JevTransport` trait; the real HTTP transport is #871 and no HTTP client is added here.

Wire types and strict parsing (rewritten for #911 to the verified shapes). The request is `{model, state, questions}`; a choice question is `{type: "choice", instructions, criteria: {option: description}}` and a noul question is `{type: "noul", instructions}`. `JevConfig` pins the model in the one form the API accepts, `jev-X.Y.Z` with three numeric parts (the bare `1.14.0` is refused by the API with HTTP 400; `latest`, `jev-latest`, `jev-preview` and anything else is refused by us) and a confidence threshold in (0, 1]; there is no default, so Jev is off until both are chosen, and the hosted judge stays off until `HostedConfig.enabled` is set. A reply is accepted only when it is an object with exactly `model` (which must equal the pinned model), `answers` and optionally `usage` (an object, otherwise ignored; its inner shape was not recorded). `answers` has exactly the asked ids, each answer exactly the shape of its kind: a choice answer has exactly `type` ("choice"), `choice`, `confidence`, `probabilities`; the choice was one offered; the probabilities cover exactly the choices, each finite and within 0..1, summing to one within 0.01; the chosen one is the most probable; the confidence is within 0..1. A noul answer is exactly `{type: "noul", noul}` with `noul` within 0..1. Any other shape, an extra field, a missing key or a string where a number belongs is an error. A request with a repeated question id is refused before any call.

Errors. The transport reports `JevTransportError::Network` (no detail) or `Status {status, body}`; its Debug withholds the body. `http_error` turns that into `JevError::Http {status, error_type}`: only the status is reported, plus `error_type` for status 400, 401 and 403 when the body is `{"detail": {"error_type": ...}}` and the value is one of the two seen (`authentication_error`, `api_usage_error`); the body of any other status is never read, and in particular a 422 body, which echoes the whole request including the message text, is never read, logged, audited or shown. Tests prove no error value, Debug output or judge error text holds the state text or the key.

The judge. The message text goes in `state` only (`{"message": text}`); the question wording is fixed, so a message cannot add or change a question. `allow`, `redact` and `deny` map to the verdicts only when both the confidence and the chosen probability reach the threshold; otherwise `Defer`. Jev returns no text, so a redaction carries a fixed placeholder and never anything Jev wrote or the original; a deny carries a fixed reason. A missing key, a transport error, a refused reply: `Defer`, as for every `HostedJudge` failure.

The facilitator path. A choice answer is advice among candidates the rules and the guard already allow. `pick(candidates, rules_decision, answer, threshold)` takes Jev's choice only when its confidence and its own probability both reach the threshold, and then only when it is `none` (narrow to nothing) or one of the candidates. A name outside the candidates is ignored, so Jev can never name a member or room the guard would refuse; below the threshold or on any doubt the rules router's decision stands (the cascade of RESEARCH-NOTES). It can route among allowed candidates or narrow; it cannot widen anything, because the candidate list is built by the guard before Jev is asked and `pick` returns only a member of it.

Label gate for structured facts. Member names, room names and claim paths leave the machine when sent, so they are gated exactly like text: each fact carries the label it was observed under and is sent only when that label and the ceiling are in the chain and the label is strictly below the ceiling (`route_question`). If the sender or the topic is gated there is no question and no call; a gated candidate is left out of the question (which only narrows), and `pick` is given only the candidates actually offered; with none left there is no call. A candidate named `none` is dropped (it is the reserved choice). An unlabelled fact is never sent. Wiring this into the facilitator loop needs a per-fact label source (members and claims do not carry one yet); until it exists nothing calls `route_question` outside tests, which is why nothing is wired in this item.

Key handling. The key is read from the environment variable `TYPESAFE_API_KEY` only, at each call (never cached), into an `ApiKey` whose Debug and Display print `<redacted>`. It is never stored in the store, a config, the audit or a log, and is never in a request body. A transport error carries no key, state or body into a `JevError`. A blank or unset variable means no call is made.

Jev text can influence its verdict (RESEARCH-NOTES 13.3): what it reads is data, and its answer is advice to the deterministic guard (the label gate, the candidate list, the threshold), never authority. It can defer, hold, route or narrow; it cannot widen what the guard allows.

Live check of 2026-11-19 (ticket comment: https://github.com/hslee16/klatch/issues/911, last comment; made-up message only, key from the human's Doppler config, never printed). Verified:
- `GET /v1/models` with a bearer key returns 200 and lists only `jev-latest` and `jev-preview`; `POST /v1/systemone` with `Authorization: Bearer <key>` works.
- `jev-latest` resolved to `jev-1.14.0` on that day (the reply says so); pins `jev-1.14.0` and `jev-1.13.0` work; the bare `1.14.0` is HTTP 400 `Unknown model`; `model` is required (HTTP 422 without it).
- `state` accepts a JSON object (`{"message": "..."}`) as well as a string.
- Option names with dashes (`topic-auth`) and the reserved word `none` work as choice options.
- Choice probabilities sum to 1 and the chosen choice is the most probable; `confidence` is a separate number (0.98 against probability 0.99).
- The request and reply shapes listed under "Wire types" above, including `type` on every answer and `noul` as the noul answer's field name. The adapter of #912 guessed these and was wrong on the question list, the model form, the reply envelope and the noul field name; all are fixed and recorded as test fixtures (synthetic text only).
- Error shapes: bad or missing key is 401/403 `{"detail": {"error_type": "authentication_error", "message": ...}}`; unknown model is 400 `{"detail": {"error_type": "api_usage_error", ...}}`; a malformed request is 422 with a FastAPI-style `detail` list whose `input` echoes the whole request body. None of the replies seen echoed the key.
