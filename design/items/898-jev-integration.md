Jev as judge and facilitator advisor: its own integration covering the whole documented API (everything but the real HTTP transport), off by default, advice to a deterministic guard (#898, part of #180 and #10; no schema change, no new wire method or command; 2026-11-18).
What Jev is (vendor docs at docs.typesafe.ai, saved and read for this item, and the live check of 2026-11-19 on #911): a decision model, not a text generator. One request is `POST /v1/systemone` with `{model, state, questions}` and optionally `assets`, `questions` a dictionary keyed by question id; the reply is `{model, answers, usage}` with `answers` keyed by question id, and carries no reasoning. Four question kinds, all implemented: `choice` (choice, probabilities, confidence), `score` (an ordered rubric of 2 to 10 levels, the API takes 1 to 10; score, confidence, legend, probabilities), `noul` (is a statement true, 0 to 1, no confidence) and `box` (an image question; four edges as fractions of width and height, confidence or null; needs Jev 1.14).

Where it plugs in. It is its own module (`klatch::jev`, feature `client`, no new dependency; serde_json only) split by concern: `request` (questions, entries, the label gate, the request rules), `image`, `answer`, `error`, `retry`, `models`, `decision`, `transport` (the seam) and `fake` (the test transport and the recorded fixtures). It is kept apart from the Claude-session facilitator of #190 so neither shapes the other. Two adapters, one per consumer. (1) The judge: `JevJudge` implements the existing `HostedTransport` of #53, so it sits under `HostedJudge` and the label gate there is unchanged (`label_below_ceiling` is that gate, a shared function used by both paths). (2) The facilitator and router: `pick` and `pick_screened` are pure helpers over the rules router's candidates and decision and a Jev answer. The seam to the network is the `JevTransport` trait (`send(key, &JevRequest)`, where a request is a method, a path, an images flag and an optional body); the real HTTP transport is part B (#871) and no HTTP client is added here. `FakeTransport` replays recorded fixtures (the live shapes of #911 and the documented shapes for what was not seen live, synthetic text only), injects statuses and retry headers, and records every request and the key it was given.

`JevConfig` pins the model in the one form the API accepts, `jev-X.Y.Z` with three numeric parts (the bare `1.14.0` is refused by the API with HTTP 400; `latest`, `jev-latest`, `jev-preview` and anything else is refused by us, and a name that `GET /v1/models` lists never changes that) and a confidence threshold in (0, 1]; there is no default, so Jev is off until both are chosen, and the hosted judge stays off until `HostedConfig.enabled` is set. A client starts with a closed gate and no retries; `with_gate` and `with_retry` open them.

Request building. `build_request` takes the model, a state, the questions, a `Gate` and `Limits` and returns the body to send or a typed refusal, before any key is read or anything is sent. The state is an `Entry`: a string, a number, a flag, null, an image, a list, an object, or a sentence (text with image references inside it). Instructions and criteria are entries too, so structured instructions, structured choice options, score levels and noul `true` and `false` criteria (primitives__advanced.md) all work; choice takes 1 to 255 options with unique non-empty names (names with dashes and `none` work), score takes 2 to 10 levels, noul criteria are optional, box takes no criteria. The documented rules (api__errors.md) are checked locally: body at most 32 MiB, UTF-8 JSON that never starts with a byte order mark, nesting at most 64 levels counted separately in each of state, instructions and criteria, finite numbers only (an integer too large for 64 bits is refused, not rounded: send it as a string), and a question id repeated or empty. The model context limit (models.md) is bounded by configuration, not by the API: the live check saw 100,000 characters accepted (18,799 tokens) and 500,000 refused with 400 `max_tokens_exceeded`, and the context is 64k tokens per request and 32k per question, so `Limits` bounds the characters of every string and key in a request at 40,000 by default (a configuration may raise it to at most 100,000, never above what was seen accepted). The long-context header is never sent. Compression: none. gzip and zstd Content-Encoding need a dependency the client feature does not have, and they raise no limit (the 32 MiB applies compressed and decompressed), so bodies go uncompressed and #916 holds the decision.

Images (images.md). `Image::from_bytes` accepts a PNG or a JPEG only (the format is told from the bytes, not from a name), reads the size from the header and refuses what the API would refuse: a file over 16 MiB, a side under 280 or over 1568 pixels, fewer than 78,400 or more than 2,458,624 pixels, an animated PNG (`acTL`), a cut-short file. Nothing is decoded and no image is resized; the API stays the one that decodes. An image goes in `assets` as `{type: image, format, data_base64}` under a reference that is written where the image belongs (a whole string value, or inside a sentence), in the state, in instructions or in criteria; object keys are never replaced, so an option is given an image through its description. References are `klatch-image-NNNN-end` (fixed width, so none is a prefix of another), and any text, key or id that contains `klatch-image-` is refused so a reference cannot match by chance. The same image used twice is one asset and two uses; every asset is referenced by construction; a box question with no image is refused; an image or a box question turns on `TypeSafe-Danger-Zone-Images: true`. `Limits` also bounds distinct images (4) and total uses (8), and the expanded size counts every use of every image twice (processing re-encodes and can enlarge it): all three are chosen numbers, not documented ones. Multipart upload, which the docs prefer because base64 is a third larger, is a body encoding for the transport and is #915. Images and box are marked by the vendor as not production ready; they stay opt in by construction (nothing in klatch sends an image today).

Strict parsing. A reply is accepted only when it is an object with exactly `model` (which must equal the pinned model), `answers` and optionally `usage` (an object; the two token counts are read when they are non-negative integers and are otherwise ignored; nothing depends on them). `answers` has exactly the asked ids, each exactly the shape of its kind. Choice: `type`, `choice`, `confidence`, `probabilities`; the choice was offered, the probabilities cover exactly the choices, each finite and within 0..1, summing to one within 0.01, the chosen one the most probable, the confidence within 0..1. Noul: exactly `{type, noul}` with `noul` within 0..1. Score: exactly `type`, `score` (within 0 and levels minus one), `confidence`, `legend` (keys 0 to n-1 exactly, the values kept but untrusted and never shown by Debug, since they echo the criteria) and `probabilities` (keys 0 to n-1, summing to one). Box: exactly `type`, `box` (exactly top, bottom, left, right within 0..1 with left before right and top before bottom) and `confidence` (a number within 0..1 or null, present). Any other shape, an extra field, a missing key or a string where a number belongs is an error. The documented score formula and `score` as the probability weighted average are not cross-checked, because probabilities come back rounded and a live false refusal would only cause outages.

Errors. The transport reports `JevTransportError::Network` (no detail) or `Status {status, body, headers}` (the `retry-after` and `retry-after-ms` values as sent); its Debug withholds the body. `http_error` turns that into a typed `JevError`: `BadRequest` (400), `ContextExceeded` (400 with `max_tokens_exceeded`), `Unauthorized` (401), `Forbidden` (403, seen live for a bad key), `PayloadTooLarge` (413), `UnsupportedMediaType` (415), `Unprocessable` (422), `RateLimited` (429), `Overloaded` (529), `Http {status}` for any other status, plus `NoKey`, `Refused(RequestError)` (the local refusals; nothing was sent), `Unreachable` and `Malformed`. A variant holds the status and at most the `error_type` (one of `authentication_error`, `api_usage_error`, `max_tokens_exceeded`), which is read only from the body of a 400, 401 or 403 and only when the body is `{"detail": {"error_type": ...}}`; no other body is ever read, and in particular a 422 body, which echoes the request including the message text, is never read, logged, audited or shown. Tests drive every status through the fake with a body that echoes the message and the key and prove no error value, Debug output or judge error text holds either.

Retries (`retry` module, mirroring sdk__python__api__retries.md). A pure policy with the SDK defaults: 2 retries, a first delay of 0.5 s doubling to at most 5 s, a quarter of each delay randomly subtracted, `retry-after-ms` then `retry-after` (seconds, decimals allowed; an HTTP date is not supported and falls back to the backoff) honoured, and a 30 s budget for the whole call including delays: a retry whose delay would reach the budget is not made. It is narrower than the SDK on purpose: only 429 and 529 are retried (api__errors.md: back off and retry); the SDK also retries 408, every 5xx and connection errors, and this does not, because an unclear failure of a call that carries message text is better surfaced than repeated. It never retries 400 (so never `max_tokens_exceeded`), 401, 403, 413, 415 or 422. The clock, the sleeper and the jitter source are injected traits (`Clock`, `Sleeper`, `Jitter`), so tests run instantly and deterministically; `SystemClock`, `ThreadSleeper` and `NoJitter` are the std implementations and a random jitter source comes with the real transport. The judge turns an exhausted retry into `Defer` like any other failure.

Models. `GET /v1/models` is typed (`ModelList` of name, description, release date, parsed strictly). `JevClient::check_key` is a cheap key check (a parseable 200 means the key works; a bad key is a typed 401) and `check_model` says whether the pinned model is listed. It is `NotListed` for a versioned id today, which is normal (models.md: versioned ids are accepted whether or not they are listed; the list holds the aliases), so what proves the pinned model is that every reply's `model` must equal it.

Confidence and probability (confidence.md, patterns__confidence-routing.md, patterns__noul-screen.md). Confidence is how concentrated the distribution is (choice: (p_max - 1/n) / (1 - 1/n); noul: none, `|2p - 1|` as a stand in; score: distance weighted from the most likely level); the probability of the option acted on is the chance it is right, and is what a threshold belongs on. For a fixed number of options confidence is a function of the top probability and is never above it. What changed from the first adapter (#912), which required both numbers to reach the threshold for every outcome: an outcome that only holds something back (a `deny`, a `redact`, a `none` route) is now taken on the probability alone at the operator's threshold, and an outcome that lets something through (an `allow`, a route to a candidate) still needs both, so the widening outcomes are exactly as strict as before. The guard-first rule is unchanged: a name outside the candidates is never taken, a failure or doubt leaves the rules decision, and nothing here can widen what the guard allows. Pure helpers exist for the documented formulas, the top to second ratio, a score's settled test (confidence first, 0.5 as the documented example floor) and the probability mass of a range of levels (for two split levels, which confidence hides). The noul screen is `NoulThresholds` (documented starting points: above 0.7 a yes, below 0.3 a no, the band between its own outcome) with `pick_screened`: a clear no narrows to nothing, unsure leaves the rules decision, a clear yes lets the pick run; the screen and the pick are asked in one request (speculative fan-out, one read of the state). That is the only documented pattern that touches the facilitator path; composite scoring and probability routing are not used. The thresholds are documented starting points, not validated on klatch data (#918), and the helpers are not yet called by the facilitator loop (#917).

The judge. The message text goes in `state` only (`{"message": text}`, as text the hosted judge already gated); the question wording is fixed, so a message cannot add or change a question. `judge_verdict` maps `allow`, `redact` and `deny` as under Confidence; anything else is `Defer`. Jev returns no text, so a redaction carries a fixed placeholder and never anything Jev wrote or the original; a deny carries a fixed reason. A missing key, a refused request (a message over the text bound is never sent), a transport error, a refused reply: `Defer`, as for every `HostedJudge` failure.

The facilitator path. A choice answer is advice among candidates the rules and the guard already allow. `pick(candidates, rules_decision, answer, threshold)` takes a `none` answer (narrow to nothing) when the probability reaches the threshold, and a candidate only when both numbers reach it; a name outside the candidates is ignored, so Jev can never name a member or room the guard would refuse; below the threshold or on any doubt the rules router's decision stands (the cascade of RESEARCH-NOTES). It can route among allowed candidates or narrow; it cannot widen anything, because the candidate list is built by the guard before Jev is asked and `pick` returns only a member of it.

Label gate for everything sent. Message text, member names, room names, claim paths, numbers, flags, object keys, choice option names and images all leave the machine when sent, so each is either klatch's own fixed wording or data carrying the label it was observed under, and `build_request` sends it only when that label and the ceiling are in the chain and the label is strictly below the ceiling (the one rule of #872). Any labelled leaf, key or image at or above the ceiling, with an unknown label, or with no ceiling set refuses the whole request (fail closed; nothing is sent, the key is not even read). An unlabelled fact has no way to be built. A client starts with a closed gate, so labelled data never leaves until `with_gate` is given the chain and the ceiling. `route_question` filters candidates by the same rule and `pick` is given only what was offered; the client's gate checks the labels again, so a question built under a higher ceiling is refused by a lower gate. `Entry` and `Key` Debug print nothing of their content. Wiring the facilitator loop needs a per-fact label source (members and claims do not carry one yet), so nothing calls `route_question` outside tests (#917).

Key handling. The key is read from the environment variable `TYPESAFE_API_KEY` only, at each call (never cached), into an `ApiKey` whose Debug and Display print `<redacted>`. It is never stored in the store, a config, the audit or a log, and is never in a request body. A transport error carries no key, state or body into a `JevError`. A blank or unset variable means no call is made.

Jev text can influence its verdict (RESEARCH-NOTES 13.3): what it reads is data, and its answer is advice to the deterministic guard (the label gate, the candidate list, the threshold), never authority. It can defer, hold, route or narrow; it cannot widen what the guard allows.

Live check of 2026-11-19 (ticket comments on #911; made-up message only, key from the human's Doppler config, never printed). Verified:
- `GET /v1/models` with a bearer key returns 200 and lists only `jev-latest` and `jev-preview`; `POST /v1/systemone` with `Authorization: Bearer <key>` works.
- `jev-latest` resolved to `jev-1.14.0` on that day (the reply says so); pins `jev-1.14.0` and `jev-1.13.0` work; the bare `1.14.0` is HTTP 400 `Unknown model`; `model` is required (HTTP 422 without it).
- `state` accepts a JSON object as well as a string. Option names with dashes and the reserved word `none` work as choice options.
- Choice probabilities sum to 1 and the chosen choice is the most probable; `confidence` is a separate number (0.98 against probability 0.99). The request and reply shapes of choice and noul, including `type` on every answer and `noul` as the noul answer's field name, are recorded as test fixtures (`fake::fixtures`, synthetic text only).
- State size: 1,000, 10,000 and 100,000 characters returned 200 (100,000 characters is 18,799 input tokens); 500,000 characters returned 400 `{"detail":{"error_type":"max_tokens_exceeded"}}` with no message. The limit is the context length, not a character count.
- Rate limit: 40 rapid sequential tiny requests all returned 200 with no rate-limit headers, so the 429 shape was not triggered.
- Error shapes: bad or missing key is 401 or 403 `{"detail": {"error_type": "authentication_error", ...}}`; unknown model and unknown question type are 400 `{"detail": {"error_type": "api_usage_error", ...}}`; an empty `questions` and invalid JSON are 422 with a FastAPI style `detail` list whose `input` echoes part of the request. The key text appeared in no reply body, header or error in any call.

Verified from the documentation only, not seen live (tracked on #911 and #918): the score and box request and reply shapes and the images header; images in state, instructions and criteria, the image limits and the 2x expanded-size estimate; the 429 and 529 reply bodies and whether `Retry-After` or `retry-after-ms` is sent; the exact `usage` shape (parsed leniently); the token cost of an image; the real token cost of the 40,000 character default for non-Latin text; and a sensible confidence threshold. Not in part A, by decision: the real HTTP transport (#871), multipart image upload (#915), request compression (#916), and wiring the facilitator helpers (#917). Part B, below, brings the transport and multipart; compression and the facilitator wiring stay open.

Part B: the real HTTPS transport (#871, #915). It lives in `src/jev/http.rs` behind the cargo feature `jev-http`, which is off by default and is not part of `cli` or `client`, so the shipped binary, the wheels and the npm package do not link an HTTP client. The client is `ureq` 3 with only its `rustls` feature (rustls with the ring provider and the bundled web PKI roots; gzip, proxy, cookies, json, the platform verifier and native-tls are all off). Blocking, no async runtime, no OpenSSL. The alternatives were `reqwest` (blocking mode needs tokio, hyper and more), a hand written HTTP/1.1 client over `rustls` alone (fewer crates, but our own response parser on a path that carries the key and the message text; rejected), and `ureq` with the platform verifier (more crates and an OS dependent trust store). Nothing in the lockfile gave an HTTP client before, so the feature adds 16 crates (the list is in the pull request); `ring` is the large one, and it is C and assembly that `rustls` needs for TLS in any case.

What the transport enforces, each with a test against a loopback server written in the test (plain sockets, 127.0.0.1 only): certificate verification is on and there is no way to turn it off (the agent config is asserted, since a TLS server cannot be run locally without a certificate fixture, which is ticket #927); https only and only `api.typesafe.ai` (`Target::parse` refuses http, another host, a look-alike host, user info, a port and a path, and the call URL is that base plus a fixed path); no redirect is ever followed (a 3xx comes back as a status and the `Location` is never contacted, tested for 301, 302, 303, 307 and 308 with a second listener that must stay unconnected); a hard connect timeout (10 s) and a hard total timeout for the whole call, body included (60 s); a reply bound of 4 MiB, applied to a declared length and to a chunked body alike; no proxy and the proxy environment variables are not read (there is no opt-in yet, ticket #928: a proxy would see where the key goes and could defeat the host pin, so it needs its own design); the key only in the `Authorization: Bearer` header, from the `ApiKey` the client reads from `TYPESAFE_API_KEY` at each call, and a key that could split a header (a control character) is refused before any connection; no `Content-Encoding` is negotiated, so a reply that has one is refused. Failures are `Network` with no detail. The only body kept from a non-success reply is that of a 400, 401 or 403 (bounded), for `error_type`; a 422 or any other status keeps no body at all, so no error, Debug or Display can hold the key or the echoed message (tested with a body that echoes the key). The 429 and 529 handling is the retry policy of part A, driven here by the real transport (a 429 then a 200 succeeds with the server's `retry-after-ms` honoured, a persistent 429 stops after two retries, a 401 is not retried). `real_client(config)` is a `JevClient` on this transport with the default retry policy, the system clock and sleeper and a jitter from the standard library's random hasher.

Multipart images (#915). A request with images is sent as `multipart/form-data` as images.md recommends: the first part is `request` (`application/json`) whose assets name a file part (`part`, `format`, no `data_base64`), then one file part per image (`image-0000`, ..., content type `image/png` or `image/jpeg`) with the file bytes as they are. The boundary is the first of a numbered series that occurs nowhere in the data. `Prepared` carries both forms: `body()` is the all JSON base64 form (kept, not sent by the real transport) and `multipart()` is the form that is sent; the 32 MiB limit is checked on the multipart size (the JSON plus the files plus 512 bytes of framing per part), which is what goes on the wire, and the expanded estimate keeps its conservative 2x on every use of every image (the documentation says each use adds the image again and processing can re-encode it, with no factor given, so no smaller number is claimed). Whether the real API accepts our multipart exactly as documented is verified by the live test, not yet by a run (#918).

Not done, by decision: request compression (#916). The `flate2` crate is not in the lockfile, `zstd` is a C dependency, and the 32 MiB limit applies to the compressed body too, so compression saves bandwidth only on requests that are small next to the model time; a valid gzip stream without compression would add nothing. The ticket stays open. Also not done: a local TLS test (a certificate fixture or `rcgen` is needed), a proxy opt-in, and wiring `klatch-bench judge-eval --judge jev` to this transport: that command is in #925, which was not merged when this was written and was written against the earlier `JevTransport::post` shape that part A replaced with `send`, so it needs main merged into it first; with the feature on it passes `klatch::jev::http::HttpTransport::new()` as the transport (ticket #929).

The live test. `src/jev/http/live.rs` has one `#[ignore]`d test, `jev_live_all`, which needs `TYPESAFE_API_KEY` and is never run by CI or the gate (the gate lints and tests the feature, ignoring it). It replays the made-up text checks of #911 (models, choice, noul) and adds score, an image in the state, in the instructions and in the criteria (all multipart), a box, the same image as base64 JSON, a bad key, an unknown model, and a burst of 60 requests over 4 threads without retries to look for a 429 or 529 and the shape of their retry hints. It records for each reply only the status, the `error_type` (the three known values) and whether the reply parsed, plus the shape of `retry-after` (absent, a number, not a number); never a body or message text. The picture is drawn in the test (a red square on white, a valid PNG made with stored zlib blocks and a CRC, no dependency) and the text is made up. Run it with `doppler run --project governingdocs --config dev_alex -- cargo test -p klatch --features jev-http -- --ignored jev_live` (add `--nocapture` to watch); the lines are also written to `$TMPDIR/klatch-jev-live.txt`.

Policy changes that come with the feature: `deny.toml` now checks all features (so the optional crates are held to the policy) and has one narrow exception, `CDLA-Permissive-2.0` for `webpki-roots` (the bundled root certificates are data under that permissive licence, notice only). A build that ships `jev-http` must add that notice to `THIRD-PARTY-LICENSES.txt`; `about.toml` does not accept it yet, on purpose, because nothing shipped links the crate.
