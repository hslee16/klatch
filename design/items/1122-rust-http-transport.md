The Rust client connects to klatch-server http over loopback TCP, behind an off-by-default feature (#1122; no schema change; 2026-11-21).
**Question.** How does the Rust client get the same HTTP and SSE transport the Python and TypeScript libraries have (item 1114, #1124), without putting a network socket type into the shipped `klatch` binary?

**Decision (the human, 2026-11-21).** The `klatch` crate may gain a TCP type behind a feature that no default, release, wheel, npm or Homebrew build enables, with a narrow allowance in the `no_telemetry` scan, the same shape as `client-socket` (item 1095).

**What was built.** `Client::connect_http(url, member, token)` and `Client::connect_http_with(url, member, token, &HttpOptions)`, in `proto/klatch/src/client/http.rs`, built on `Client::over`. The stream is `GET /v1/stream`; each `data:` line is one frame line (comments, `event:` and `id:` lines are ignored); each request is a `POST /v1/frames` with `X-Klatch-Session`, retried while the server answers 429 (inbox full, at most 40 tries 50 ms apart). Both carry `Authorization: Bearer TOKEN` and `X-Klatch-Member`. A 401 is `Error::Api` with code `identity.refused` (the message never repeats the token). The member is verified; there is no typed-name floor over HTTP.
- Loopback only, checked before any socket opens: `http://127.0.0.1:PORT`, `http://localhost:PORT` (taken as 127.0.0.1, never resolved) or `http://[::1]:PORT`; no other scheme, host, userinfo, path or query, and port 0 is refused. A member or token that is not visible ASCII without spaces is refused too, so a value cannot split a request. Both refusals are `Error::Session`.
- Reconnect: when the stream ends without a close, the reader reopens it (`reconnect_attempts`, default 5, `reconnect_delay` times n between tries), drops the new session's `hello`, and resubscribes each subscribed room from the last `seq` seen, so there is no gap and no repeat. When that fails the session is over and the client reports a session error.
- Deadlines: opening a connection, sending a post and reading its status use `connect_timeout` (default 10 s). The stream read itself has none (heartbeats keep it busy; `close` shuts the socket, which unblocks it), as in the other libraries.

**Why the binary stays network-free.** `TcpStream` is named in exactly one file, `src/client/http.rs`, declared `mod http;` directly under `#[cfg(feature = "client-http")]`. `client-http = ["client"]` is in no other feature, so `default`, `cli` and `client` never turn it on. `tests/no_telemetry.rs` allows `TcpStream` in that file only, while the parent declares it that way (no `TcpListener`, no resolver, no other socket type, anywhere), and new tests assert that no feature turns `client-http` on, that it brings in nothing but `client`, and that no other path gets the allowance. `klatch-server` asks for the feature in its dev-dependencies only.

**Tests.** `proto/klatch-server/tests/client_http.rs` runs against the real `klatch-server http` in a throwaway home under /tmp, with a credential issued in process: the whole conformance scenario of `proto/klatch/tests/client_scenario` unchanged (the including crate now also provides `ATTRIBUTION`, `verified` here), a refused credential, urls refused before a spy listener sees a connection, header values refused, nothing listening, close, a reconnect with no gap and no repeat, and a killed server. The broken stream is injected with `HttpFault`, not provoked from the platform. A stand-in server checks the headers sent, `data:` lines as frames, a 429 retried and a 500 not retried. Every wait has a deadline and no stream is read to its end.

**What this does not cover.** Windows and Linux runs (the suite ran on macOS); a read timeout on a half-open stream (the other libraries have none either).
