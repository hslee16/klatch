MCP over Streamable HTTP on the loopback listener of `klatch-server http` (#1060, phase 4 of epic #1056; no schema change; 2026-11-21).
**Question.** How does an MCP client that speaks only HTTP use the klatch tools, with the identity and limits of phase 3 and nothing new to trust?

**What was built.** `proto/klatch-server/src/mcp_http.rs`, routed from `wire_http.rs` at `POST /mcp` on the listener the wire routes already use. Each request is one JSON-RPC message handed to the same `McpServer` over the same `SharedGateway` that `klatch mcp --stdio` and `klatch-server channel` use, as a `Session` for the credential's member; so a tool means here what it means there. A request is answered `200` `application/json` (the JSON answer the 2025-06-18 specification lets a server give instead of an event stream); a notification or a response from the client is `202` with no body; a batch is `400` (that revision has none), bad JSON `400` with a parse error. `GET` and `DELETE` are `405` with `Allow: POST`, the specification's answer for a server that offers no stream.

**No session id.** Every request stands alone and is authenticated on its own, so there is nothing to resume, nothing to hijack and nothing to delete, and no state that could outlive a revoked credential. The cost is that nothing can be pushed to the client: no server-initiated messages.

**Channels are stdio only.** `initialize` over HTTP never declares `experimental['claude/channel']` (the adapter's `with_channel` is not called), because nothing can push `notifications/claude/channel` over a request and its answer. A test pins the absence.

**Who is calling.** The function `authenticate` of phase 3: `Authorization: Bearer` with `X-Klatch-Member`, checked live (token, expiry, revocation) on every request; every failure is the same `401 unauthorized`; no typed-name tier. A credential revoked mid-conversation is refused at the next request (tested). The caller is the credential's member; a `member` or `sender` argument of a tool is ignored. After the credential: `Origin` (a page on another origin, including `null`, is `403`: DNS rebinding cannot reach a loopback server through a browser), the body size (`413` before it is read), `MCP-Protocol-Version` (`400` for a revision other than 2025-06-18; absent is accepted), `Accept` (`406` when a JSON answer is refused).

**Limits** are the listener's: 16 KiB headers, 1 MiB bodies, a 5 second deadline to read a request, `--max-connections` shared with the wire streams, loopback only. A `klatch_wait` call holds its connection for up to its own bound (55 seconds).

**Tests** (`klatch-server/tests/mcp_http.rs`, the server as a child process, a temp store, a read timeout on every socket, no open stream read to its end; unit tests in `mcp_http.rs`). The ten integration tests were red first (no route). Not done: a bench scenario (the bench cannot drive a `klatch-server` child, #1078); an event stream for server-initiated messages and session ids (needs a use for them first); TLS and remote use (#157, #161, phase 5).
