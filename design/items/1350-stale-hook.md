A killed forwarder leaves a stale webhook; the watcher reports it and prints the fix, it never deletes (#1350; no schema change; 2026-11-22).
`gh webhook forward` creates a development webhook and removes it on a clean exit, so a forwarder ended by `kill -9`, a crash or a reboot leaves the hook and every restart fails with HTTP 422 "Hook already exists" until a person deletes it. The ticket offered two fixes: the wrapper deletes the hook itself, or the watcher detects it and tells the human. The second is chosen (the safe one, in keeping with the read-only watcher). `gh-watch-forward` now runs gh as a supervised child (SIGTERM is passed on, so `launchctl bootout` still gives gh its clean exit), and on exit 1 with "Hook already exists" it deletes nothing: it writes one line, `stale webhook on the repository: run gh-watch clean-hooks`, leaves the marker `forwarder.stale` and exits 75, so launchd's `ThrottleInterval` spaces the retries. `gh-watch status` ends with `forwarder down: stale webhook` (exit 5) when the forwarder is down and the marker exists.

    `gh-watch clean-hooks` is the only launcher command that calls gh: one read-only `gh api repos/OWNER/REPO/hooks`, run only when the human asks. It lists hooks named `cli` whose URL is the GitHub forwarding service and prints `gh api -X DELETE .../hooks/ID`; it deletes nothing. A `--delete-stale` flag was considered and not built: even with the name and URL checks and no local forwarder process, a hook that looks identical may belong to a live forwarder on another machine, and a wrong delete silently blinds that watcher, so the delete stays with the human. The receiver is untouched (still no gh call and no HTTP client). Stopping the forwarder with `launchctl bootout`, never `kill -9`, is documented in PR-SWEEP.md and the session-start section of CLAUDE.md.
