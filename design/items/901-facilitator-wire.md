A facilitator can route over MCP: the wire methods `join` and `asks` and the tools `klatch_join`, `klatch_asks` and `klatch_invite` (#901, follow-up of #190; part of #180; no schema change; 2026-11-20).
The facilitator (#190) creates rooms, reads open asks and invites, but `klatch mcp --stdio` had only post, read, claim, release, who and wait, and the wire had `invite` but no `join` or `asks`, so an MCP-only facilitator could not route. Two wire methods now call the same gateway methods as the commands: `join` (`room`, result `{}`, the caller only, making the room when new, so the room-creation capability and the role checks apply) and `asks` (`room`, result `{ "asks": [...] }`, each `seq`, `sender`, `text`, `ts`, `claimed`, `waiting_on_asker` and the working `room`; the guard sees a read without advance, so a room above the caller's clearance is refused). The MCP server gets `klatch_join`, `klatch_asks` (its result carries the data notice, since an ask is another member's text) and `klatch_invite` (the existing `invite` method). Each has a wrapper in the Python, TypeScript and Rust clients; `tests/client_methods.rs` checks them. PROTOCOL.md section 5, INTEGRATION.md and `proto/AUTHZ-AUDIT.md` list them, and the known gap for #901 is closed.

  The wire `join` does not carry the harness evidence the command line gives (`join_with_harness`), so a join over the wire is the generic floor, which is what a caller without such evidence stays. Cycles through asks, which `klatch asks` also prints, are not on the wire result; a client derives them from `asks` and `claims`.
