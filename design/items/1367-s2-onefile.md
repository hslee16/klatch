Scenario S2 of the coordination bench is built for the clone topology: three agents change one file at once on the onefile fixture, with a hidden checker and a history-based overwrite metric (#1367; no schema change; 2026-11-23).
Epic #1362 needs the scenario where claims matter: several agents told to change the same file with no ordering. F2 `onefile` is a standard library settings renderer whose whole logic is `onefile/core.py` (about 120 lines with the three changes in). Three tickets change it together: A adds a `timeout` option and `parse_timeout`, B adds a `retries` option and `backoff_delays`, C changes `render_header` and adds a `label` option. They overlap on purpose: every ticket adds a row to the shared option table at the same place, two (A and B) add a kind to the shared `format_value` helper at the same place, and two append a function at the end of the file, so concurrent edits really conflict at merge, and an agent that copies a stale file or force pushes silently drops a colleague's work. The header prints the number of table rows, so the three changes also have to agree in the merged file. The visible tests cover only the old behaviour and survive all three changes. The fixture's `reference/` (the full solution and each ticket's edit as fake-agent steps) is never in a checkout.

The hidden checker `checks/onefile/` loads `core.py` by file and tests each ticket on its own against independent oracles and seeded random inputs, so a lost colleague's change cannot hide behind a working one. It prints units completed (0 to 3), structural checks (the whole table, the integrated render, the import, conflict markers, the visible tests), a merge state (clean, conflicts-left, tests-broken), `lost_edits` (tickets missing from main), `lost_table_entries` and per-author commits and surviving lines (git blame). Its `--file` mode says which tickets one version of the file has.

The scenario file `scenarios/s2.json` holds arms B0 B1 K1 K2 K3 (K3 not at M0), N 20 per arm at M0 (the cheap binary scenario), the SPEC 8.1 caps (1.80 USD a run, 60 USD for one topology) and the metric definitions. The harness fills `overwrites` as edits committed anywhere and missing from the final main: it runs the checker's per-ticket test on the file as every non-merge commit of the origin and of every agent's clone has it, and counts a ticket that passed somewhere and fails on the final main. From that it splits `silent_overwrites` (no agent saw a git conflict) from `overwrites_after_conflict` and counts `conflicts_resolved` (conflicts in a run that ended with all three changes in main). The fake agent gained a `replace` step (an edit of the file as it is, not a copy of a stale one). Tests run the checker on the reference and on eleven broken variants (one ticket missing, each ticket alone, a silent overwrite, conflict markers, a broken shared helper two ways, a lost table entry, wrong results, a file that does not import), and the metrics through the whole harness with fake agents that cooperate in sequence, collide and resolve, collide and leave it, overwrite silently with a force push, resolve destructively and give up.

Two gaps are stated, not hidden. Topology T-shared (one working directory for all agents, the primary topology for the K arms in SPEC S2) is not built: run.py makes one clone per agent, the prompts say so, and a shared checkout needs its own run mode, prompt variant and final-file-only metrics; it is ticketed as follow-up. `claim_conflicts` (needs the K arms' store export) and `time_to_recover_s` (needs the time of the first conflict, which the stream parser does not keep) are null with the reason in the scenario file. Per-run granularity of the silent split is a known approximation: a run with any conflict puts all its lost edits under `overwrites_after_conflict`. Nothing here ran a model or spent money; the real run, the human's budget approval and the arms review (#1365) remain, and the ticket closes when M0 results exist.
