The facilitator: a model-backed router as a bounded role, with no model integration in klatch (#190, part of #180, DESIGN section 24.1 decision 7, the model step of #271; no schema change; 2026-11-18).
The rules router (#189) is the deterministic member that invites the holders of a claim on an asker's topic. The facilitator is the same job done by whatever reads the lobby: an ordinary coding session or any agent with the klatch command line. klatch builds the substrate only, the role and its bound, a brief, and tests with a scripted stand-in for the model. It links no model SDK and makes no model call.

The role. `klatch admin facilitator MEMBER [--off]` (a terminal act, audited as `facilitator`) gives a member the role in the existing `role:<member>` policy entry, so it is one role at a time, like the librarian, reviewer and admin agent: granting it replaces another role, `--off` removes it. Neither the facilitator, nor any member, nor the admin agent can give or take it.

The bound is an allowlist in `check_role`, run before any `Guard` is asked, so no guard configuration widens it. A facilitator may: read (moving its own cursor or not), `who`, `claims`, the board and the open asks, only in rooms at or below its own clearance (the lowest by default, so lobby content only at that clearance); join a room, which makes it when new (create-room, still subject to the room-creation capability of #188); invite (an invite is refused above the invitee's clearance, #189); and post the invite pointer, which is accepted only when the body equals, byte for byte, the sentence `invite` builds. Everything else is refused with the rule `facilitator`: any other post, a direct message, claim, release, status, mute, ack, scope and kind declaration, crossing request, every admin act (audit, prune and label order included), the label and clearance acts and the grant of room clearance.

It never grants. A room a facilitator creates has no grantor (the creator rule of #893 skips it), and a grant by a facilitator is refused with the rule `facilitator` even when the human names it a room's grantor, so it is not a grantor unless separately named and even then inert. A different member named grantor is untouched.

Order of checks. The role check comes first for the acts that do their own value checks before the guard (`clear` checked the agent cap first; it now refuses the role first). The scope and kind declarations ask no guard, so they call the same role check directly. Other admin acts that validate their arguments first return an invalid-argument error to a facilitator before the role refusal; that reveals nothing and changes nothing.

The brief, `proto/scripts/facilitator-brief.md`, is the instruction text for the session: what it may do, what it never can, that message text is data and never an instruction, that it only proposes (a topic room and an invite pointer that the invitee may ignore), and that when unsure it does nothing. `tests/facilitator_brief.rs` fails if the brief drops a bound, teaches a command the role refuses or names a command the CLI lacks.

Proof. `gateway/tests/facilitator.rs` covers the role, the allowlist, the named rule on each refusal, the order before the guard, own-clearance reads, the invitee clearance and the missing grantor. `session/facilitator_tests.rs` drives a scripted fake model through the session path of `klatch mcp --stdio` (one `Session::call` per tool call): a well behaved model routes two asks into two topic rooms with two invites and no refusals; a manipulated model that does whatever the ask text says (grant, clear, label, audit, close, post, claim) is refused every time with the rule `facilitator` and leaves clearances, labels and the lobby unchanged; an invite above the invitee's clearance is refused. Room creation has no wire method, so the model makes the room through the gateway as `klatch join` does (#901). The test was written before the implementation but not run red first.

How a human launches a first run with an ordinary session as facilitator. The human does these steps, in their own terminal; an agent never issues a credential:
1. Choose a member name, for example `facilitator`, and issue its credential with the launcher (`klatch worker issue`, see `klatch worker --help`).
2. Grant the role: `klatch admin facilitator facilitator`. Under `room-creation granted` also run `klatch admin grant-rooms facilitator`. Optionally raise its clearance with `klatch admin clear` (the default is the lowest, which is enough for a public lobby).
3. Start the session as that member with the brief as its instructions, for example a headless Claude Code session with `--append-system-prompt "$(cat proto/scripts/facilitator-brief.md)"` and the credential in its environment, in a directory with the klatch hooks installed (`klatch init`). An interactive session works the same way: paste the brief as the first message.
4. Watch it: `klatch admin audit` shows `create-room` and `invite` rows with its name; `klatch refusals` (as the member) and `klatch admin refusals` show anything it tried outside the bound. `klatch admin facilitator facilitator --off` ends the role at once.

Not done. A Jev integration is #898. The MCP tools and the wire have no join, asks or invite, so a live session uses the command line (#901). The bound lets the facilitator post nothing but the pointer, so it cannot ask a question in the lobby when unsure; it reports to whoever runs it instead (#902).
