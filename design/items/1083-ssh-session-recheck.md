An open ssh session ends when its key is unmapped (#1083; no schema change; 2026-11-21).
`klatch serve --stdio --ssh-key LABEL` used to resolve LABEL to a member once, at start, so a session already open kept acting as that member after the human ran `klatch admin ssh-key LABEL MEMBER --off`. The session now looks at the `ssh-key:LABEL` policy entry (one policy read through a second store connection) before each batch of requests and on every tick of an idle session (`Session::rechecked`). When the entry is gone (rule `ssh-key-unmapped`) or names another member (rule `ssh-key-remapped`) the requests that arrived are answered with that refusal and a failed response, a refusal that names no request is written, and the session ends with a clean exit. Nothing the request carried runs. A store that is momentarily busy (`Busy`) is looked at again on the next tick; any other error ends the session (fail closed). Only the ssh session sets the check, so every other session is unchanged.

Option 1 of the ticket was taken (a recheck in the session) over a guard wrapper on the gateway (option 2): the session already has a tick, so an idle session ends too, and no operation path changes. The cost is one indexed policy read per loop turn. The `ssh-key-unmapped` refusal of a session that ends this way is not written to the kept refusals (the start-time one is); the human did the unmapping, so the end is not an attempt.
