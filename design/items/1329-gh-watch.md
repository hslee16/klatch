A webhook-driven GitHub watcher tells the coordinator instead of polling (#1329; no schema change; 2026-11-22).
`proto/scripts/gh-watch` pairs `gh webhook forward` (run by the human, who holds the `admin:repo_hook` scope) with a loopback receiver written in standard-library Python. **Shape:** the receiver binds a loopback address only, accepts `POST /hook`, verifies `X-Hub-Signature-256` (HMAC SHA-256) against a secret read from a mode-0600 file, caps the body, drops events outside an allow-list and repeated `X-GitHub-Delivery` ids, then turns an event into at most a few one-line notes: ALERT for a failed or timed-out check or workflow on the default branch, a failed check on an open non-draft PR, or a PR whose `mergeable_state` is `dirty`; INFO for PR and issue lifecycle and for `main moved to SHA; open PRs may now conflict`. Notes are appended to a log flushed per line (for `tail -F` and the Monitor tool) and optionally posted to a klatch room by an installed binary as a named member.

**Why read-only:** the watcher has no GitHub client, no `gh` call and no code path that merges, labels, comments, pushes or closes; a test checks the source for any of them. The sweep acts, the watcher tells. **Why not the server intake or `klatch anchor github`:** they need the human passphrase (#1267); this needs no key and no store access. **Payload text is data:** titles, branch names, logins and labels lose control and format characters, are truncated, and are never run, evaluated or put into a command. **Limits:** events are missed while the forwarder is down, so one slow poll stays as the backstop; `mergeable_state` is often null right after a push; the payload does not say which checks are required; `gh webhook forward` passes the secret as an argument visible to the same user. The audit table is unchanged: nothing is added to the server.
