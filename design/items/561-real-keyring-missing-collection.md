A missing login collection on a real gnome-keyring reads as locked, not as no key (#561; no schema change; 2026-11-22).
The stand-in tests for #561 matched the text `Unknown object`, but gnome-keyring's own bus answers `Object does not exist at path` when the login collection was never created. Run in the container (Debian 12, aarch64) that left an existing store reporting "no key" instead of a locked-keyring error, the case the item was meant to close. The check now accepts both wordings; a locked collection (`Locked` is `b true`) already read correctly. A silent miss whose state cannot be read stays a miss, because custody still refuses to make a key for an existing encrypted store.

The Linux container harness now runs both real states: `run.sh locked` starts the daemon without a login collection, then makes the collection and locks it, and asserts a Locked error for read and delete in each. The real-keyring tests also build their backend under a service name of their own again; since the detecting read of #562 `detect` took the key name, so all of them shared one service and raced.
