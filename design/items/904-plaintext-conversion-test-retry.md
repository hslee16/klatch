The plaintext conversion test runs the conversion again after a busy refusal (#904; no schema change, no code change; 2026-11-19).
A refusal ("another klatch has the store open; stop it and run this again") is the conversion's designed answer when an old klatch keeps the plaintext open for longer than the wait, and it changes nothing, so it is not data loss; the flaky CI failure was the test unwrapping the first conversion while a writer thread opened and closed the store every millisecond, which on a loaded Linux runner can out-wait the 300 ms test limit. The test now does what the message says (run it again, up to 500 times, checking each refusal left the plaintext in place) and still checks that every write the old binary was told succeeded is in the encrypted store. A second test pins the retry without a clock: an old klatch holds the store until the first refusal, then lets go, and the second run converts every row. No product code changed. The failure could not be reproduced on macOS under heavy CPU load (90 runs), so the diagnosis rests on the code path and the CI message, not on a local red run.
