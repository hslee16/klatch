coordbench maps an agent's own budget or turn stop to spend-cap or turn-cap, and the even per-agent budget split is an open design question (#1553; no schema change beyond the new outcome word turn-cap; 2026-11-25).
`claude -p` ends an agent that used its --max-budget-usd with a result of subtype error_max_budget_usd (terminal_reason budget_exhausted) and one that used --max-turns with error_max_turns, both exit code 1. Until now the harness saw only the nonzero exit and recorded `crash`; the S3 B1 pilot (approval ceiling 1 USD) showed outcome crash with valid true and 4 of 4 units correct. `agentcap.py` now reads the result subtype and terminal_reason that `streams.py` keeps in each agent's summary: any worker (a cut session, the killed S6 victim and the role members excluded, as for crash) that stopped on a cap makes the run `spend-cap` (budget) or `turn-cap` (turns), spend first when both happened, and the notes name each agent with its subtype, spend and turns. The SPEC had no turn-cap outcome, so section 7 gains `turn-cap` and `schema.OUTCOMES` the same word. An agent that exited nonzero for another reason is still a `crash`; a run the harness itself stopped on the run cap or the wall cap keeps `spend-cap` or `timeout` as before.

    Metric semantics are unchanged and `metric_version` stays 2: a run with outcome crash, spend-cap or turn-cap already stays in the ledger and in the denominator and is scored on what the hidden checker found (SPEC section 5); only the label in the outcome counts moves. A report that pools old records of this kind will still show them as crash; there are no such records in the repository. The statistics side has one open inconsistency (censoring, #1613): report.py censors only `timeout`.

    The per-agent budget is the run cap divided by the agent count (an even split, passed as --max-budget-usd). It was not changed here; it is a pre-registration question for the owner. The evidence: the S3 pilot gave 0.33 USD to each of 3 agents and agent b hit it after finishing its part, while the recorded B1 pilot streams under tests/fixtures/pilot-b1 show that agents with the same prompt differ by a factor of 1.6 in spend (a 0.0910 USD in 13 turns, b 0.1492 USD in 21 turns, both success). In S3 agent c blocks and waits for the handoff, so it polls and re-reads the board and legitimately spends more than an agent that does not block; an even split stops the busiest agent first while the others still have budget, so the arm that coordinates by waiting pays a cap penalty a non-waiting arm does not. Options, none chosen: (1) keep the even split and report spend-cap as a result of the arm (simple, biased against waiting); (2) a per-agent cap that is a multiple of the even share (for example 2x) while the run cap stays the binding total; (3) no per-agent budget, only the run total and the turn cap (the harness already stops the team on the run total); (4) per-role shares fixed in the scenario, set from the pilot cost of each role. The decision belongs with the owner before the first registered run (#1612).
