Backend cancel hook: a look blocked in the backend ends at an ACP session/cancel (#1562)
What the ticket asks. #1564 made `session/cancel` visible while a prompt runs, but a look already inside `Backend::handle` was only dropped when it returned. For the in-process gateway that is a bounded store read; for a backend whose look can wait (the shared gateway, where the owner thread serves one request at a time) it is a hang until the owner is free.

Design. `Backend` gains two methods with defaults. `canceller()` returns an `Arc<dyn CancelHook>` (`Send + Sync`, so the thread that reads the input can call it while the handler thread is blocked); the default is `NoCancel`, whose `cancel(call_id)` returns `false`: it never claims a cancel it did not do (#485). `handle_cancellable(who, call, harness)` returns `Outcome::Done(frames)` or `Outcome::Cancelled`; the default runs `handle_as` to its end and is never `Cancelled`, which agrees with the default hook. `cancel` returns `true` only for the first cancel of a look in flight; a repeat, an unknown id and a look that finished are `false`, so a cancel storm is a bounded set of map lookups.

The shared backend (`gateway/shared/cancel.rs`). Each `handle_cancellable` registers a flag under the call id (the table belongs to one `SharedBackend` handle and a clone starts a new one, because two connections may both have a request "1"; a duplicate id in flight is simply not registered, so a cancel never reaches the wrong look), queues the job as `handle` does, and waits on the owner's reply with a 20 ms tick that looks at the flag. A cancel raises the flag; the waiter answers `Cancelled` within one tick. The job checks the flag when the owner reaches it: a look that never began does nothing (no read, no refusal row, no audit row). A look the owner is already running finishes with every check and audit it passes and its answer is dropped; the cancel never reaches into the owner and releases nothing (a look holds no claim, cursor or lease). The entry is removed by a guard that removes only its own entry, however the wait ends.

ACP. The reader thread knows each prompt's JSON-RPC request id, so both threads derive the call id from it (`acp-<id>`); on `session/cancel` the reader raises the prompt flag (as before) and calls the hook for that call id. The handler makes the look with `Session::call_cancellable`; `Cancelled` ends the prompt as the not-yet-started case does: `stopReason` `cancelled`, no `session/update`, never a partial answer. Only the named session's outstanding prompts are touched.

Where a wait blocks on this path and how it ends. (1) The queue behind the owner thread in `SharedBackend::handle_cancellable`: the cancel hook, within one tick. (2) The owner running the look itself (a store read bounded by the store's timeout): not interrupted; the waiter has already left. (3) The ACP handler's idle wait for input: bounded by its one second tick, and a cancel is read by the reader thread, not this wait. (4) The reader's send into the 64-line queue when the handler is busy: ends when the handler takes a line or drops its end. (5) The reader's read of the input: ends with the input. The in-process `Gateway` backend has no wait of its own (a look is a synchronous store read in the calling thread), so its hook stays the honest default. `klatch wait` and `Transport` waits are loops in the caller over short polls and do not go through `Backend`.

Tests. `session/cancel_hook_tests.rs`, every wait deadline-bound: cancel during a blocked look, cancel of a look that had not started (no effect), after completion, wrong id, two concurrent looks, two connections with the same id, the default hook, a 100-cancel storm, 200 cancel cycles with a flat thread count, and ACP end to end with the owner still held.
