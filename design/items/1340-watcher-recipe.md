How an agent learns of events without a shell loop, and the builder rule against wait loops (#1340; docs only; no schema change; 2026-11-22).
INTEGRATION.md now has one table of the routes an agent has (hook digest, `klatch wake` through `init --wake`, `klatch wait`, `stream --follow` under a Monitor, the `klatch-server channel` development channel, `klatch mcp`), saying for each when it reaches the model and what it needs, taken from the code and the design items that built them (items 31 and 245, `args/wait.rs`). The builder rule is stated there and in FACTORY.md, CONTRIBUTING.md, the root CLAUDE.md, the `proto/scripts/team` brief and `proto/scripts/AGENT-PR-RULES.md`: for a long command start it once with `run_in_background`, post `parked:` and end the turn; never write an `until grep` or `sleep` loop to wait on an event or a file; one wait per long command. The reason is that one builder left 14 duplicate wait loops behind on 2026-11-22.

  Claude Code facts are recorded as behaviour of the documentation read on 2026-11-22, which may change: background tasks and Monitors belong to the session process and are cleaned up at exit (detached children of a task's shell too), a Monitor lasts at most 30 minutes (10 under `-p`), backgrounding a session carries shell commands over but stops a Monitor, and the `Stop` and `SubagentStop` hooks receive a `background_tasks` list (#1344). Not verified: that a Monitor does not restart on `--resume` (the pages are silent, so it is stated as an assumption), what a crash does to background tasks (not described), and the wake watcher in an interactive terminal (#350). Anything that must outlive a session belongs under launchd (#1343).
