Admin passphrase rows are written only by the proof, with an audit of every refused write (#1275; no schema change; 2026-11-24).
The verifier (`admin-passphrase`), the failure counter (`admin-passphrase-fails`) and the unlock window (`admin-unlock-secs`) live in the policy table (#1233). Three options were on the ticket. (b) built: `PolicyStore::policy_set`, the one generic writer every gateway method uses, refuses any key under the `admin-passphrase` prefix and the window key (`is_proof_key`), set or clear, and a new method `reserved_policy_set`, called only from `proof/`, writes them and refuses every other key, so the two writers never overlap. (c) built in part: a refused generic write keeps an audit row `policy-reserved-refused` with the key name as target and an empty detail (never the value); every change the proof commands make already has its own row (`passphrase-set`, `passphrase-changed`, `passphrase-reset`, `passphrase-rehashed`, `unlock-window`). Not built: an audit of a change made by a writer that skips the store API (SQL on the open store). A SQLite trigger would record it but needs a schema migration and a process holding the store key can drop the trigger, so it is detection of the careless only; it is left to the choice of (a).

(a) Not built, a decision for the human: a MAC over the three rows under a key kept outside the store. The key would have to live somewhere a same-user process that already holds the store key cannot read: a Keychain item with user presence (macOS), a separate OS user that owns the key, or a daemon socket. That is a credential and keystore decision (#318, #1261), so it is not taken here; the MAC and the trigger audit are worth building only once such a place exists. Until then the limit stays as SECURITY.md states it: a same-user process holding the store key can rewrite the rows without the klatch command line.
