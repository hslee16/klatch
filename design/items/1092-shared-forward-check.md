A test fails when SharedTransport has no forward for a Transport method (#1092; test only; no schema change; 2026-11-21).
`SharedTransport` implements `Transport` through a `forward!` list. A new required trait method with no forward already fails to compile (E0046), but only after both changes are in one tree, which is how #1085 and #1087 slipped past review and were caught by the integration gate. A new trait method with a default body is worse: it compiles, and the handle silently runs the default on the caller's thread instead of the owner's.
`klatch/tests/shared_forward.rs` reads `gateway/transport.rs` and `gateway/shared.rs`, collects the trait's method names and the names the handle implements (the `forward!` entries and the hand-written methods), and fails naming every trait method with no forward. `post` is the one allowed exception (its default only calls `post_labeled`, which is forwarded); an exception is added to `DEFAULTED_ON_PURPOSE` with a reason. The test also fails if its parse finds too few methods, so a layout change cannot make it pass vacuously. It was red first against a probe trait method with a default and no forward. The single-method-list and trait-split options in the ticket stay open under #1069 and #1071.
