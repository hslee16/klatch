The coordbench harness clones the bare origin with --no-local, so a clone no longer races an agent's push (#1435; 2026-11-23).
The coordbench harness checks progress during a run by cloning the run's bare origin into a checkout (the poll checkout, `check-poll`) every few seconds, and clones it once per agent at the start and once more for the final check. A clone by path is a local clone: git walks `objects/` of the origin and links or copies the files one by one. While an agent's `git push` is being received, `objects/` holds quarantine and temporary entries that git renames or removes, so the walk now and then fails ("failed to copy file ... No such file or directory"). `run.git` raised, `run_one` caught it as a setup error, and the run ended early with a record that has no scenario metrics. That is what showed up as intermittent failures in `test_k1_and_k2_run_end_to_end` and in the S1, S2 and S3 tests under load, each passing on rerun.

Every clone of the origin in `run.py` now passes `--no-local`. The clone then goes through upload-pack, which reads one consistent snapshot of refs and objects and ignores whatever else is in `objects/`. This is a condition that holds by construction, not a wait or a retry. A test plants a directory in `objects/` that a local clone cannot open and checks the run still finishes `ok` (red before the change: `failed to iterate over .../objects/`).

The race was reproduced in isolation: a loop of local clones against a pusher failed once in 172 clones with the message above, and the harness-level runs failed too rarely to see in a few hundred runs, so the proof of the fix is the mechanism plus the zero-failure suite runs recorded on the pull request.
