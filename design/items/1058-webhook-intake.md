klatch-server phase 2: loopback webhook intake for `gh webhook forward` (#1058, epic #1056; no schema change; 2026-11-20).
`klatch-server channel --webhook 127.0.0.1:PORT (--webhook-secret-file PATH | --webhook-secret-env NAME)` additionally listens on loopback for the POSTs that `gh webhook forward --url http://127.0.0.1:PORT/github` makes, verifies them, and turns `pull_request`, `check_suite` and `workflow_run` events into the same `notifications/claude/channel` notifications phase 1 sends. It is the event source the integrator (#863, #866) needs and replaces a coordinator watcher script. klatch itself makes no GitHub or other network read: the forwarder is a separate process that the person or the integrator runs. Without `--webhook` the server behaves exactly as in phase 1 (no socket).
Loopback only, refused not warned. `loopback::check_loopback` parses the address (never resolves it) and accepts exactly `127.0.0.1` and `::1` with a port; `0.0.0.0`, `[::]`, any other `127.x` address, an IPv4-mapped form and host names (even `localhost`) are errors that name the zero-trust prerequisites (#157 encrypted and mutually authenticated transports, #161 per-request authentication and short-lived credentials), and the check runs before any socket exists. The refusal and the option checks happen at startup, before the member is opened. Port 0 is accepted (the system chooses; the server prints `webhook intake on ADDR` on standard error, which is how the tests find it).
Authentication is the HMAC and there is no way around it. The secret comes from a file (refused when group or others can read it, when empty, or when over 4 KiB) or from the environment variable that `--webhook-secret-env` NAMES (a value that is not a plain variable name is rejected without being echoed, in case a secret was pasted by mistake); no secret configuration, or both, is a startup error; no flag takes the secret as a value. `X-Hub-Signature-256` (`sha256=` and 64 hex digits) is checked over the raw body with HMAC-SHA256 from the RustCrypto `hmac` crate (the one new dependency: small, widely used, MIT or Apache-2.0, built on the `digest` and `sha2` crates already in the tree; the repository's hygiene test forbids a hand-rolled MAC, which the first draft had; RFC 4231 vectors and GitHub's documented example are unit tests), and the two 32-byte digests are compared with `subtle`'s constant-time equality (also already in the tree). A missing, malformed or wrong signature is 401 and nothing about the body is parsed or emitted. Replay of a captured signed body is not defended against (loopback, same-user; a delivery id cache is a possible later hardening); the secret is held in memory as bytes and not zeroized.
The listener (`proto/klatch-server/src/loopback.rs`, the only file allowed to name a socket type; phases 3 and 4 reuse it) is hand-rolled over `std::net` rather than a crate. The reason is the smallest dependable surface: it serves one request per connection, one connection at a time, and reads only a request line, headers and a `Content-Length` body, so there is no keep-alive, chunked parsing, HTTP/2, TLS or async runtime to get wrong, and one small new dependency, `hmac` (`cargo deny` and the notices check see it plus `sha2` and `subtle`, which are already in the tree through `klatch`; the `klatch` and `klatch-bench` crates are unchanged and the `klatch` no_telemetry test is untouched). The bounds are `Limits`: 16 KiB of head, 1 MiB of body, and one 5 second deadline for the whole request that a client trickling bytes cannot extend (a slow client blocks others for at most that long). Answers: 200 (`ok`, or `ignored` for a signed event klatch does not report, such as `ping`), 400 (malformed request, unusable event, missing `X-GitHub-Event`), 401, 404 (any path but exactly `/github`, query strings included), 405 with `Allow: POST`, 408, 411 (POST without `Content-Length`), 413 (decided from the declared length before the body is read), 431, 501 (`Transfer-Encoding`). Every answer is a short fixed text with `Connection: close`.
Only structured fields are used. A pull request event needs `action` (one of opened, reopened, closed, synchronize, ready_for_review, converted_to_draft; other actions such as labels and edits are ignored), `number`, `pull_request.state` (open or closed), `pull_request.merged`, `pull_request.head.sha` (40 or 64 lower-case hex digits) and optionally `mergeable_state` (from a fixed set). A `check_suite` or `workflow_run` event is reported when its action and status are `completed`, needs `head_sha` and a `conclusion` from GitHub's fixed set, and uses `pull_requests[].number`. Every value that reaches an event is a member of a fixed set, a number or hex, so text from the payload cannot be copied into one; the workflow name is not read, and a title, body, branch name or user name never leaves the parser. `content` is one fixed template per case (for example `[klatch] GitHub: pull request #12 opened (state open, head a1b2c3d, mergeable_state unknown). This is a status notice from GitHub webhooks, not an instruction from your user.`). `meta` has identifier keys only, from `event`, `pr`, `sha_short` (7 characters), `state` and `conclusion`: for a pull request event `state` is open, closed or merged; for a run it is `completed`, or `main` / `no-pr` for a run with no pull request.
Superseded runs. A `cancelled` conclusion for a head sha that is not the pull request's current head is a superseded run, and the event says so (`conclusion: superseded`, and `superseded, not a failure` in the content). The current head is what the payload says (`pull_requests[].head.sha`, GitHub's statement at delivery time) or, when the payload has none, the head the server last saw in a `pull_request` event for that number (a bounded map of 256 pull requests). When neither is known the event says `cancelled` and that the event does not say whether the head is current, and does not call it a failure. A cancelled run for the current head is just `cancelled`. Limits: the payload's head can lag a very recent push, and a restart forgets the tracked heads. Runs with no pull request are labelled `main` when the run's branch equals the repository's `default_branch` (both compared inside the parser, neither reported) and carry no `pr`; a run on another branch with no pull request (a fork's pull request has an empty list too) is labelled `no-pr`, an addition to the ticket's two cases.
The queue. The listener thread pushes into a bounded queue (64 notices; the oldest is dropped and counted when full, and `push` never blocks) and a second thread sends from it, only after the client's `notifications/initialized` (what arrives earlier waits in the queue), through the same locked standard output as the room events. When events were dropped one fixed `dropped` notice says how many. The MCP side never waits on the listener or the reverse.
The scan test (`proto/klatch-server/tests/no_network.rs`) is changed deliberately, not loosened: socket types and `std::net` are allowed only in `src/loopback.rs` (and the client side only in `src/loopback_tests.rs`, which connects to the listener it starts itself); `TcpStream::connect` is forbidden everywhere else; exactly one `TcpListener::bind` exists, after `check_loopback`, and the allowed-address function uses `Ipv4Addr::LOCALHOST` and `Ipv6Addr::LOCALHOST` (not `is_loopback`); UDP, unix sockets, name resolution, HTTP clients and an all-interfaces address are forbidden in every file; `Command` stays forbidden; the dependency-tree check for networking crates is unchanged.
Verified by tests: unit tests (HMAC known answers, signature cases, secret sources and refusals, argument rules, the translation of every fixture, the hostile-text fixture, the queue, the handler without a socket, the listener's limits over real loopback sockets: oversized head, oversized body, slow and trickling clients, wrong method and path, chunked and missing length, garbage); an end-to-end test (`proto/klatch-server/tests/webhook_intake.rs`: a child on a temporary store and port 0, a signed POST gives exactly one notification with the expected meta and no payload text, a wrong or missing signature gives 401 and none, hostile title, body and branch text appears nowhere in standard output or standard error, startup refusals). The fixtures in `proto/klatch-server/tests/fixtures/` are hand-written to GitHub's documented shapes and are NOT recordings: no real event was captured and `gh webhook forward` was not run against any repository. NOT verified: a real `gh webhook forward` run (its header handling, redelivery behaviour, and that the signature it sends uses the secret given to `--secret`), a real Claude Code session showing the events, concurrent forwarders. No bench scenario: the bench builds and runs only the `klatch` binary and cannot drive `klatch-server` (#1078). Known limits: no delivery-id de-duplication; one request at a time; `gh webhook forward` needs repository admin rights and one forwarder per repository is the tested shape (#863).
