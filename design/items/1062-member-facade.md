The member setup is a library facade, `klatch::member`, so a second binary does what `klatch mcp --stdio` does (#1062; prerequisite of #1057, epic #1056; pure move; no schema change; 2026-11-20).
`klatch-server` (epic #1056) has to open the encrypted store, find the key, settle who the caller is and build the gateway from the same environment as `klatch mcp --stdio` (`KLATCH_NAME`, `KLATCH_SCOPE`, `KLATCH_HOME`, `KLATCH_KEY_DIR`, `KLATCH_IDENTITY_FILE`), with the same guards, and the code to do that was private to the `klatch` binary. Decision (the coordinator, 2026-11-20): move it into the library behind one small facade and make the binary a caller of it, with no copy of security-sensitive logic. Option 3 of the #1057 comment (spawn the installed `klatch`) was not taken.
Moved, files and tests unchanged except for paths and imports: `custody.rs` (store open and key source), `identity.rs` (caller discovery, credential file handling, the member name a session keeps), `scope.rs` (scope, attrs, kind) now live under `klatch/src/member/`, and `wake_pointer` (was `commands/wait.rs`), `now`, `CliClock`, `db_path` and the gateway-and-principal part of `run_as_member` are in `member/mod.rs`. The facade is `open_member(&Who, Call) -> Result<Option<Member>>` (a `Member` is the gateway and the `Caller`, with `principal()`), plus `Who` (the `--as-member`, `--discover`, `--codex`, `--member-scope`, `--member-kind` flags as plain data), `Call` (does the command read a hook's JSON from standard input; is it the SessionEnd hook), `now`, `db_path`, `CliClock`, `wake_pointer`, `discover_session` and `registry_and_domain`. The binary keeps its clap types (`WhoFlags`, `Cmd`) and maps them to `Who` and `Call`; `run_as_member` is now `open_member` followed by the same match as before.
Visibility: `identity` and `scope` are private modules of `member`; only the items above are `pub`. `member::custody` is `pub` and `#[doc(hidden)]` because the binary's `admin`, `worker`, `run`, `anchor`, `judge` and `doctor` modules use the key functions (backup, restore, rotation, archive key settling, label keys); it carries no stability promise, like `keys` and `store`. Nothing the binary could not reach before is reachable that was not already `pub` in a hidden module, and no check was weakened: every guard (the credential check, the refusal of another member's name under a credential, the session-id rule for hooks, scope validation, sealed label keys limited to the member's clearance) is the same code.
Evidence that nothing changed: the full workspace tests (2739 passed, 8 ignored, before and after, plus the one new test), the gate, and the whole bench (126 scenarios passed, 0 regressions) gave the same results before and after, and the no_telemetry, zero-trust and AUTHZ-AUDIT tests ran with only their file paths updated. `wake_pointer` still names `std::env::current_exe()`, so a different binary that calls it names itself; a server that wants the `klatch` path in the pointer needs its own text (not decided here). The one new test, `tests/member_facade.rs`, opens two members through the facade in a temporary home with its own key directory and posts and reads a message; it was written after the move (the facade did not exist before it), so it was not red first.
