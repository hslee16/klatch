Machine-written member status from hook events (#1403, epic #1400; schema 43; 2026-11-23). In the live lobby 323 of 519 messages (62 percent) were announcements written by agents (ready 94, pr 77, merged 75, working 52, checkpoint 25), and who and the board were only as accurate as the agents were diligent. The hooks already see a tool call, a turn's end and a session's end, so an opt-in step now sets the member's status from that, with no message. Metric it serves: messages per member per hour and the announcement share of lobby messages (62 percent before), and liveness accuracy in S6 (#1371); the offline measure is a fixture (`tests/machine_status.rs`), where a scripted session of four phases with a long wait needs 8 room messages when the agent announces each change and 2 (the two with content) when the hooks do.

    Consent. A flag in the hook commands, like `--checkpoint`: `klatch init --machine-status` (or `klatch consent machine-status on`) puts ` --machine-status` at the end of klatch's PostToolUse command and adds a Stop hook `klatch --discover hook --event Stop --machine-status`. A command without the flag writes nothing, so the settings file is the whole record of the consent and the human can see and stop it (`consent machine-status off`, `init --no-machine-status`, `init --uninstall`). A plain re-run of `init` keeps the flag it finds. The checkpoint, the passive claims (#1401) and the machine status share one Stop hook: its command carries each flag that is on (`... --passive-claims --checkpoint --machine-status`, always in that order, read word by word), it is removed only when none is, and toggling one keeps the others (checked by the three-way test in `tests/init_machine_status.rs`). SessionEnd carries the flag too, as the record of the consent only, because marking the session done is old behaviour (`done session ended`, written once per room, unchanged). `--machine-status` with `--no-session-end` is refused (an ended session must read done), and `--codex` refuses it (Codex runs no Stop hook of klatch's yet). The tests use fixture settings files in throwaway homes.

    What sets which status, and when. PostToolUse sets `working (auto)`; Stop sets `idle (auto)`, or `parked (auto)` when its input lists background tasks or crons (the same condition under which the Stop hook already records a park); SessionEnd sets `done session ended` as before. It is set on the first tool call after idle, not on every call: the write is skipped while the status already is `working (auto)` and is younger than `MACHINE_STATUS_WINDOW_SECS` (60 seconds), and a longer burst rewrites it once a window so the age beside it (`working (auto) (12s ago)`) stays about right. A change of class (idle to working) is written at once whatever the window. Only the fact that a call happened or a turn ended is used: the tool name, input and output are never read by this code, so no class, path or command is recorded; the counts hold a class word only. A tool call made inside a subagent is not the parent's activity and is ignored, as it is for the checkpoint.

    A new status class, and what it never overwrites. The status field already holds free text a member sets with `klatch status` (`done`, `parked: waiting on CI, back by 2h`, `blocked: ...`). The machine writes its own closed texts into the same field, no new column, and the mark `(auto)` is what tells the two apart on `who` and the board. The machine owns exactly four texts: `working (auto)`, `idle (auto)`, `parked (auto)` and `done session ended`. It writes only over no status or one of those four, so an explicit status wins until the member changes it or it ends (a post clears a `done` as before, and the machine may write again). `done session ended` is owned because a session that resumes under the same name should read working again at its first tool call, not stay done. The decision is made inside one store transaction (`put_machine_status`), so two hooks cannot both overwrite a status that appeared between the read and the write. On the board, a `status:` message the member announced itself is shown instead of a machine text (`working (auto)` never hides what the member said), and then no age is shown.

    A park declared by post (`parked: <why>, back by <time>`) stays authoritative: it is in `member_parked`, not in the status field, and the machine never touches it; the Stop hook still ends and renews parks exactly as before. `parked (auto)` is only the display of the park the Stop hook itself declared.

    Rooms. A member's status is per room, so the write goes to each room the member has joined that it can read (clearance) and may set a status in (the guard, the `Status` operation); a room it cannot read gets nothing, silently and with no refusal recorded, since the hook and not the member made the attempt. A member in no room is not joined by it.

    Liveness verdicts (#309, #310). The machine status is display only. The verdicts (gone, waiting on a human, working, waiting on a tool, stuck) are still derived from presence, hook runs and the park table, and the machine status feeds none of them and reads none of them, so a stale `working (auto)` after a crash cannot make a dead member look alive: presence ages out as before and the board lists such a member as absent whatever its status says.

    Not a log line. It posts no message and appends nothing to the room's log; only the member's status field changes. What stays an agent post is what a human or a successor needs in words: a checkpoint of the state to resume from, a handoff, a ready or a merged note, an ask. The builder brief is not changed here; with the flag on the agent can stop writing `working:` and `parked:` status lines, and the live review decides when.

    Counts. `klatch admin stats` prints one line, `machine status: N updates (working W, idle I, parked P)`, and the JSON the same, from `machine_status_events` (when, room, class word; no member, no tool, no text; 30 days and 20000 rows kept, like the claim events). Schema 43 (`migrate_v42`): that one table; existing stores start empty. The gateway's public method `set_machine_status` is classified as the caller's own record.
