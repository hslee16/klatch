A cascade judge: Jev first, a stronger judge for what Jev does not decide confidently, and an offline simulator (#936; no schema change, no new wire method or command; judge-slot composition plus bench tooling; 2026-11-19).
The first results (proto/klatch-bench/judge-eval/results/2026-11-19) showed two judges that fail in opposite ways. Claude Sonnet is the best judge (about 99 percent, 0 to 1 leaks on corpus 1) and takes about 3 s an item; Jev alone leaks 21 to 29 percent of what should not cross but answers in about 150 ms, and its confidence is informative (a leak rate of at most 1 percent needs a threshold of 0.95 on dev and 0.80 on test, so the threshold is unstable). The judge slot holds one judge, so a judge made of two is new: `CascadeJudge` (src/domain/cascade_judge.rs) implements `Judge` over an ordered pair, with an explicit `CascadePolicy`.

The policy. The first stage is a `Reader`: it reports a `Reading` (its pick, the probability of the pick, its confidence) or none. The policy decides which readings are taken without asking the second judge, and every knob is a field: `deny_threshold` (default 0.9): a first-stage deny is accepted when the probability of the deny reaches it; a deny only holds a message back, so this is the lower bar. `allow_threshold` (default 0.98): a first-stage allow is accepted only when both the probability and the confidence reach it; an allow is the one outcome that lets text cross, and for a choice the confidence is never above the probability, so requiring both only makes it stricter. `redact_threshold` (default none): a first-stage redact is always escalated, because the first judge has no text to redact with (Jev returns none); a number accepts a redaction as the placeholder `[redacted by the first judge]`, which can only narrow. A knob set to none means that outcome is never accepted without escalating. Everything not accepted, and a first stage that gave no reading (gated, unreachable, a reply that did not parse, a NaN), goes to the second judge, whose verdict is final. If the second judge defers or fails the cascade defers: it never falls back to the first judge's weaker pick and never allows by default. So the cascade allows only what the second judge allowed, or what the first judge was very sure of; either stage may narrow. The defaults are conservative starting points to be tuned on dev, not numbers measured to be right.

Label gates. A hosted stage is behind its own gate and the gate is not repeated by the cascade. The first stage is wrapped in `GatedReader` (off by default; text only when its label is strictly below the ceiling; any failure is no reading), the same rule as `HostedJudge`; Jev implements `ReadingTransport` (`JevJudge::read`, its pick, probability and confidence before any threshold). The Claude judge keeps its own ceiling check (`label_below_ceiling`). Text at or above the ceiling is never sent to either stage and the cascade defers (tested with a hosted fake behind each stage). The cascade is wired into no gateway path and adds no command or wire method; the production slot stays a single judge until someone composes one in configuration.

Reporting. `CascadeJudge::decide` returns the verdict and which `Stage` decided (first, or second; a second-stage defer means neither decided), and the bench records it through `EvalJudge` (`Judged.stage`, `Record.stage`, a `stage` field in each result row). The report prints the escalation rate with a Wilson interval; latency (p50, p99) is end to end and tokens and cost are summed over the stages actually called.

Running it (from proto/; the Jev line needs the key and `--features jev-http`, the Claude stage needs the `claude` CLI):

    doppler run --project governingdocs --config dev_alex -- cargo run -p klatch-bench --features jev-http -- judge-eval --judge cascade:jev:jev-1.14.0:0.9,claude:sonnet --split dev --out cascade-dev.json

Both stages must report a pick, so each is `claude:<model>` or `jev:<model>[:<threshold>]` (rules and null report none). The deny threshold is `--deny-threshold`, else the first Jev stage's own threshold in the spec (so the example uses 0.9), else 0.9; the allow threshold is `--allow-threshold`, else 0.98 raised to the deny threshold when that is higher; `--redact-threshold` is off unless given. The Jev stage's own verdict is not used (only its pick), so a low threshold in the spec also works when the deny threshold is a flag.

The simulator. Running Claude on every item for every threshold would cost a run each; the combination can be worked out from two recorded runs. Record each judge once on the same items with `--out` (the first with a low Jev threshold such as `jev:jev-1.14.0:0.01` so every pick is recorded), then:

    cargo run -p klatch-bench -- judge-eval cascade-sim --first jev-dev.json --second sonnet-dev.json [--thresholds 0.5,0.7,0.8,0.9,0.95,0.99] [--allow-thresholds 0.9,0.95,0.98,0.99,1.0] [--redact-threshold F]

It prints the two judges alone as recorded and then one row per (deny threshold, allow threshold) pair with accuracy, strict leaks, over-blocks and escalation rate with Wilson intervals, deferrals, mean end-to-end latency and total cost, and calls no judge. It reads each row's pick, probability and confidence (a file written before this change has no probability, and the confidence stands in; that can only make the simulation escalate more than the real cascade), applies the same `CascadePolicy` code as the real cascade, and for an escalated item takes the second judge's recorded verdict and its leak and over-block flags. It refuses two files from different splits, with different item sets, or with a different ground truth for the same id (a results file does not name its corpus, so the item ids and truths are how a different corpus or corpus version is told), and a file that is not a runner `--out` file.

Limits. The simulation reuses the second judge's recorded verdicts; the second judge is not run as a second stage, is not deterministic, and its prompt does not know about the cascade, so a real cascade run can differ, and the real run is the figure to report. The simulation also assumes the second judge's verdict on an item does not depend on which threshold escalated it. The rule for thresholds is dev to choose, test to score once: the two splits disagreed about Jev's leak-free threshold (0.95 and 0.80), so a threshold read off the split being scored is tuned to it. The hard corpus (`corpus-hard.jsonl`, #931) exists; the coordinator runs it with both the real cascade and the simulator, and the search items in it were kept because one judge got them wrong, so score design and search items apart (`--origin`). Corpus 1 is too easy to separate strong judges, runs are single (no variance), and one author's labels are the ground truth (#924).
