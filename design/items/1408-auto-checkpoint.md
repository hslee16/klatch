Automatic machine checkpoint at Stop and SessionEnd (#1408, epic #1400; schema 42; 2026-11-23). Agents rarely wrote the `checkpoint:` and `handoff:` words (checkpoint 25 of 519 posts, handoff 1), so a session that ended or was compacted took its working state with it. An opt-in step in the Stop and SessionEnd hooks now writes a compact machine checkpoint beside the member's durable task, so a successor or the same member after a resume loses nothing it could not have said itself. Metric it serves: lost work at handoff in S3 (#1368) and time to the first correct contribution after resume in S9 (#1374); the offline measure is a fixture (`tests/auto_checkpoint.rs`), where of five facts a successor needs (three files edited, a claim held, an ask open) only the ask is recoverable through klatch without the checkpoint and all five with it.

    Consent. The consent is a flag in the hook commands, like `--wake`: `klatch init --checkpoint` (or `klatch consent checkpoint on`) adds a Stop hook `klatch --discover hook --event Stop --checkpoint` and puts ` --checkpoint` at the end of klatch's own PostToolUse and SessionEnd commands. A hook command without the flag records nothing, so a settings file is the whole record of the consent and the human can see and stop it (`consent checkpoint off`, `init --no-checkpoint`, `init --uninstall`). A plain re-run of `init` keeps the flag it finds. `--checkpoint` with `--no-session-end` is refused (the last checkpoint is written by SessionEnd), and `--codex` refuses it (Codex runs no async or Stop hooks of klatch's yet). The tests use fixture settings files in throwaway homes.

    What is recorded. PostToolUse input carries `tool_name`, `tool_input` and `cwd`. klatch keeps the class of the call, from a closed list (edit, write, run, read, other; an MCP tool's own name is the user's text and becomes `other`) and, for an edit or a write only, the path made repo-relative: cleaned against `cwd`, then taken under the nearest directory at or above `cwd` that holds a `.git` entry (else `cwd`); a path outside it, longer than 120 bytes or with a control character is dropped. The command line, the file content, the old and new strings and the tool output are read by the hook and dropped; they never reach the gateway, and the gateway itself refuses a class outside the list or a path that is absolute, has `..` or a control character, so the trail cannot carry text a hook did not mean to send. A tool call made inside a subagent is not the parent's work and is not recorded. The trail (`member_trail`, one row per member) keeps the 24 latest distinct files, newest last, and the 8 latest classes.

    The checkpoint. At a Stop and at a SessionEnd the gateway builds one line for each of the member's rooms that it can read through the guarded `board` and where it works (an open task, a live claim or an open ask there; else the default lobby, so a member with nothing declared still leaves one): `turn ended` or `session ended (reason word)`, `claims` (its live claims there), `asks open` and `waiting on me` (numbers of its own asks, never their text), `status` (the first word of its last status), `files` (newest first) and `tools`. A room the member can no longer read refuses at the board and gets nothing; a room where it does no work gets nothing, so work paths are not shown in a direct message or an unrelated room. Everything is a path, a number or a closed word; nothing comes from a message body, so nothing of a sealed label reaches it. A Stop with nothing to say writes nothing; a SessionEnd always writes. Byte cap: 600 bytes (about 150 tokens), enough for eight or so paths and the rest of the line yet cheap where a task line or briefing shows it. Over the cap the oldest files go first and are counted (`files a b +9`), then the tools, and a line still too long is cut at a character boundary.

    Retention. One row per room and member in `machine_checkpoints`, replaced and never appended (`put_machine_checkpoint` deletes then inserts in one transaction). A reader ignores one older than a task is held (a week, `TASK_HOLD_SECS`), and pruning spares a member with one inside that window and takes its rows with the member afterwards. Removing a member from a room takes its checkpoint there. The SessionEnd checkpoint is written before the claims are released, so it names them.

    Explicit checkpoints. The owner's own `checkpoint:` always wins: the task line shows it first, and the machine one follows marked `machine checkpoint N ago: ...`; a newer explicit checkpoint does not erase the machine one and the machine one never replaces the explicit one (they live in different places: the log and the table). A member with no open task gets a stand-in task titled `session` that says `no task declared`, so a member that never wrote `working:` still leaves where it stood; a member whose last status word was `done` leaves no stand-in.

    Compaction and clear. The hook docs list the SessionEnd reasons `clear`, `resume`, `logout`, `prompt_input_exit` and `other`; compaction is not one of them (it fires SessionStart with matcher `compact`). Decision: at `clear` and `resume` a final checkpoint is written (the model's context is gone, the work is not), the trail is cleared with it (the next context starts a new trail), and the row stays for the member's next session and for others; at compaction nothing is written and nothing is lost, because the checkpoint of the last Stop stands and the session start board shows it. The reason is mapped to one word of five before it is used; the text of an unknown reason is never kept.

    Counts. `klatch admin stats` prints one line, `machine checkpoints: N written (M at session end), K replaced an earlier one, B bytes`, and the JSON the same, from `machine_checkpoint_events` (when, room, replaced, last, bytes; no text column, 30 days and 20000 rows kept, like the claim events). The no-leak test over every option combination covers it. Schema 42 (`migrate_v41`): `member_trail`, `machine_checkpoints`, `machine_checkpoint_events`; existing stores start empty.
