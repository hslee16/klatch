klatch-server ships as the second binary of every release archive, the platform wheels and the Homebrew formula (#1236; decision D1 of the release epic #1232; no schema change; 2026-11-21).
Before this, `klatch-server` had `publish = false`, no `--version`, and was in no archive, wheel or formula, so the MVP scope (the daemon over a Unix socket, loopback HTTP and MCP, the webhook intake) could not be installed. Decision D1 (human, 2026-11-21): it ships next to `klatch`. The pieces: (1) `release/package-archive.sh` builds each archive with `klatch`, `klatch-server`, LICENSE and THIRD-PARTY-LICENSES.txt under one directory and refuses to build one without both binaries; `release/check-archive.sh` asserts that exact layout (and that both are executable) and, with `--smoke`, unpacks the archive and runs `release/check-packaged-server.sh` on the server in it. build-release.yml calls both for each of the six targets, so what CI packs is what `release/test-package-archive.sh` tests (with stand-in binaries, no build). (2) The two binaries are built by two `cargo build` invocations, not one, so the `klatch` binary is exactly what `cargo build -p klatch` makes and `klatch-server` stays its own artifact. (3) One CycloneDX 1.5 SBOM per archive covers both: cargo-cyclonedx runs once per binary and `release/merge-sbom.py` merges the two (klatch's metadata, klatch-server as a component, every component and dependency once by bom-ref); the workflow fails if `klatch-server`, `subtle` or `hmac` is missing from the result. (4) The notices need no new config: cargo-about and cargo-deny already run over the whole workspace with all features, so klatch-server's own crates (libc, sha2, subtle, hmac) were already in THIRD-PARTY-LICENSES.txt and under the deny policy; `proto/check-notices.sh` now also fails if klatch-server itself or any crate in the dependency tree of either binary is missing from the file, so this stays true. (5) The platform wheels put `klatch-server` in `<name>.data/scripts/` beside `klatch`, so pip installs both on the environment's PATH; `build_wheels.py` takes the second binary from the same archive, checks the macOS minimum of both, and refuses an archive without it; the workflow asserts the contents of every wheel (both scripts, executable, both licence files). The npm package is the TypeScript client and never held a binary, so it gets nothing. (6) `install/install.sh` extracts the one archive whose SHA-256 it verified (it covers both binaries), refuses it if either binary is missing, writes both beside their targets and renames only when both are written, so an existing install is replaced whole or not at all; UNINSTALL.md removes both. (7) The Homebrew formula lives in the tap repository, not here: RELEASING.md now says the bump must install and test both binaries, and the tap change is ticketed.

    The claim. `klatch-server` does open sockets, so "no telemetry, no outbound calls" (true of `klatch`, pinned by `proto/klatch/tests/no_telemetry.rs`) is not reused for it. SECURITY.md and the README state a second claim: klatch-server opens loopback listeners only, starts no program and makes no outbound connection. It is backed by `proto/klatch-server/tests/no_network.rs` (dependency tree and source audit, the one `TcpListener::bind` after the loopback check, the daemon's single Unix listener and probe), now also by a test that the optional `jev-http` transport (ureq, rustls, ring, webpki-roots) is not in its build, a test that both documents state the claim, and, on the packaged binary of every archive, `release/check-packaged-server.sh`: `--version` prints `klatch-server <version>` (a new flag; `-V` too), `--help` names the subcommands, `http --listen 0.0.0.0:0` and `[::]:0` are refused with a refusal message, and `daemon --socket` in a throwaway home starts, makes its socket, stops on SIGTERM and removes it. Like the audit for `klatch`, this is a check of what the code could do and of three behaviours, not a capture of one run's traffic.

    Crates.io. The recommendation, taken: `klatch-server` stays unpublished (`publish = false`; `no_network.rs` pins it). Reasons: `cargo install klatch` keeps installing only the network-free binary, so nobody gets a socket-opening program by accident through the crate named in the README; the binary reaches users through the archives (checksummed, signed, attested, with the SBOM), the wheels and Homebrew, which is where the checks above run; a second published crate would need `klatch = { path, version }`, its own `cargo publish --dry-run --locked` in CI and the gate, a lockstep entry in `release/check-versions.sh`, and a trusted-publishing entry on crates.io, all for a path nobody asked for. A user who wants it from source runs `cargo install --locked --git https://github.com/hslee16/klatch klatch-server`. Publishing it later is a decision that removes `publish = false`, changes the `no_network.rs` pin and adds the dry run.

    What is not covered here: the real six-target build and the SBOM merge on real cargo-cyclonedx output are only exercised by the Release dry run workflow (manual); this change was checked locally for the host target (release build, the archive made by the same script, its listing, the packaged-server check on the real binary, a wheel built from the archive). The musl and Intel targets are built and smoke tested by that workflow, as before.
